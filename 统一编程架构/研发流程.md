# AI 驱动一体化研发流程

## 1. 一句话说明

这是一套从“业务诉求”到“业务建模语言”、再到“Backend 出码、测试、上线、反馈迭代”的研发闭环。

核心目标是让研发过程中的角色、工具、产出物和 AI 提效点都标准化，使 AI 能稳定参与需求结构化、模型生成、影响分析、出码解释、测试补全和运营反馈归因。

## 2. 流程总览

```text
业务诉求 / 客户需求 / 运营反馈 / 生产缺陷
        │
        ▼
1. 需求提出与澄清
        │
        ▼
2. 需求规格编写
        │
        ▼
3. 需求结构化
        │
        ▼
4. 业务建模语言建模
        │
        ▼
5. IR 校验与影响分析
        │
        ▼
6. Backend 出码
        │
        ▼
7. 测试验证
        │
        ▼
8. 上线运营
        │
        ▼
9. 反馈回流与新需求迭代
```

## 3. 一页式总览

| 阶段 | 主责角色 | 工具（组件 / AI） | 核心产出物 | 效率提升预估 |
|------|----------|------------------|------------|--------------|
| 需求提出与澄清 | 产品经理、运营人员 | 需求管理工具、运营反馈平台、AI 需求摘要 | 需求背景、业务目标、待确认问题 | 20%～40% |
| 需求规格编写 | 产品经理 | 需求规格模板、AI 需求补全、业务知识库 | 需求规格、验收标准、变更范围 | 20%～40% |
| 需求结构化 | 产品经理、业务架构师、建模工程师 | AI 结构化助手、Frontend、模型设计器 | 结构化需求、对象草稿、流程草稿、规则草稿 | 30%～60% |
| 业务建模语言建模 | 建模工程师、业务架构师 | VS Code Studio、业务建模语言设计器、Frontend、Middle、AI 建模助手 | 业务建模语言文件、模型文件、统一 IR | 30%～60% |
| IR 校验与影响分析 | 建模工程师、开发工程师、测试工程师 | Middle、语义校验器、影响分析器、AI 影响摘要 | 校验报告、影响分析、复用资产清单 | 40%～70% |
| Backend 出码 | 开发工程师 | Backend、Java / C++ / SQL Generator、CLI、AI 代码解释 | 代码、配置、测试骨架、工程结构、生成报告 | 50%～80% |
| 测试验证 | 测试工程师 | 测试平台、测试执行器、AI 测试用例生成 | 测试用例、测试数据、测试报告、缺陷单 | 30%～60% |
| 上线运营 | 运维 / 运营人员 | CI/CD、监控平台、日志平台、AI 告警摘要 | 发布记录、运行指标、异常记录、运营反馈 | 20%～40% |
| 反馈回流与迭代 | 产品经理、业务架构师、开发 / 测试 / 运维 | 影响分析器、业务建模语言仓库、AI 缺陷归因 | 迭代需求、模型变更、测试补充、知识条目 | 20%～40% |

## 4. 角色与产出物

| 角色 | 负责什么 | 主要产出物 | AI 怎么帮 |
|------|----------|------------|-----------|
| 产品经理 | 定义业务目标、需求范围、验收标准 | 需求规格、验收标准、优先级、变更范围 | 摘要诉求、补全场景、发现异常路径、生成追问清单。 |
| 业务架构师 | 识别业务对象、流程、规则和领域术语 | 业务模型、流程模型、规则模型、领域术语 | 抽取规则、发现冲突、推荐历史模型和复用资产。 |
| 建模工程师 | 将需求转换为业务建模语言 | 业务建模语言文件、模型文件、统一 IR | 生成模型草稿、补全引用、解释模型诊断。 |
| 开发工程师 | 基于 IR 和生成结果完成工程落地 | Java / C++ / SQL、配置、工程代码、生成报告 | 解释生成代码、定位差异、建议人工扩展点。 |
| 测试工程师 | 验证需求、模型、IR 和代码是否满足验收 | 测试用例、测试数据、测试报告、缺陷单 | 补全测试场景、生成测试草稿、建议回归范围。 |
| 运维 / 运营人员 | 发布、监控、收集运行反馈 | 发布记录、运行指标、异常记录、运营反馈 | 摘要告警、归因日志、识别异常趋势。 |
| 架构治理人员 | 维护语言规范、生成模板和资产治理 | 语言规范、生成模板、资产目录、治理报告 | 审查规范、提取可复用资产、沉淀知识。 |
| AI Agent | 辅助结构化、生成、校验、解释和归因 | 建议稿、模型草稿、测试草稿、修复建议 | 必须输出来源、置信度、待确认项和无法判断项。 |

## 5. 产品经理的需求规格

产品经理产出的需求规格，是后续建模、校验、出码和验收的输入契约。它不应只是自然语言长文，而应按固定结构表达。

| 规格项 | 应写清楚什么 |
|--------|--------------|
| 业务目标 | 解决什么业务问题，成功标准是什么。 |
| 业务场景 | 哪些用户、系统、业务动作、触发条件参与。 |
| 角色权限 | 谁能发起、审批、查询、修改、撤销。 |
| 业务流程 | 正常流程、分支流程、异常流程、回退流程。 |
| 业务规则 | 校验、计算、准入、状态流转、风控、权限规则。 |
| 数据对象 | 业务对象、字段、枚举、状态、主从关系、唯一性约束。 |
| 接口协作 | 输入输出、超时、重试、异常处理、依赖系统。 |
| 验收标准 | 功能、数据、流程、异常和回归验收条件。 |
| 非功能要求 | 性能、容量、安全、审计、可用性、兼容性、合规。 |
| 变更范围 | 影响哪些产品、模块、接口、数据、报表、权限。 |
| 优先级 | 必须实现、可延后、明确不做。 |

AI 友好要求：

- 每条需求、规则、对象、接口和验收标准都要有编号。
- 业务目标、流程、规则、对象、接口、验收标准分开写。
- 对不确定内容标记“待确认”，不要混在正文里。
- 保留来源材料，如客户反馈、运营数据、缺陷单、监管要求。

## 6. 需求如何转成业务建模语言

需求不会直接生成代码，而是先进入业务建模语言体系。

```text
需求规格
  │
  ▼
结构化需求
  │
  ▼
业务建模语言 Frontend
  │
  ▼
业务建模语言模型 / AST / 初步语义结构
  │
  ▼
业务建模语言 Middle
  │
  ▼
统一 IR
```

转换过程：

| 步骤 | 输入 | 处理 | 输出 |
|------|------|------|------|
| 需求结构化 | 需求规格、验收标准、历史模型 | AI 抽取场景、流程、规则、对象、接口、测试语义 | 结构化需求 |
| Frontend 解析 | 结构化需求、模型文件、DSL 输入 | 解析业务建模语言、可视化模型或元数据 DSL | 模型结构、AST、初步语义 |
| Middle 治理 | 模型结构、元数据、规则、测试语义 | 做语义校验、类型检查、引用检查、影响分析 | 统一 IR、诊断报告 |
| 仓库复用 | 统一 IR、场景、领域标签 | 检索组件、模板、规则、测试和翻译模板 | 复用资产清单 |

结构化需求应拆成六类对象：

| 对象 | 说明 |
|------|------|
| 场景 | 业务场景、触发条件、前置条件、后置结果。 |
| 流程 | 流程节点、条件分支、状态流转、回退动作。 |
| 规则 | 规则名称、输入、判断条件、输出、失败原因。 |
| 对象 | 业务对象、字段、枚举、状态、约束。 |
| 接口 | 服务接口、输入输出、异常模型。 |
| 测试语义 | 正常用例、异常用例、边界用例、回归范围。 |

## 7. Backend 如何出码

Backend 负责把统一 IR 翻译为目标语言代码、配置、测试代码和工程产物。

```text
统一 IR
  │
  ├─ Java Generator ──► Java 服务代码 / 接口适配代码 / 单元测试
  ├─ C++ Generator  ──► C++ 业务代码 / 低延迟交易逻辑 / 测试代码
  ├─ SQL Generator  ──► SQL 查询 / 脚本 / 数据处理逻辑
  ├─ 配置生成器      ──► 接口配置 / 规则配置 / 部署配置
  └─ 测试代码生成器  ──► 单元测试 / 集成测试 / 回归测试骨架
```

Backend 出码的输入和输出：

| 类型 | 内容 |
|------|------|
| 输入 | 统一 IR、目标语言参数、工程模板、翻译模板、测试语义、元数据规范。 |
| 输出 | Java / C++ / SQL、配置、测试代码、工程结构、生成报告、差异报告、追踪关系。 |
| 质量要求 | 可重复、可构建、可测试，代码能追踪到需求、模型和 IR 来源。 |
| AI 友好要求 | 生成报告记录 IR 版本、模板版本、生成文件、人工扩展点和失败原因。 |

开发工程师主要处理三类工作：

- 补充 IR 暂时无法表达的少量工程适配代码。
- 处理生成器暂不支持的目标语言细节。
- 根据测试和评审结果修正模型、模板或人工扩展点。

## 8. 上线运营与反馈迭代

上线不是流程结束，而是下一轮迭代的输入来源。

```text
上线发布
  │
  ▼
运行日志 / 监控指标 / 告警 / 用户反馈 / 生产缺陷
  │
  ▼
反馈归类与影响分析
  │
  ▼
需求规格更新
  │
  ▼
业务建模语言模型更新
  │
  ▼
IR 校验与 Backend 重新出码
  │
  ▼
测试回归与上线
  │
  ▼
资产沉淀到业务建模语言仓库
```

上线后重点收集：

- 运行日志、异常堆栈、告警事件。
- 性能指标、容量指标、稳定性指标。
- 用户行为、业务结果、运营反馈。
- 生产缺陷、应急修复、回滚记录。
- 与需求目标不一致的业务偏差。

迭代原则：

- 先做影响分析，再决定修改需求、模型、IR、Backend 模板或人工代码。
- 优先修改需求规格和业务建模语言模型，再重新生成代码。
- 生产缺陷必须补充测试语义和回归用例。
- 可复用规则、模板、缺陷模式和经验沉淀到业务建模语言仓库。

## 9. AI 友好的研发资产标准

AI 要稳定参与研发流程，关键不是只接入大模型，而是让产出物结构化、可追踪、可校验、可复用。

| 资产类型 | 必备字段 | AI 可执行动作 |
|----------|----------|---------------|
| 需求规格 | 需求 ID、背景、目标、场景、规则、对象、接口、验收标准、优先级 | 摘要、补全、冲突检查、生成结构化需求。 |
| 结构化需求 | 来源需求 ID、元素类型、名称、描述、输入、输出、约束 | 转业务建模语言草稿、生成追问清单、发现遗漏。 |
| 业务建模语言模型 | 模型 ID、版本、依赖、来源需求、关联规则、关联测试 | 语法检查、模型补全、模板推荐、影响分析。 |
| 统一 IR | IR 版本、节点、引用、类型、规则、来源映射 | 语义校验、生成代码、生成测试、差异比较。 |
| Backend 生成报告 | IR 版本、模板版本、生成文件、差异、告警、人工扩展点 | 解释生成结果、定位差异、生成评审摘要。 |
| 测试资产 | 测试 ID、需求 ID、规则 ID、输入数据、预期结果、执行结果 | 补齐用例、建议回归范围、归因失败原因。 |
| 运营反馈 | 反馈 ID、版本、问题类型、日志、指标、影响范围、复现条件 | 告警摘要、缺陷归因、关联需求和模型。 |
| 仓库资产 | 资产 ID、类型、适用场景、输入输出、依赖、示例、测试 | 检索、推荐、适配、生成相似资产。 |

通用要求：

- 每个产出物有唯一 ID、版本、责任人和来源。
- 自然语言说明可以保留，但必须配套结构化字段。
- 重要结论必须追踪到需求、模型、IR、代码、测试或运行证据。
- AI 输出必须标记“已确认”“待确认”“无法判断”三类状态。
- 可复用经验进入业务建模语言仓库，作为下一轮 AI 上下文。

## 10. AI Agent 执行边界

| AI 可执行动作 | 输入 | 输出 | 人工确认角色 |
|---------------|------|------|--------------|
| 需求摘要与追问 | 客户诉求、运营反馈、历史需求 | 摘要、追问清单、风险点 | 产品经理 |
| 需求结构化 | 需求规格、领域术语、历史模型 | 对象、流程、规则、接口、测试语义草稿 | 产品经理、业务架构师 |
| 模型草稿生成 | 结构化需求、模板、业务建模语言规范 | 业务建模语言草稿、待确认项 | 建模工程师 |
| 语义校验解释 | IR、校验报告、历史模型 | 错误解释、修复建议、影响摘要 | 建模工程师、架构治理人员 |
| 代码生成解释 | 生成报告、目标代码、模板 | 代码摘要、差异解释、人工扩展建议 | 开发工程师 |
| 测试补全 | 验收标准、IR、影响分析 | 测试用例草稿、回归范围建议 | 测试工程师 |
| 缺陷归因 | 日志、告警、测试失败、代码差异 | 可能原因、证据链、修复方向 | 开发工程师、运维人员 |
| 资产沉淀 | 修复记录、测试补充、复用经验 | 候选模板、规则、知识条目 | 架构治理人员 |

AI 不直接完成以下决策：

- 不直接确认需求范围和优先级。
- 不直接确认业务规则最终正确性。
- 不直接合并生成代码或发布生产环境。
- 不直接关闭缺陷和运营反馈。
- 不直接发布业务建模语言规范、生成模板和仓库资产。

## 11. 关键治理要求

| 治理项 | 要求 |
|--------|------|
| 人工审核 | AI 生成的需求、模型、代码、测试和分析报告必须由对应责任角色确认。 |
| 可追踪 | 需求、模型、IR、生成代码、测试用例、缺陷和发布记录之间应建立追踪关系。 |
| 可重复 | 同一版本 IR、模板和目标参数应生成一致工程产物。 |
| 可回滚 | 发布产物、配置和模型版本需要支持回滚。 |
| 可沉淀 | 复用规则、模板、测试、缺陷模式和经验应进入业务建模语言仓库。 |
| 可度量 | 需求周期、建模周期、出码比例、测试覆盖、缺陷率和运营反馈处理时长应持续度量。 |

## 12. 总结

这套流程的主线是：

- 产品经理把业务诉求沉淀为需求规格。
- 业务架构师和建模工程师把需求规格转换为业务建模语言。
- Middle 将模型治理为统一 IR。
- Backend 基于 IR 生成代码、配置、测试和工程产物。
- 测试、上线和运营反馈持续回流。
- 新需求和缺陷修复通过影响分析进入下一轮迭代。

最终目标是形成“需求可建模、模型可校验、IR 可生成、代码可追踪、反馈可回流、资产可复用”的研发闭环。
