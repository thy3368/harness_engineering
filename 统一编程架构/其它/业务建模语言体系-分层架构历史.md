# AI 驱动一体化研发流程分层架构说明

## 1. 文档目标

本文档参考 [task3.md](./task3.md)，按经典编译器三分法对 **业务建模语言体系** 进行分层描述，重点说明每一层的：

- 逻辑架构。
- 目标实现架构。
- 当前实现架构。
- 当前差距与建设重点。

分层口径如下：

| 层次 | 定位 | 核心问题 |
|------|------|----------|
| Frontend | 输入侧规格定义与模型解析 | 业务逻辑如何进入统一 IR |
| Middle | 统一业务建模语言 IR 与语义治理 | 业务语义如何被稳定表达、校验、测试和复用 |
| Backend | 目标语言与工程产物生成 | 统一 IR 如何生成 Java / C++ / SQL 等目标产物 |

## 2. 总体分层架构

```text
业务需求 / 可视化模型 / 元数据 DSL / 业务建模语言文本
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Frontend：输入侧规格定义与模型解析              │
│ - 业务建模语言规格定义                         │
│ - HSDDML / HFlow JSON / 大数据 YML / XML       │
│ - 可视化模型解析 / 文本解析 / 需求结构化         │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Middle：统一业务建模语言 IR 与语义治理          │
│ - 统一业务建模语言 IR                          │
│ - AST / 语义模型 / 元数据规范                  │
│ - 类型系统 / 语义校验 / 影响分析 / 测试语义      │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Backend：目标语言与工程产物生成                 │
│ - Java Generator / C++ Generator / SQL Generator│
│ - 配置生成 / 测试代码生成 / 工程适配             │
│ - JRES / CRES 等目标运行或生成体系              │
└──────────────────────────────────────────────┘
                    │
                    ▼
Java / C++ / SQL / 配置 / 测试代码 / 工程产物
```

## 3. Frontend：输入侧规格定义与模型解析

### 3.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 定义业务建模语言的输入侧规格，将需求、模型、元数据 DSL、可视化配置和业务建模语言文本解析为标准输入。 |
| 输入契约 | 接收需求文档、业务流程、业务规则、可视化模型、业务建模语言文本、HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等。 |
| 输出契约 | 输出可进入 Middle 层的规范化模型、语法结构、元数据引用和初步语义结构。 |
| 交互契约 | 与开发工具、AI Agent、模型设计工具、文件系统和元数据来源交互。 |
| 质量契约 | 输入结构清晰、格式可解析、模型引用明确、错误可诊断、版本可识别。 |

### 3.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 业务建模语言规格 | 统一定义流程式、声明式、函数式三类业务表达。 |
| 文本解析器 | 解析业务建模语言文本，生成语法树或标准结构。 |
| 元数据 DSL 解析器 | 支持 HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等输入格式。 |
| 可视化模型解析器 | 将流程图、规则配置、模型配置转换为标准模型结构。 |
| AI 需求结构化 | 将自然语言需求转换为可建模输入。 |
| 诊断与格式化 | 提供语法诊断、格式化、错误提示和版本识别能力。 |

### 3.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| HSDDML | 已存在的元数据或数据建模输入格式。 |
| HFlow JSON | 已存在的流程或编排类输入格式。 |
| 大数据 YML | 已存在的大数据处理或配置类输入格式。 |
| 表设计器 XML | 已存在的表结构或数据设计输入格式。 |
| 业务建模语言文本 | 需要进一步统一规格、解析和诊断能力。 |
| 可视化模型 | 需要统一与业务建模语言 IR 的转换关系。 |

### 3.4 差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 多种 DSL 格式并存 | 建立统一 Frontend 输入规范和解析适配层。 |
| 可视化模型与文本模型关系不清 | 明确可视化模型到业务建模语言 IR 的转换规则。 |
| AI 生成输入缺少稳定约束 | 定义 AI 生成业务建模语言的 prompt / spec / skill 规范。 |
| 输入错误诊断能力不足 | 建设统一语法检查、格式化和诊断能力。 |

## 4. Middle：统一业务建模语言 IR 与语义治理

### 4.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 承接 Frontend 输入，形成统一业务建模语言 IR，负责语义治理、依赖关系、类型系统、影响分析、测试语义和资产复用。 |
| 输入契约 | 接收 Frontend 输出的规范化模型、语法结构、元数据引用和初步语义结构。 |
| 输出契约 | 输出稳定、透明、可测试、可翻译、可复用的统一业务建模语言 IR。 |
| 交互契约 | 与 Frontend、Backend、测试工具、影响分析工具、业务建模语言仓库交互。 |
| 质量契约 | IR 语义稳定、向下兼容、可审查、可追踪、可测试、可生成。 |

### 4.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 统一业务建模语言 IR | 作为业务逻辑的核心中间表达。 |
| AST / 语义模型 | 承载结构化语法、语义节点、引用关系和依赖关系。 |
| 元数据规范 | 管理数据模型、接口模型、流程模型、规则模型和测试模型。 |
| 类型系统 | 管理字段类型、对象类型、表达式类型、服务接口类型。 |
| 语义校验 | 校验引用合法性、规则一致性、流程完整性和兼容性。 |
| 影响分析 | 分析需求、模型、IR、生成代码、测试资产之间的影响关系。 |
| 测试语义模型 | 支撑 IR 测试、测试用例生成和测试报告生成。 |
| 资产复用接口 | 支撑组件、模板、规则和知识复用。 |

### 4.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 分散元数据规范 | 各类 DSL 和工具中已有部分元数据表达，但尚未统一。 |
| 局部语义模型 | 不同工具内可能已有局部模型或规则表达。 |
| 局部校验能力 | 部分工具具备格式校验、模型校验或代码生成前校验。 |
| 组件化资产雏形 | 存在可复用业务逻辑或模板，但缺少统一业务建模语言仓库治理。 |

### 4.4 差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 缺少统一 IR 定义 | 定义统一业务建模语言 IR、AST 和语义模型。 |
| 元数据规范分散 | 建立统一元数据规范和引用关系。 |
| 语义校验不统一 | 建设统一语义校验、类型系统和兼容规则。 |
| 测试语义不足 | 建立 IR 测试语义模型和测试生成规范。 |
| 资产复用缺少治理 | 建设业务建模语言仓库与组件复用规范。 |

## 5. Backend：目标语言与工程产物生成

### 5.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 将统一业务建模语言 IR 翻译为 Java / C++ / SQL 等目标语言代码，以及配置、测试代码和工程产物。 |
| 输入契约 | 接收统一业务建模语言 IR、元数据规范、翻译规则、目标语言参数和工程模板。 |
| 输出契约 | 输出 Java / C++ / SQL、配置文件、测试代码、工程结构和生成报告。 |
| 交互契约 | 与 Middle、开发工具、代码仓库、构建流水线、JRES / CRES 等目标体系交互。 |
| 质量契约 | 生成结果可追踪、可重复、可构建、可测试，目标代码能追踪到 IR 和模型来源。 |

### 5.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| Java Generator | 将 IR 生成 Java 服务代码、接口适配代码和测试代码。 |
| C++ Generator | 将 IR 生成 C++ 业务代码、核心交易逻辑或低延迟代码。 |
| SQL Generator | 将 IR 生成 SQL 查询、脚本或数据处理逻辑。 |
| 配置生成器 | 生成接口、规则、部署、运行参数等配置。 |
| 测试代码生成器 | 生成单元测试、集成测试、回归测试代码。 |
| 工程模板适配 | 适配不同目标工程结构和构建方式。 |
| 原生代码解析 | 支持 Java / C++ 存量代码解析、理解和迁移辅助。 |
| 生成报告 | 输出生成结果、差异、依赖和可追踪关系。 |

### 5.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 代码生成器 | 已有或计划中的目标代码生成能力。 |
| JRES | Java 方向运行、生成或工程承载体系。 |
| CRES | C / C++ 方向运行、生成或工程承载体系。 |
| 局部原生代码解析 | Java / C++ 存量代码解析能力需要进一步整合。 |
| 局部工程模板 | 不同目标语言或产品线可能已有独立工程模板。 |

### 5.4 差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 多语言生成规则不统一 | 建立统一 Backend 翻译规则和生成模板。 |
| 生成结果可追踪不足 | 建设 IR 到目标代码的映射和生成报告。 |
| Java / C++ 生成体系分散 | 统一 JRES / CRES 与业务建模语言 IR 的对接方式。 |
| 存量代码迁移困难 | 建设原生代码解析和迁移辅助能力。 |
| 测试代码生成不足 | 建设基于 IR 测试语义的测试代码生成器。 |

## 6. 分层映射关系

| 分层 | 逻辑架构核心 | 目标实现架构 | 当前实现架构 |
|------|--------------|--------------|--------------|
| Frontend | 输入侧规格定义与模型解析 | 业务建模语言规格、文本解析、DSL 解析、可视化模型解析、AI 需求结构化 | HSDDML、HFlow JSON、大数据 YML、表设计器 XML、局部可视化模型 |
| Middle | 统一业务建模语言 IR 与语义治理 | IR、AST / 语义模型、元数据规范、类型系统、语义校验、影响分析、测试语义 | 分散元数据规范、局部语义模型、局部校验能力 |
| Backend | 目标语言与工程产物生成 | Java / C++ / SQL Generator、配置生成器、测试代码生成器、原生代码解析 | 代码生成器、JRES、CRES、局部工程模板 |

## 7. AI 更友好、更原生的业务建模语言设计注意点

### 7.1 总体原则

AI 更友好的业务建模语言，不应只是“让 AI 更容易写代码”，而应让 AI 更容易 **理解业务语义、生成稳定结构、接受工具校验、解释变更原因、修复错误并沉淀资产**。

| 原则 | 说明 |
|------|------|
| 结构优先 | 语言表达应尽量结构化，减少大段自由文本。 |
| 语义显式 | 业务对象、字段、规则、流程、接口、状态、异常路径需要显式表达。 |
| 上下文可定位 | 每段语言结构应能定位到需求、模型、规则、测试或生成产物。 |
| 可校验 | AI 生成结果必须能被语法校验、语义校验、引用校验和测试校验。 |
| 可解释 | 语言结构应支持 AI 解释“为什么这样生成、引用了什么、影响了什么”。 |
| 可修复 | 错误诊断应能反馈给 AI，驱动定向修复，而不是重新生成整段内容。 |
| 可复用 | 语言组件应具备参数化、模板化和测试绑定能力。 |

### 7.2 Frontend 设计注意点

| 设计点 | 说明 |
|--------|------|
| 输入格式清晰 | 业务建模语言文本、可视化模型、元数据 DSL 应有明确边界和结构。 |
| 少歧义语法 | 避免同一业务含义存在多种等价写法，减少 AI 生成不稳定。 |
| 显式字段引用 | 字段、对象、服务、规则应使用可解析引用，而不是纯自然语言描述。 |
| 支持局部生成 | 支持 AI 只生成某个流程、规则、函数或模型片段。 |
| 支持错误定位 | 语法错误、引用错误、缺失字段应能定位到具体节点。 |
| Prompt 友好 | 语言规格应能整理成 AI 可使用的 spec / skill / 示例集。 |

### 7.3 Middle 设计注意点

| 设计点 | 说明 |
|--------|------|
| IR 结构稳定 | 统一业务建模语言 IR 应稳定，避免频繁破坏性变化。 |
| 语义节点明确 | 流程、规则、数据访问、服务调用、异常处理、测试断言应有明确节点类型。 |
| 元数据引用统一 | IR 中的对象、字段、接口、规则引用应统一指向元数据规范。 |
| 类型系统可解释 | 类型、枚举、集合、对象、表达式应能被 AI 和工具共同理解。 |
| 影响分析可计算 | IR 应保留依赖关系，支持变更影响分析。 |
| 测试语义内置 | 语言结构应能直接关联测试场景、输入数据、预期结果和断言。 |
| 版本兼容明确 | AI 生成和修复时需要知道当前 IR 版本和兼容约束。 |

### 7.4 Backend 设计注意点

| 设计点 | 说明 |
|--------|------|
| 生成规则确定 | 目标代码生成应由规则化 Backend 承担，避免完全依赖 LLM 直接出码。 |
| 目标语言差异显式 | Java / C++ / SQL 的差异应通过生成规则、模板和目标语言参数表达。 |
| 代码可追踪 | 生成代码应能追踪到对应 IR 节点、模型对象和业务规则。 |
| 支持差异生成 | 支持根据 IR 变更生成目标代码差异，而不是全量覆盖。 |
| 生成报告标准化 | 输出生成结果、失败原因、依赖关系和可追踪映射。 |
| AI 修复有边界 | AI 修复建议应优先回到 IR 或生成规则层，而不是直接修改目标代码。 |

### 7.5 AI 协作契约

| 契约 | 说明 |
|------|------|
| 上下文契约 | AI 输入应包含需求、模型、IR 片段、元数据、错误诊断、测试报告和资产示例。 |
| 生成契约 | AI 输出应优先生成业务建模语言结构，而不是直接生成目标语言代码。 |
| 校验契约 | AI 输出必须经过语法、语义、引用、兼容和测试校验。 |
| 解释契约 | AI 应能说明生成依据、引用对象、变更点和潜在影响。 |
| 修复契约 | AI 根据诊断结果进行局部修复，保留变更说明。 |
| 资产契约 | AI 生成或修复后的稳定片段可沉淀为组件、模板、规则或测试资产。 |

### 7.6 建设重点

| 建设重点 | 说明 |
|----------|------|
| 业务建模语言 spec | 将语言语法、语义、示例、禁用写法整理成 AI 可消费规范。 |
| 标准示例库 | 提供流程式、声明式、函数式、服务编排、规则表达的高质量示例。 |
| 错误诊断协议 | 将工具诊断结果结构化，便于 AI 定向修复。 |
| 上下文组装规范 | 定义 AI 生成时应携带哪些需求、模型、IR、资产和测试上下文。 |
| 组件化表达 | 支持 AI 生成和复用小粒度、可测试、可组合的语言组件。 |
| 人工审查点 | 明确哪些 AI 生成结果需要业务架构师、开发人员或测试人员确认。 |

## 8. 建设顺序建议

| 阶段 | 建设重点 |
|------|----------|
| 第一阶段 | 明确 Frontend 输入规范，统一业务建模语言规格定义。 |
| 第二阶段 | 定义 Middle 统一业务建模语言 IR、AST、元数据规范和语义校验。 |
| 第三阶段 | 建设 Backend Java / C++ / SQL 生成能力，并对接 JRES / CRES。 |
| 第四阶段 | 建设 IR 测试、影响分析和资产仓库。 |
| 第五阶段 | 引入 AI Agent、MCP、自动修复和运维反馈闭环。 |

## 9. 总结

按 Frontend / Middle / Backend 分层后，业务建模语言体系的边界更加清晰：

- Frontend 负责“业务逻辑如何进入统一 IR”。
- Middle 负责“业务语义如何被稳定表达和治理”。
- Backend 负责“统一 IR 如何生成目标语言和工程产物”。

目标架构应重点围绕 **统一业务建模语言 IR** 建设，当前实现则需要逐步把 HSDDML、HFlow JSON、大数据 YML、表设计器 XML、JRES、CRES、代码生成器等能力纳入统一分层体系。
