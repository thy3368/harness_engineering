## 一、项目概述

### 1.1 项目名称

一体化开发工具（Unified Development Platform，UDP）

### 1.2 项目定位

公司级战略基础设施，构建基于 **VSCode 自封装 IDE** 的一体化开发工具平台；以**伪代码**为业务逻辑的统一中间表达，以 **LightCode AI 能力**驱动自然语言到伪代码的智能化生成，将现有分散的开发工具体系渐进收编为统一平台，实现"一套工具、一种伪代码、AI 驱动开发全流程"。

### 1.3 项目周期

**2026 年 5 月 — 2028 年 12 月（约 2.5 年）**，分三阶段推进。

### 1.4 核心策略

**伪代码优先、IDE 自封装、UF30 起步、LightCode 赋能、渐进收编**

### 1.5 一句话描述

以伪代码体系为主轴、VSCode 自封装 IDE 为载体、LightCode AI 能力为驱动，从收编 UF30 伪代码工具开始，用 2~3 年时间将公司分散的开发工具演进为"AI 驱动、伪代码表达、一体化管理"的统一开发平台。

### 1.6 核心交付目标

| 维度 | 目标 |
|------|------|
| **一个 IDE** | 基于 VSCode 自封装的公司专属 IDE（替代多种开发工具并存局面） |
| **一种伪代码** | 统一伪代码体系作为业务逻辑的中间表达（IR），覆盖三范式，支持 Java/C++/SQL 多目标输出 |
| **一套元数据** | 五层资源模型（L0-L4），稳态/敏态分离管理 |
| **一个前端标准** | 布局—逻辑—数据对接三层分离 |
| **AI 驱动开发** | 以 LightCode 为底座，开发自然语言→伪代码的 spec/skill 配套，让 AI 以伪代码为目标输出，实现"描述需求→生成伪代码→编译执行"的全链路 AI 驱动 |

### 1.7 关键里程碑预览

| 时间 | 里程碑 |
|------|--------|
| 2026-05 | **M0：UF30 伪代码开发工具收编首个版本发布 + 伪代码语法标准化草案 + 元数据规范修订启动**；LightCode 伪代码 skill 设计启动 |
| 2026-07 | **M1：伪代码语法规范 v1.0 + 元数据规范 v1.0 同步正式发布**；**LightCode 自然语言→伪代码 skill beta版上线**；VSCode 元数据插件基础可用 |
| 2026-08 | M2：VSCode 插件元数据管理完整版 + LightCode skill 正式上线 + 试点推广 |
| 2026-12 | M3：VSCode 自封装 IDE 首个正式版 + 伪代码编译器 MVP |
| 2027-06 | M4：伪代码三范式 + 首批 2 个工具收编完成 |
| 2027-12 | M5：前端三层分离 MVP + 稳态/敏态元数据落地 |
| 2028-12 | M6：全面一体化，Eclipse 退役，AI Agent MVP |

## 二、背景依据与战略价值

### 2.1 背景依据

#### 2.1.1 公司要求

**"开发工具体系需要有整体规划，最终演进成一体化工具。"** 本方案是对该要求的具体响应和落地路径。

#### 2.1.2 业务驱动

| 驱动因素 | 具体表现 |
|----------|----------|
| **工具碎片化导致效率损失** | 开发者跨部门使用时面临重复学习成本，功能重叠造成维护资源浪费 |
| **伪代码体系亟待统一** | Ares Studio 与 UF30 均采用伪代码体系，语法相似但独立维护，亟需合并统一 |
| **AI 战略需要统一底座** | 未来 AI 辅助开发需要统一的伪代码体系和元数据规范，分散工具无法支撑 |

#### 2.1.3 技术驱动

| 驱动因素 | 说明 |
|----------|------|
| AI 编码工具成熟 | 大语言模型能力快速提升，金融 IT 领域 AI 辅助开发进入可落地阶段 |
| UF30和Ares伪代码基础良好 | UF30和Ares已有成熟的伪代码语法和插件实现，是最优起点 |
| VSCode 开源生态成熟 | VSCode 基于 MIT 协议开源，可自封装为公司专属 IDE，大幅降低 IDE 碎片化风险 |
| Eclipse 生态衰落 | Eclipse 4.6 已严重落后，主流产品正迁移至 VSCode / IDEA |

### 2.2 战略价值分析

#### 2.2.1 量化价值

| 价值维度 | 当前状态 | 目标状态 | 预期收益 |
|----------|----------|----------|----------|
| **AI 赋能** | AI 能力需逐个工具单独集成，且无伪代码标准约束导致输出质量不稳定 | 以伪代码为 AI 输出目标，复用 LightCode 插件开发 spec/skill，AI 生成可控、可审查、可编译 | 2026年即可落地，无需等待独立 AI 平台建设 |
| **伪代码价值** | Ares Studio 与 UF30 两套语法分别维护 | 统一伪代码体系 | 消除重复维护，知识沉淀可复用 |
| **开发效率** | 开发者平均需掌握 2~3 种 IDE | 统一 IDE 一站式开发 | 学习成本降低 50%+，跨工具切换时间消除 |
| **维护成本** | 元数据管理、调试等共性功能在 5+ 工具中重复实现 | 共性能力沉淀到基座 | 减少 30~40% 重复开发投入 |

#### 2.2.2 对公司战略的支撑

```
公司统一平台战略
  └─ UDP 一体化开发工具
       ├─ 支撑 AI 辅助开发战略
       ├─ 支撑低代码/零代码平台演进
       ├─ 支撑 MDD（模型驱动开发）体系落地
       └─ 支撑金融 IT 三基线合规要求
```

## 三、现状分析与问题量化

### 3.1 工具全景盘点

基于全面盘点，当前公司开发工具覆盖 **7 个产品组、16+ 插件、5 大 IDE 平台**：

| 产品组 | 主要插件 | IDE 平台 | 核心功能 | 状态 |
|--------|----------|----------|----------|------|
| ARES Studio | ARES4CRES / ARES4UFT / ARES4Start / ARES4HEP / ARES4Debug | Eclipse 4.6 | 业务开发、元数据管理、HEP 对接、调试、**伪代码体系** | 在用，功能成熟 |
| 恒生开发工具 | HDT | Eclipse 4.6 | 元数据管理、数据库管理、业务代码开发 | 在用 |
| LDP 开发工具 | ARES4UFT / ARES4Start | Eclipse 4.6 | UFT 对象设计、业务代码开发 | 在用 |
| LDP Studio | — | Eclipse Theia 1.38 | 元数据接口管理、静态扫描、代码评审 | 在用，较新 |
| 低代码平台 | 低码 1.0 / 低码新架构 / HEP / GAPS5 / GXP5.0 | Web / VSCode / IDEA / Eclipse | 页面构建、流程设计、服务编排、协议适配 | 活跃迭代 |
| 数智应用 | LightCode | IDEA / VSCode | 大模型辅助代码生成、测试、纠错 | 活跃迭代 |
| 经纪架构部 | **UF30 伪代码开发工具** | **IDEA 2021.3** | **伪代码开发（含 HEP 功能）** | **在用，试点中，新一代估值选型倾向** |

### 3.2 伪代码体系现状

Ares Studio 与 UF30 均采用伪代码体系，两者关系如下：

| 维度 | Ares Studio 伪代码 | UF30 伪代码工具 |
|------|-------------------|----------------|
| 语法风格 | 相似 | 相似 |
| 覆盖范围 | 偏流程式、声明式 | 偏流程式、声明式，HEP 功能较完整 |
| IDE 平台 | Eclipse 4.6 | IDEA 2021.3 |
| 选型倾向 | — | **新一代估值当前选型倾向** |

> **结论**：UF30 伪代码工具是当前最具竞争力的起点，应收编并统一发展。

### 3.3 五大核心问题

#### 问题一：五大 IDE 平台并存，体验碎片化

| IDE | 版本 | 承载插件数 | 维护状态 |
|-----|------|-----------|----------|
| Eclipse | 4.6 | 8+ | 停滞，仅维护 |
| Eclipse Theia | 1.38 | 1 | 维护中 |
| VSCode | — | 4+ | 活跃 |
| IDEA | 2021.3 / 最新 | 3+ | 活跃 |
| Web | — | 3+ | 活跃 |

**影响**：开发者跨部门协作时需反复切换 IDE，重复学习成本高，体验割裂。

#### 问题二：伪代码体系重复维护，两套语法分立

Ares Studio 与 UF30 伪代码语法高度相似，却由两个团队分别维护，造成：
- 知识无法共享，维护成本重复
- 两套编译器/解析器分别演进，无法互通
- 无法形成公司级统一中间表达

> **根本原因**：Ares Studio 承载于 C/C++ 平台（编译目标为 C/C++），UF30 承载于 Java 平台（编译目标为 Java），底层平台差异导致两套伪代码体系长期分立。

#### 问题三：元数据格式不统一，DSL 生态碎片化

| DSL 格式 | 使用方 | 互通成本 |
|----------|--------|----------|
| hsddml | 低代码平台 | — |
| HFlow JSON/XML | 公共平台 | 高 |
| 大数据 YML | 大数据处理平台 | 高 |
| 表设计器 XML | 高性能低延时 | 高 |
| UF30 伪代码 DSL | 经纪架构部 | 中 |

**影响**：元数据互通需逐对开发转换器，复杂度 O(n²)。AI 难以跨系统共享知识。

#### 问题四：功能大量重叠，维护成本持续增长

| 功能维度 | 涉及工具数 | 重复度 |
|----------|-----------|--------|
| 元数据管理 | 5 | 高 |
| 数据库/接口设计 | 4 | 高 |
| 业务代码开发 | 4 | 高 |
| 调试能力 | 2（实现不同） | 中 |

#### 问题五：难以支撑 AI 化演进

| 未来需求 | 当前障碍 |
|----------|----------|
| AI 代码生成 | 元数据规范碎片化，伪代码不统一，缺乏统一训练数据 |
| AI 跨工具智能协作 | 无统一操作规范和事件模型 |
| AI 变更影响分析 | 元数据依赖关系分散在各工具中，无法全局分析 |

### 3.4 改进紧迫性评估

| 维度 | 紧迫性 | 理由 |
|------|--------|------|
| 伪代码统一 | 高 | 两套伪代码并行维护，越晚统一成本越高 |
| AI 赋能需求 | 高 | 统一伪代码体系是 AI 辅助开发的前提 |
| Eclipse 退役 | 中 | Eclipse 4.6 已停止维护，安全风险和技术债持续增加 |

## 四、总体技术方案

### 4.1 指导原则

| 原则 | 说明 | 权衡取舍 |
|------|------|----------|
| **伪代码优先** | 以伪代码体系为主轴，其他能力（元数据、AI、前端）围绕伪代码演进 | 前期聚焦，暂缓部分功能，但核心价值更快体现 |
| **UF30 起步** | 以收编 UF30 为起点，快速拿出可用版本，在实战中演进 | 不追求架构完美，优先交付可用产品 |
| **AI 自然语言 → 伪代码** | 复用 LightCode 现有 AI 插件能力，核心工作是开发自然语言到伪代码的 spec/skill 配套，使 AI 能以伪代码为目标输出 | LightCode 插件本身现成，节省集成成本；难点在伪代码语义理解和 spec/skill 设计质量 |
| **AI 内建** | AI 能力作为平台原生能力，而非事后附加 | 增加初期复杂度，但避免后期改造的高昂成本 |
| **CLI 核心** | 工具核心逻辑实现为 CLI（Headless），IDE 仅为 UI 层 | CLI 开发成本略高，但 CI/CD 友好、可脱离 IDE 运行 |
| **渐进收编** | 不推倒重来，现有工具按优先级逐步纳入统一平台 | 牺牲部分架构纯粹性，换取平滑过渡和业务连续性 |
| **稳态/敏态分离** | 基础元数据区分稳定结构和易变配置 | 增加元数据管理复杂度，但大幅降低变更影响半径 |

### 4.2 五层资源架构模型

开发期资源按职责和变更频率分为五个层级：

```
┌─────────────────────────────────────────────────────────┐
│                    L4 前端资源层                          │
│         布局（可视化）│ 逻辑（伪代码）│ 数据对接（声明式）     │
├─────────────────────────────────────────────────────────┤
│                    L3 业务逻辑层                          │
│    声明式（数据操作）│ 流程式（业务流程）│ 函数式（数据转化）     │
│              统一伪代码中间表达 → 目标代码                  │
├─────────────────────────────────────────────────────────┤
│                    L2 业务模型层                          │
│       服务接口 │ 业务对象 │ 业务规则 │ 枚举 │ 状态机         │
├─────────────────────────────────────────────────────────┤
│                    L1 基础元数据层                        │
│     稳态：表结构、数据字典、报文结构、协议                  │
│     敏态：字段扩展、校验规则、映射配置、视图定义             │
├─────────────────────────────────────────────────────────┤
│                    L0 工具底座层                          │
│          CLI 核心（Headless）+ VSCode 自封装 IDE           │
├─────────────────────────────────────────────────────────┤
│                    AI 能力层（横切）                       │
│   LightCode 自然语言→伪代码 │ AI 补全/解读 │ 变更影响分析    │
│          伪代码是 AI 的统一输出目标和输入上下文              │
└─────────────────────────────────────────────────────────┘
```

## 五、核心主线：伪代码体系方案

> 伪代码体系是本规划的**核心主轴**，其他能力（IDE、元数据、AI、前端）均以伪代码体系为中心展开。

### 5.1 定位

伪代码不是"简化的编程语言"，而是**业务逻辑的统一中间表达（Intermediate Representation，IR）**：

```
┌────────────────┐        ┌──────────────┐        ┌──────────────────┐
│  AI 自然语言    │  ────→ │  伪代码 IR    │  ────→ │   目标执行代码    │
│  需求 / 指令    │        │ （统一中间表达）│        │ Java / C++ / SQL │
└────────────────┘        └──────────────┘        └──────────────────┘
                                  ↕
                          ┌──────────────┐
                          │   可视化建模   │
                          │  拖拽/表单配置 │
                          └──────────────┘
```

### 5.2 核心特征

| 特征 | 说明 |
|------|------|
| **承前启后** | 向前与可视化建模结合，向后与 AI 代码生成结合，是整个平台的核心纽带 |
| **人工可读可写** | 业务分析师、架构师可参与编写和审查 |
| **机器可编译** | 可编译为 Java / C++ / SQL 等目标语言 |
| **可视化可双向绑定** | 可视化建模工具 ↔ 伪代码双向同步 |
| **跨范式统一** | 声明式、流程式、函数式的输出都可归一化 |

### 5.3 三范式映射

| 范式 | 适用场景 | 伪代码表达示例 | 目标代码 |
|------|----------|--------------|----------|
| **声明式** | 数据操作、CRUD、查询定义 | `QUERY account WHERE balance > 10000 RETURN name, balance` | Java JDBC / MyBatis / SQL |
| **流程式** | 业务流程、审批流、工作流 | `FLOW tradeApproval: START → validate → approve/reject → END` | Spring Bean / 状态机 |
| **函数式** | 数据转化、映射、计算 | `TRANSFORM input: MAP fieldA→a, FILTER status=active, CALC sum(amount)` | Java Stream / C++ Pipeline |

### 5.4 与现有伪代码体系的关系

#### Ares Studio 伪代码 vs UF30 伪代码

| 维度 | Ares Studio 伪代码 | UF30 伪代码工具 | UDP 伪代码体系 |
|------|-------------------|----------------|---------------|
| 语法基础 | 相似 | 相似 | **以 UF30 为主起点，吸收 Ares Studio 成熟实践** |
| 范式覆盖 | 偏流程式/声明式 | 偏流程式/声明式 | **扩展至三范式全覆盖** |
| IDE 平台 | Eclipse | IDEA | **VSCode 自封装 IDE** |
| 编译目标 | C/C++ | Java | **C/C++ / Java / SQL 多目标** |
| 可视化 | 部分 | 部分 | **全范式双向绑定（中远期）** |

**策略**：以 UF30 为起点收编，同步吸收 Ares Studio 中的成熟语法实践，统一为公司级伪代码体系，逐步扩展至三范式全覆盖。

### 5.5 伪代码体系演进路线

| 里程碑 | 时间 | 内容 |
|------|------|------|
| **P0** | 2026-05 | **验证后发布 UF30 现有版本**（IDEA插件形态，首个可用版本）；联合 Ares Studio + UF30 团队同步完成伪代码语法标准化草案 |
| **P1** | 2026-05~07 | 语法规范评审：草案通过公司评审，发布语法规范 v1.0 正式版；元数据规范 v1.0 同步发布 |
| **P2** | 2026-05~08 | **LightCode 自然语言→伪代码 skill**：复用 LightCode 现有插件，开发 spec/skill 配套，5月调研设计、7月可测试版、8月正式上线 |
| **P3** | 2026-08~12 | 编译器增强：优化编译器，新增 C++/SQL 目标输出；启动 VSCode 插件移植 |
| **P4** | 2026-Q4~2027-H1 | AI 伪代码补全上下文感知深化；可视化↔伪代码双向绑定 MVP |
| **P5** | 2027-H1 | 三范式完整支持：函数式范式；可视化↔伪代码双向绑定完善 |
| **P6** | 2027-H2~2028 | 多目标代码优化；跨项目逻辑复用；AI Agent MVP |

## 六、IDE 形态方案（VSCode 自封装）

### 6.1 为什么选择 VSCode 自封装

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **VSCode 自封装（推荐）** | MIT 开源可商用；Extension API 成熟；一套扩展覆盖所有场景；可定制启动页/品牌/插件商店 | 需要维护 fork | **采用** |

## 七、元数据管理方案

> **概念界定**：本章讨论的"元数据"是指 **UDP 平台层面的五层资源模型元数据**（L0-L4），覆盖表结构、报文结构、伪代码关联关系、前端布局等开发工程元数据。

### 7.1 统一元数据描述规范

**目标**：统一所有开发工具的元数据描述格式，消除 DSL 碎片化（hsddml / HFlow JSON / 大数据 YML / 表设计器 XML 等），建立统一的五层资源模型元数据规范。

**基础**：元数据规范基于 HEP 现有元数据规范修订扩展，继承 HEP 已有的标准化描述和版本管理能力，而非从零设计。

| 规范项 | 说明 |
|--------|------|
| 资源通用属性 | id、type、version、dependencies |
| 结构描述 | 表结构、字段定义、关系映射、约束规则 |
| 伪代码关联 | 伪代码与元数据的引用关系描述 |
| AI 友好格式 | 结构化、带语义标注的元数据描述，便于 AI 理解和补全引用（从 v1.0 即纳入） |
| 领域扩展点 | 各工具可定义自有扩展字段 |

**演进节奏**：

| 版本 | 时间 | 内容 |
|------|------|------|
| 元数据规范 v1.0 | 2026-07（**5月同步伪代码规范启动设计**） | 统一基础属性规范、伪代码关联关系、**AI 友好格式（语义标注、结构化引用描述）**；基于 HEP 现有规范修订；**与伪代码语法规范 v1.0 同步发布** |
| 元数据规范 v2.0 | 2027-H2 | 跨层依赖图谱、元数据变更追溯 |
| 元数据规范 v3.0 | 2028 | 稳态/敏态分离管理、变更审批流程、依赖追踪与影响分析 |

> **设计原则**：AI 友好格式从 v1.0 即纳入——元数据规范在设计之初就应考虑 AI 可理解性（语义标注、结构化引用关系），避免后期改造。稳态/敏态分离、变更审批、依赖追踪等高级能力则在元数据模型成熟后再实现。

### 7.2 与 HEP 平台的关系

| HEP 已有能力 | UDP 吸收与扩展 |
|--------------|---------------|
| 元数据标准化描述和版本管理 | 纳入统一元数据规范体系（作为 v1.0 修订基础） |
| 元数据驱动的代码生成 | 扩展为五层资源模型驱动的全链路生成 |
| 元数据变更可追溯性 | 扩展为变更影响分析 + AI 辅助 |
| HEP 特有功能 | 保留为兼容插件，逐步迁移 |

### 7.3 稳态/敏态分离与变更影响分析（2027+ 能力）

> **说明**：稳态/敏态分离管理和变更影响分析属于元数据管理的高级能力，在元数据规范 v1.0 建立基础后再逐步实现。

#### 7.3.1 稳态/敏态分离

| 维度 | 稳态（Structure） | 敏态（Configuration） |
|------|-------------------|----------------------|
| 定义 | 数据基础结构的描述 | 基于结构的扩展配置 |
| 变更频率 | 低（季度/年度规划） | 高（迭代频繁） |
| 典型内容 | 表名、字段名/类型/长度、主外键、报文结构、协议 | 校验规则、默认值、显示标签、映射规则、字段扩展 |
| 变更影响 | 影响面大，可能波及代码生成和下游系统 | 影响面小，通常仅影响展示和校验 |
| 管控级别 | 严格审批、版本化管理、变更影响分析 | 灵活配置、支持热更新 |

#### 7.3.2 变更影响分析

当稳态元数据发生变更时，系统自动执行影响分析：

```
表字段变更 → 分析引用该字段的业务对象（L2）
           → 分析使用该字段的服务接口（L2）
           → 分析依赖该接口的伪代码（L3）和前端（L4）
           → 生成影响范围报告和变更建议
```

> **实现节奏**：v1.0 重点关注统一描述格式和 AI 友好性；v3.0（2028）实现完整的稳态/敏态分离管理 + 变更审批流程 + 依赖追踪与影响分析。

### 9.2 关键约束

| 约束 | 说明 | 应对措施 |
|------|------|----------|
| **金融合规** | 代码/设计数据不得上传至外部模型 | AI 推理在私有化环境执行，数据不离开内网 |
| **可解释性** | AI 生成的伪代码必须可审查 | 伪代码本身人工可读，附带推理说明和置信度评分 |
| **渐进引入** | AI 能力需逐步验证 | 每个场景独立评估效果，灰度上线 |

### 9.3 与 LightCode 的关系

| 维度 | 策略 |
|------|------|
| **自然语言→伪代码** | **核心集成点**：复用 LightCode 现有 AI 插件能力，开发自然语言到伪代码的 spec 和 skill 配套（LightCode 插件本身现成，工作量在伪代码语义 spec 设计和 skill 调优）；2026年 Q2 起推进，8月正式上线 |
| 代码补全 | 保留 LightCode 代码级补全能力；伪代码语义补全由 UDP 自建（LightCode 不具备此能力） |
| 代码生成 | 升级为平台级能力，结合元数据和伪代码上下文生成更精准的代码；伪代码作为中间层使 AI 输出更可控 |

## 附录

### 附录 A：架构决策记录（ADR）

#### AD-001：VSCode 自封装 IDE

- **状态**：已接受
- **上下文**：原方案需要适配 VSCode / IDEA / Web / Theia / Eclipse 五种 IDE，每种独立适配成本高，长期维护碎片化严重
- **决策**：基于 VSCode 开源项目（MIT 协议）进行自封装，构建公司专属 IDE，内置 UDP 核心插件包，所有插件基于统一的 VSCode Extension API 开发
- **后果**
  - ✅ 消除多 IDE 适配碎片化，一套 Extension API 覆盖所有场景
  - ✅ 品牌定制，用户认知统一
  - ✅ 封装成本约 3.5 人月，显著低于多 IDE 适配方案
  - ⚠️ 需要维护 VSCode Fork，定期跟随上游更新
  - ⚠️ IDEA 用户需要迁移（通过过渡期策略缓解）

#### AD-002：UF30 收编为起点

- **状态**：已接受
- **上下文**：选型窗口开放，UF30 伪代码工具是当前选型倾向，Ares Studio 也有相似伪代码体系，两者语法接近但分立维护
- **决策**：以收编 UF30 为起点，5月发布首个版本，不另起炉灶，在 UF30 基础上统一发展
- **后果**
  - ✅ 5月即可发布可用版本，快速响应选型需求
  - ✅ 继承 UF30 已有用户群和使用习惯
  - ✅ 避免从零开始的长期投入
  - ⚠️ 需要处理 UF30 遗留技术债
  - ⚠️ 需要协调 Ares Studio 团队统一语法标准

#### AD-003：伪代码体系作为平台核心主轴

- **状态**：已接受
- **上下文**：Ares Studio 与 UF30 两套伪代码体系并存，语法相似但因承载平台不同（Ares Studio 为 C/C++ 平台，UF30 为 Java 平台）而长期分立，且伪代码是连接可视化建模与目标代码、连接 AI 与人工编写之间的关键桥梁
- **决策**：将统一伪代码体系确定为整个 UDP 平台的核心主轴，其他能力（IDE、元数据、AI、前端三层）均以伪代码为中心展开
- **后果**
  - ✅ 方向聚焦，2026年主要精力集中在核心价值上
  - ✅ AI 能力以伪代码为中间层，控制性和可解释性更强
  - ✅ 消除 Ares Studio 与 UF30 重复维护成本
  - ⚠️ 其他能力（前端三层分离、全量工具收编）相对延后
