# AI 驱动一体化研发流程业务建模语言仓库分层架构说明

## 1. 文档目标

本文档用于描述 **业务建模语言仓库** 在 AI 驱动一体化研发流程中的分层架构。

业务建模语言仓库是业务建模语言体系的资产治理与复用中心，负责管理业务建模语言组件、模型模板、规则模板、测试模板、翻译模板、AI 生成规范和领域知识，并支撑开发工具、AI Agent、Frontend / Middle / Backend 的资产复用。

本文按以下结构描述每一层：

- 逻辑架构。
- 目标实现架构。
- 当前实现架构。
- 当前差距与建设重点。

## 2. 总体分层架构

```text
│ 资产回流层                                    │
│ - 项目资产回流 / 测试资产回流 / 缺陷模式回流    │
│ - 运维反馈回流 / 人工审核 / 资产发布            │
└──────────────────────────────────────────────┘
                    │

│ - 版本 / 兼容性 / 分类 / 标签 / 检索 / 变更记录 │

                    │
                    ▼

└──────────────────────────────────────────────┘
```

## 3. 资产定义层

### 3.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 定义业务建模语言仓库可管理的资产范围、资产类型和标准结构。 |
| 输入契约 | 接收业务建模语言组件、业务流程模板、模型模板、规则模板、测试模板、翻译模板、AI Prompt / Skill / Spec 和领域知识。 |
| 输出契约 | 输出具备统一结构、可版本管理、可检索、可复用的资产定义。 |
| 交互契约 | 与资产管理层、资产复用层、开发工具、AI Agent 和业务建模语言体系交互。 |
| 质量契约 | 资产定义清晰，结构稳定，分类明确，具备复用所需的输入参数、适配规则和测试说明。 |

### 3.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 业务建模语言组件 | 管理可复用业务逻辑、流程片段、规则片段和数据转换逻辑。 |
| 模型模板 | 管理数据模型、接口模型、流程模型、规则模型和测试模型模板。 |
| 规则模板 | 管理校验规则、计算规则、准入规则和业务约束。 |
| 测试模板 | 管理正常路径、异常路径、边界条件、权限失败和外部接口失败等测试模板。 |
| 翻译模板 | 管理 Java / C++ / SQL 等目标语言生成规则和工程模板。 |
| AI 生成规范 | 管理 Prompt、Skill、Spec 和 AI 上下文组织规范。 |
| 领域知识 | 管理业务术语、领域规则、常见缺陷、修复经验和最佳实践。 |

### 3.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 可复用业务逻辑 | 存在分散的可复用业务逻辑，但缺少统一仓库管理。 |
| 模型与规则经验 | 存在数据模型、流程模型、规则配置等经验沉淀，但结构不统一。 |
| 测试经验 | 存在测试用例、缺陷场景和测试经验，但未统一模板化。 |
| 翻译规则经验 | 存在目标语言生成或工程模板经验，但未统一沉淀。 |
| AI 上下文经验 | 存在 AI 使用经验，但 Prompt / Skill / Spec 尚需体系化。 |

### 3.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 资产类型未统一 | 明确组件、模板、规则、测试、翻译、AI 规范和领域知识的资产分类。 |
| 资产结构未统一 | 定义每类资产的标准字段、输入参数、输出结果和适配规则。 |
| 资产复用条件不明确 | 为可复用资产绑定适用场景、依赖模型、测试模板和兼容范围。 |
| AI 可用资产不足 | 将 Prompt、Skill、Spec 和领域知识纳入仓库资产定义。 |

## 4. 资产管理层

### 4.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 管理仓库资产的版本、兼容性、分类、标签、检索、权限、变更记录和发布状态。 |
| 输入契约 | 接收资产定义层输出的组件、模板、规则、测试、翻译、AI 规范和领域知识资产。 |
| 输出契约 | 输出可治理、可检索、可追踪、可发布的资产目录和资产版本。 |
| 交互契约 | 与资产定义层、资产复用层、资产回流层、开发工具和项目仓库交互。 |
| 质量契约 | 资产版本清晰，变更记录完整，兼容性可识别，检索结果稳定，发布状态明确。 |

### 4.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 资产目录 | 按领域、场景、类型、模型、语言和标签组织资产。 |
| 版本管理 | 管理资产版本、兼容范围、历史版本和变更记录。 |
| 兼容性管理 | 管理资产与业务建模语言 IR、元数据规范、目标语言版本的兼容关系。 |
| 分类与标签 | 支持按业务领域、业务场景、技术栈、目标语言、质量等级进行分类。 |
| 检索索引 | 支持关键字、标签、领域、模型、依赖关系和语义检索。 |
| 发布管理 | 支持草稿、待审核、已发布、废弃等资产状态。 |
| 权限与审计 | 支持资产维护权限、使用权限、变更审计和引用审计。 |

### 4.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 分散文件或项目资产 | 资产可能分散在不同项目、工具或文档中。 |
| 局部模板管理 | 部分团队或工具可能已有局部模板，但未统一治理。 |
| 局部知识沉淀 | 领域知识和经验可能以文档、代码片段或人工经验形式存在。 |
| 版本与兼容性管理不足 | 资产版本、兼容范围和变更记录需要统一定义。 |

### 4.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 缺少统一资产目录 | 建设统一资产目录和分类标签体系。 |
| 版本策略不明确 | 定义资产版本、兼容性、变更记录和废弃策略。 |
| 检索能力不足 | 建设关键字、标签、领域、模型和语义检索能力。 |
| 资产治理流程缺失 | 建立资产审核、发布、废弃、权限和审计机制。 |

## 5. 资产复用层

### 5.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 支撑开发工具、AI Agent、Frontend / Middle / Backend 对仓库资产进行检索、推荐、适配、引用和测试绑定。 |
| 输入契约 | 接收复用场景、业务模型、业务建模语言 IR、目标语言、标签、上下文和用户意图。 |
| 输出契约 | 输出候选资产、推荐结果、适配建议、引用关系、复用结果和测试模板绑定关系。 |
| 交互契约 | 与开发工具、AI Agent、业务建模语言 Frontend / Middle / Backend、资产管理层交互。 |
| 质量契约 | 复用结果可解释、可追踪、可测试，资产引用关系明确，适配过程可审查。 |

### 5.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 资产检索接口 | 支持按领域、场景、标签、模型、目标语言和关键字检索资产。 |
| 资产推荐接口 | 根据需求、模型、IR 上下文和历史使用情况推荐资产。 |
| 资产适配接口 | 支持将组件、模板、规则适配到当前项目模型和上下文。 |
| 资产引用接口 | 记录项目对资产的引用、版本和依赖关系。 |
| 测试模板绑定 | 为复用资产绑定测试模板、测试数据和断言规则。 |
| AI 上下文接口 | 为 AI Agent 提供可检索的领域知识、组件示例和生成规范。 |

### 5.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 手工复用 | 当前复用可能依赖人工查找、复制和改造。 |
| 局部组件复用 | 部分组件或模板可能在团队内部复用，但缺少统一引用关系。 |
| AI 上下文复用不足 | AI Agent 可用的组件、模板和领域知识上下文需要统一提供。 |
| 测试绑定不足 | 复用资产与测试模板、测试报告之间缺少稳定绑定。 |

### 5.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 复用入口不统一 | 建设面向开发工具和 AI Agent 的统一资产检索与推荐接口。 |
| 复用过程不可追踪 | 建立资产引用、版本、依赖和适配记录。 |
| 复用质量不可验证 | 为资产绑定测试模板和质量要求。 |
| AI 复用缺少上下文 | 建设 AI 可直接使用的资产上下文接口和示例库。 |

## 6. 资产回流层

### 6.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 将项目交付结果、测试结果、缺陷修复、运维反馈和领域经验沉淀为仓库资产。 |
| 输入契约 | 接收项目业务建模语言 IR、生成代码、测试报告、缺陷记录、修复方案、运行日志、运维反馈和领域经验。 |
| 输出契约 | 输出候选组件、候选模板、缺陷模式、测试补充、知识条目和待审核资产。 |
| 交互契约 | 与工程集成层、开发工具、测试工具、运维平台、资产管理层交互。 |
| 质量契约 | 回流资产需经过清洗、归类、审核、测试绑定和版本标识后才能发布。 |

### 6.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 项目资产提交 | 从项目交付中提交可复用 IR 组件、模型模板和规则模板。 |
| 测试资产回流 | 将测试用例、测试数据、测试报告和覆盖率结果沉淀为测试模板。 |
| 缺陷模式回流 | 将缺陷原因、修复方式、影响范围和预防规则沉淀为知识或规则。 |
| 运维反馈回流 | 将运行日志、异常信息、性能问题和生产反馈转化为资产改进建议。 |
| 人工审核发布 | 对候选资产进行审核、分类、版本标识和发布。 |
| 资产改进闭环 | 根据复用效果、测试结果和运维反馈持续优化资产。 |

### 6.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 项目交付资产 | 存在项目级组件、模板、测试、缺陷和经验，但回流机制待建立。 |
| 测试结果 | 测试报告和缺陷数据需要与仓库资产建立关系。 |
| 运维反馈 | 运行日志和生产问题尚未稳定回流到资产体系。 |
| 人工经验 | 经验沉淀依赖人工整理，缺少标准化入口和审核流程。 |

### 6.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 项目交付与仓库断裂 | 建立项目资产提交和候选资产生成机制。 |
| 缺陷与测试经验未资产化 | 建立缺陷模式、测试模板和预防规则回流机制。 |
| 运维反馈难以沉淀 | 建立运维反馈到需求、模型、IR、测试和知识库的回流链路。 |
| 缺少审核发布流程 | 建立候选资产审核、分类、版本和发布机制。 |

## 7. 分层映射关系

| 分层 | 逻辑架构核心 | 目标实现架构 | 当前实现架构 |
|------|--------------|--------------|--------------|
| 资产定义层 | 定义资产类型与标准结构 | 组件、模型模板、规则模板、测试模板、翻译模板、AI 生成规范、领域知识 | 分散业务逻辑、模型经验、规则经验、测试经验、AI 使用经验 |
| 资产管理层 | 管理版本、兼容性、分类、标签、检索、权限和发布状态 | 资产目录、版本管理、兼容性管理、分类标签、检索索引、发布管理、权限审计 | 分散文件、局部模板、局部知识、版本管理不足 |
| 资产复用层 | 支撑检索、推荐、适配、引用和测试绑定 | 检索接口、推荐接口、适配接口、引用接口、测试模板绑定、AI 上下文接口 | 手工复用、局部组件复用、AI 上下文不足、测试绑定不足 |
| 资产回流层 | 将交付、测试、缺陷、运维反馈沉淀为资产 | 项目资产提交、测试资产回流、缺陷模式回流、运维反馈回流、人工审核发布 | 项目资产、测试结果、运维反馈、人工经验尚未统一回流 |

## 8. 建设顺序建议

| 阶段 | 建设重点 |
|------|----------|
| 第一阶段 | 定义资产类型、资产结构、目录分类和标签体系。 |
| 第二阶段 | 建设版本管理、兼容性管理、检索索引和发布状态管理。 |
| 第三阶段 | 对接开发工具和 AI Agent，提供资产检索、推荐、适配和引用能力。 |
| 第四阶段 | 为复用资产绑定测试模板和质量要求。 |
| 第五阶段 | 打通项目交付、测试结果、缺陷修复、运维反馈到仓库的回流闭环。 |

## 9. 总结

业务建模语言仓库是 AI 驱动一体化研发流程中的资产治理与复用中心。

按分层架构划分后：

- 资产定义层负责“仓库管理什么资产”。
- 资产管理层负责“资产如何治理和检索”。
- 资产复用层负责“资产如何被开发工具和 AI Agent 使用”。
- 资产回流层负责“项目经验如何沉淀为可复用资产”。

目标建设重点是把分散的业务逻辑、模型模板、规则经验、测试经验、翻译规则和领域知识沉淀为统一、可检索、可复用、可追踪的业务建模语言资产体系。
