# AI 驱动一体化研发流程开发工具分层架构说明

## 1. 文档目标

本文档用于描述 **开发工具** 在 AI 驱动一体化研发流程中的分层架构。

开发工具不是单一 IDE，而是面向业务建模语言体系的操作入口和能力编排层，负责连接开发人员、AI Agent、业务建模语言 Frontend / Middle / Backend、代码仓库、构建流水线和运维反馈。

本文按以下结构描述每一层：

- 逻辑架构。
- 目标实现架构。
- 当前实现架构。
- 当前差距与建设重点。

## 2. 总体分层架构

```text
开发人员 / 业务架构师 / 测试人员 / AI Agent
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 开发入口层                                    │
│ - IDE GUI / CLI / MCP / 直接文件              │
│ - Claude Code / Codex 等 AI Agent 接入         │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 工具能力层                                    │
│ - 编辑 / 校验 / 测试 / 生成 / 影响分析          │
│ - 资产检索 / AI 辅助 / 报告输出                │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 工具内核层                                    │
│ - 调用业务建模语言 Frontend                    │
│ - 调用业务建模语言 Middle                      │
│ - 调用业务建模语言 Backend                     │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 工程集成层                                    │
│ - Git / CI/CD / 测试报告 / 部署运维反馈         │
└──────────────────────────────────────────────┘
```

## 3. 开发入口层

### 3.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 为不同角色和不同场景提供统一开发入口，支持 IDE GUI、CLI、MCP、直接文件和 AI Agent 接入。 |
| 输入契约 | 接收用户操作、命令行参数、MCP 工具调用、业务建模语言文件、模型文件、测试文件和 AI 上下文。 |
| 输出契约 | 输出编辑结果、命令执行结果、工具调用结果、诊断信息、测试报告、生成结果和影响分析结果。 |
| 交互契约 | 与工具能力层交互，不直接承载业务建模语言解析、语义校验和代码生成逻辑。 |
| 质量契约 | 多入口能力一致，交互结果可追踪，文件可版本管理，AI Agent 调用具备标准上下文和工具接口。 |

### 3.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| VS Code Studio | 提供统一 IDE GUI，支持编辑、可视化、诊断、测试和生成操作。 |
| CLI | 支持校验、测试、生成、影响分析、批处理和流水线集成。 |
| MCP Server | 支持 Claude Code、Codex 等 AI Agent 访问项目上下文和调用工具能力。 |
| 直接文件接口 | 支持业务建模语言文件、模型文件、测试文件的直接编辑和版本管理。 |
| AI Agent 接入 | 支持自然语言驱动开发、问题分析、生成建议和修复建议。 |

### 3.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| VS Code Studio | 作为目标统一开发入口的当前实现线索。 |
| IDE GUI | 已规划为日常开发和可视化操作入口。 |
| CLI | 已规划为自动化、流水线和批处理入口。 |
| MCP | 已规划为 Claude Code、Codex 等 AI Agent 接入方式。 |
| 直接文件 | 已规划为版本管理、工程集成和人工编辑方式。 |

### 3.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 多入口能力边界尚未统一 | 明确 IDE、CLI、MCP、直接文件的职责边界和统一调用接口。 |
| MCP 接入规范不足 | 定义 AI Agent 可调用的工具列表、上下文结构和返回结果格式。 |
| 文件接口与工具操作关系不清 | 明确业务建模语言文件、模型文件、测试文件的目录结构和版本管理方式。 |
| GUI 与 CLI 能力可能重复实现 | 建设统一工具能力层，避免入口层重复实现核心逻辑。 |

## 4. 工具能力层

### 4.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 承载开发工具的核心操作能力，包括编辑、校验、测试、生成、影响分析、资产检索、AI 辅助和报告输出。 |
| 输入契约 | 接收开发入口层传入的文件、命令、上下文、模型、测试配置和 AI 请求。 |
| 输出契约 | 输出诊断结果、格式化结果、测试报告、生成报告、影响分析报告和资产检索结果。 |
| 交互契约 | 向下调用工具内核层能力，向上向开发入口层返回标准化结果。 |
| 质量契约 | 能力接口统一，结果格式统一，错误信息可诊断，执行过程可追踪。 |

### 4.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 业务建模语言编辑器 | 支持语法高亮、补全、跳转、格式化和引用查看。 |
| 诊断器 | 支持语法诊断、模型引用诊断、语义诊断和兼容性诊断。 |
| 测试执行器 | 支持业务建模语言 IR 测试、测试用例执行和测试报告输出。 |
| 生成触发器 | 支持触发 Java / C++ / SQL、配置和测试代码生成。 |
| 影响分析器 | 支持需求、模型、IR、生成代码和测试资产之间的影响分析。 |
| 资产检索器 | 支持从业务建模语言仓库检索组件、模板、规则和领域知识。 |
| AI 辅助器 | 支持需求结构化、IR 生成建议、问题解释和修复建议。 |
| 报告输出器 | 输出诊断报告、测试报告、生成报告和影响分析报告。 |

### 4.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 编辑能力 | 待统一到业务建模语言编辑器。 |
| 校验能力 | 待统一到诊断器，并与 Middle 层语义校验对接。 |
| 测试能力 | 待统一到测试执行器，并与业务建模语言 IR 测试语义对接。 |
| 生成能力 | 待统一到生成触发器，并与 Backend 生成器对接。 |
| AI 辅助能力 | 已有 Claude Code、Codex 接入规划，需要统一上下文和工具调用规范。 |

### 4.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 工具能力清单尚未固化 | 明确编辑、校验、测试、生成、影响分析、资产检索的能力边界。 |
| 结果格式不统一 | 定义诊断结果、测试报告、生成报告、影响分析报告的统一结构。 |
| AI 辅助缺少约束 | 定义 AI 生成、解释、修复建议的输入上下文和输出格式。 |
| 工具能力与语言内核耦合关系不清 | 通过工具内核层统一封装 Frontend / Middle / Backend 调用。 |

## 5. 工具内核层

### 5.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 统一封装业务建模语言 Frontend / Middle / Backend 能力，为工具能力层提供稳定调用接口。 |
| 输入契约 | 接收工具能力层传入的解析、校验、测试、生成、影响分析和资产复用请求。 |
| 输出契约 | 输出 Frontend 解析结果、Middle 语义结果、Backend 生成结果和相关报告。 |
| 交互契约 | 与业务建模语言体系交互，屏蔽入口层和能力层对底层实现细节的直接依赖。 |
| 质量契约 | 调用接口稳定，执行结果可追踪，错误信息可定位，生成结果可重复。 |

### 5.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| Frontend 调用服务 | 调用业务建模语言规格解析、文本解析、DSL 解析和可视化模型解析能力。 |
| Middle 调用服务 | 调用统一业务建模语言 IR、AST / 语义模型、元数据规范、语义校验、影响分析和测试语义能力。 |
| Backend 调用服务 | 调用 Java / C++ / SQL Generator、配置生成器、测试代码生成器和工程模板适配能力。 |
| 工具上下文管理 | 管理项目上下文、文件上下文、AI 上下文、模型上下文和执行上下文。 |
| 执行编排器 | 编排解析、校验、测试、生成、报告输出等工具链流程。 |

### 5.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| HSDDML | 作为 Frontend 输入格式之一，需要通过工具内核统一解析适配。 |
| HFlow JSON | 作为 Frontend 输入格式之一，需要通过工具内核统一解析适配。 |
| 大数据 YML / 表设计器 XML | 作为 Frontend 输入格式之一，需要通过工具内核统一解析适配。 |
| 统一业务建模语言 IR | 作为 Middle 核心能力，需要由工具内核统一调用。 |
| 代码生成器 | 作为 Backend 能力，需要由工具内核统一触发。 |
| JRES / CRES | 作为目标生成或运行体系，需要由工具内核统一对接。 |

### 5.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 工具入口可能直接依赖底层能力 | 建设工具内核层，统一封装语言体系能力。 |
| Frontend / Middle / Backend 调用边界不清 | 明确三层能力的调用接口、输入输出和错误结构。 |
| 上下文管理分散 | 建设统一项目上下文、模型上下文、AI 上下文和执行上下文。 |
| 工具链流程缺少统一编排 | 建设执行编排器，统一解析、校验、测试、生成和报告输出流程。 |

## 6. 工程集成层

### 6.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 连接开发工具与工程交付体系，支撑代码仓库、构建流水线、测试报告、部署运维和反馈回流。 |
| 输入契约 | 接收生成代码、配置、测试代码、工程模板、构建参数和发布参数。 |
| 输出契约 | 输出代码提交、构建结果、测试报告、部署结果、运行反馈和缺陷信息。 |
| 交互契约 | 与 Git、制品库、CI/CD、测试平台、运维平台和业务建模语言仓库交互。 |
| 质量契约 | 工程产物可构建、可测试、可发布，运行反馈可回流，交付链路可追踪。 |

### 6.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| Git 接口 | 支持生成产物提交、变更对比、版本管理和回滚。 |
| CI/CD 接口 | 支持构建、测试、扫描、制品生成和发布触发。 |
| 测试报告接口 | 接收单元测试、集成测试、IR 测试和覆盖率报告。 |
| 运维反馈接口 | 接收运行日志、异常信息、性能指标、生产缺陷和用户反馈。 |
| 资产回流接口 | 将组件、模板、测试、缺陷修复和经验沉淀到业务建模语言仓库。 |

### 6.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 代码仓库 | 待明确与开发工具生成产物的集成方式。 |
| 构建流水线 | 待明确与 CLI、生成器、测试执行器的集成方式。 |
| 测试报告 | 待统一报告结构和回收方式。 |
| 运维反馈 | 待建立反馈到需求、模型、IR 和资产仓库的闭环。 |

### 6.4 当前差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 工程交付链路尚未闭环 | 打通生成、提交、构建、测试、发布和反馈流程。 |
| 测试报告与生成链路割裂 | 统一 IR 测试、目标代码测试和工程测试报告。 |
| 运维反馈难以回流研发资产 | 建设运维反馈接口和资产回流接口。 |
| 工程集成标准不明确 | 定义 Git、CI/CD、测试平台、运维平台的集成契约。 |

## 7. 分层映射关系

| 分层 | 逻辑架构核心 | 目标实现架构 | 当前实现架构 |
|------|--------------|--------------|--------------|
| 开发入口层 | 多入口统一访问 | VS Code Studio、IDE GUI、CLI、MCP Server、直接文件、AI Agent 接入 | VS Code Studio、IDE、CLI、MCP、直接文件 |
| 工具能力层 | 编辑、校验、测试、生成、影响分析、资产检索 | 编辑器、诊断器、测试执行器、生成触发器、影响分析器、资产检索器、AI 辅助器 | 编辑、校验、测试、生成、AI 辅助能力待统一 |
| 工具内核层 | 统一调用业务建模语言 Frontend / Middle / Backend | Frontend 调用服务、Middle 调用服务、Backend 调用服务、上下文管理、执行编排器 | HSDDML、HFlow JSON、大数据 YML、表设计器 XML、IR、代码生成器、JRES、CRES |
| 工程集成层 | 连接代码仓库、构建测试、部署运维和反馈回流 | Git 接口、CI/CD 接口、测试报告接口、运维反馈接口、资产回流接口 | 代码仓库、构建流水线、测试报告、运维反馈待明确 |

## 8. 建设顺序建议

| 阶段 | 建设重点 |
|------|----------|
| 第一阶段 | 明确开发入口层和工具能力层边界，固化 IDE / CLI / MCP / 文件入口。 |
| 第二阶段 | 建设工具内核层，统一封装业务建模语言 Frontend / Middle / Backend 调用。 |
| 第三阶段 | 建设 MCP Server 和 AI Agent 接入能力，支持 Claude Code / Codex 使用工具链。 |
| 第四阶段 | 打通编辑、校验、测试、生成、影响分析和报告输出流程。 |
| 第五阶段 | 打通 Git、CI/CD、测试报告、运维反馈和资产回流闭环。 |

## 9. 总结

开发工具是 AI 驱动一体化研发流程的操作入口和能力编排层。

按分层架构划分后：

- 开发入口层负责“谁通过什么入口使用工具”。
- 工具能力层负责“工具能做什么”。
- 工具内核层负责“如何调用业务建模语言体系能力”。
- 工程集成层负责“如何进入工程交付和反馈闭环”。

目标建设重点是避免 IDE、CLI、MCP、AI Agent 各自实现一套逻辑，而是通过统一工具能力层和工具内核层，复用同一套业务建模语言 Frontend / Middle / Backend 能力。
