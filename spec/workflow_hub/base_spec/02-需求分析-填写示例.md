## 2. 引言

### 1.1 编写目的

本文档对"消息队列TTL自动清理"需求进行需求分析，作为设计、开发和测试的依据。

### 1.2 目标与背景

UMQ 在生产环境长期运行后，部分业务系统因升级或下线导致其订阅的消息队列变为"僵尸队列"——无消费者但持续堆积消息。某交易系统运维团队反馈，这类僵尸队列导致 Broker 存储空间持续增长、GC 频繁触发，已影响同集群中其他正常业务队列的性能。本需求引入 TTL（Time-To-Live）自动清理机制，解决僵尸队列的自动发现与清理问题。

### 1.3 假设与约束

| 类别 | 内容 |
|------|------|
| 假设 | 1. 生产环境已部署 UMQ V3.1 及以上<br>2. 运维团队具备管理控制台操作权限<br>3. 队列的消费者状态信息可通过 Broker 元数据获取 |
| 约束 | 1. 不能影响现有队列的正常消息投递和消费<br>2. TTL 清理操作需可审计，满足合规要求<br>3. 必须有防误删机制<br>4. 开发周期不超过 20 人天 |

### 1.4 术语定义

| 术语/缩写 | 定义说明 |
|-----------|----------|
| TTL | Time-To-Live，存活时间，超时后自动清理 |
| 僵尸队列 | 无活跃消费者且持续堆积消息的队列，通常由业务系统下线后遗留 |
| queueTTL | 队列级 TTL，队列在无消费者且无新消息后的自动过期时间 |
| messageTTL | 消息级 TTL，单条消息从入队到过期的存活时间 |
| Broker | UMQ 的消息服务节点 |

## 3. 价值表达三要素

### 2.1 解决什么问题

**痛点：** 部分业务系统（如旧版清算模块、已下线的报表服务）升级或退役后，队列未同步清理，变成僵尸队列。无消费者但生产端仍在写消息，导致持续堆积。

**影响范围：** 当前某交易系统集群中有约 120 个僵尸队列（占总队列数 15%），累计堆积超过 8000 万条消息，占用 35GB 存储。

**不做会怎样：**
- Broker 存储以每月约 5GB 增长，预计 6 个月后触发磁盘满告警，影响所有业务队列写入
- GC 频繁触发导致正常队列投递延迟 P99 从 15ms 升至 40ms，已接近风控系统容忍上限（50ms）
- 运维每月花约 8 小时人工排查清理，且过去 6 个月发生过 2 次误删活跃队列事件，每次恢复耗时约 4 小时

### 2.2 适合什么场景

**目标用户：** UMQ 运维工程师、交易系统运维管理员

**业务场景：**
- 日常巡检发现无消费者的堆积队列，需要安全清理释放资源
- 业务系统升级或下线后，自动清理关联的消息队列
- 为消息设置有效期，防止过期数据无限堆积

**使用前提：**
- UMQ 版本升级至 V3.2
- 运维人员通过管理控制台或配置文件设置 TTL 参数
- 队列必须先经过"无消费者观察期"才会触发 TTL 倒计时

### 2.3 场景边界

| 序号 | 场景类型 | 场景描述 | 是否适用 | 原因说明 | 替代方案 |
|------|----------|----------|----------|----------|----------|
| 1 | 适用 | 业务系统下线后遗留的僵尸队列自动清理 | 适用 | 无消费者且无业务价值，TTL 到期后安全删除 | - |
| 2 | 适用 | 临时调试/测试队列的自动过期清理 | 适用 | 设置较短 TTL 可自动回收 | - |
| 3 | 适用 | 消息级过期清理（如行情快照超过 3 秒无价值） | 适用 | 过期消息自动丢弃节省存储 | - |
| 4 | 不适用 | 需要永久保留历史消息的归档类队列 | 不适用 | 归档消息需长期保留 | 用独立归档服务，或将队列标记为"免清理" |
| 5 | 不适用 | 消费者临时断连的正常业务队列（如网络闪断） | 不适用 | 短暂断连不代表队列废弃 | queueTTL 设足够长（建议 ≥ 24 小时），结合消费者心跳检测 |

### 2.4 收益分析

| 序号 | 收益维度 | 当前基线 | 预期目标 | 衡量方式 | 验证时间点 |
|------|----------|----------|----------|----------|------------|
| 1 | 运维效率 | 每月 8 小时人工清理 | ≤ 0.5 小时（仅审核清理日志） | 运维工单系统工时统计 | 上线后首月 |
| 2 | 存储成本 | 僵尸队列占 35GB，月增 5GB | 降至 ≤ 2GB（仅 TTL 观察期暂存） | 监控平台存储用量 | 上线后 2 周 |
| 3 | 运营风险 | 6 个月内 2 次误删，恢复共 8 小时 | 误删降至零（TTL 含安全保护） | 误删事件工单数量 | 上线后 3 个月 |
| 4 | 系统性能 | 正常队列延迟 P99 从 15ms 升至 40ms | 清理后回落至 15ms 以内 | 监控平台延迟指标 | 上线后 2 周 |

## 4. 需求描述（黄金圈法则）

### 3.1 Why — 业务问题

某交易系统运维团队反馈：生产集群约 120 个僵尸队列，持续堆积消息导致存储压力和性能劣化。当前只能人工巡检发现和清理，效率低且有误操作风险。

### 3.2 How — 解决思路

1. **队列级 TTL：** 队列在指定时间内无消费者且无新消息写入时，自动清理
2. **消息级 TTL：** 单条消息超时后在消费时自动跳过，后台定期物理清理
3. **安全保护：** 清理前做活跃度检查（消费者心跳、最近消费时间），防止误清理；操作可审计

### 3.3 What — 具体需求

1. **queueTTL 配置：** 队列在无消费者超时后自动删除
2. **messageTTL 配置：** 过期消息自动清理
3. **队列最大长度限制：** 超限时按 FIFO 淘汰旧消息
4. **TTL 即将过期通知：** 倒计时达到阈值时告警通知运维
5. **管理控制台支持：** 可视化 TTL 配置和剩余时间

### 5.2 业务流程分析

**当前流程（AS-IS）：**

```
运维人员定期巡检（每周） → 人工筛查无消费者队列 → 逐一确认是否可删
→ 手动执行删除 → 记录操作日志
```

问题：巡检频率低、确认耗时（需联系业务方）、有误删风险

**期望流程（TO-BE）：**

```
运维配置TTL策略（一次性） → 系统自动监测队列活跃度 → 满足TTL条件时
→ 发送即将清理通知 → 等待保护期 → 自动清理 → 记录审计日志
```

核心变化：从"人工定期巡检+手动清理"变为"策略驱动+自动清理+通知确认"

## 7. 功能需求

### 6.1 功能模块一：TTL配置管理

#### 6.1.1 队列TTL配置（queueTTL）

| 字段 | 内容 |
|------|------|
| 需求编号 | UMQ-2026-0042-F001 |
| 优先级 | P1-关键 |
| 功能描述 | 支持为队列设置存活时间（queueTTL），队列在指定时间内无活跃消费者且无新消息写入时，自动删除该队列及所有堆积消息。通过配置文件（hs.bindings.input.[instanceId].queueTTL）或管理控制台设置，单位毫秒，默认 0（不过期）。 |

**验收标准：**

| 序号 | Given | When | Then |
|------|-------|------|------|
| AC-1 | Q1 配置 queueTTL=3600000（1小时），无活跃消费者 | 1 小时无消费者且无新消息 | 系统自动删除 Q1 及所有消息，记录审计日志 |
| AC-2 | Q1 配置 queueTTL=3600000，倒计时已开始 | 新消费者连接到 Q1 | 倒计时立即重置并暂停 |
| AC-3 | Q1 的 queueTTL=0 | 长时间无消费者 | 不会被自动清理 |

#### 6.1.2 消息TTL配置（messageTTL）

| 字段 | 内容 |
|------|------|
| 需求编号 | UMQ-2026-0042-F002 |
| 优先级 | P1-关键 |
| 功能描述 | 支持为队列中的消息设置存活时间（messageTTL），消息从入队起计时，超时后消费端拉取时自动跳过，后台线程异步清理。通过 hs.bindings.input.[instanceId].messageTTL 配置，单位毫秒，默认 0（不过期）。 |

**验收标准：**

| 序号 | Given | When | Then |
|------|-------|------|------|
| AC-1 | Q1 配置 messageTTL=60000（1分钟），10 条消息中 3 条已超时 | 消费者拉取消息 | 只收到 7 条未过期消息，3 条被跳过 |
| AC-2 | Q1 配置 messageTTL=60000 | 后台清理线程执行扫描 | 过期消息物理删除，释放存储，记录日志 |

#### 6.1.3 队列最大长度限制

| 字段 | 内容 |
|------|------|
| 需求编号 | UMQ-2026-0042-F003 |
| 优先级 | P2-重要 |
| 功能描述 | 支持为队列设置最大消息数（queueMaxLength）和最大存储字节数（queueMaxLengthBytes），超限时按 FIFO 淘汰最旧消息。默认 0（不限制）。 |

**验收标准：**

| 序号 | Given | When | Then |
|------|-------|------|------|
| AC-1 | Q1 配置 queueMaxLength=10000，当前 10000 条 | 写入 1 条新消息 | 最旧 1 条被淘汰，总数保持 10000 |
| AC-2 | Q1 配置 queueMaxLengthBytes=1GB，当前占用 1GB | 写入 100KB 新消息 | FIFO 淘汰旧消息腾出空间，新消息入队 |
| AC-3 | 同时配置了 maxLength 和 maxLengthBytes | 任一限制先触达 | 先触达的生效 |

#### 6.1.4 TTL即将过期通知

| 字段 | 内容 |
|------|------|
| 需求编号 | UMQ-2026-0042-F004 |
| 优先级 | P2-重要 |
| 功能描述 | 队列 queueTTL 倒计时达到阈值（如剩余 10%）时，控制台显示告警标识，并通过配置的告警通道（邮件/企业微信）通知运维。通知含队列名、所属实例、TTL 配置、剩余时间和堆积消息数。 |

**验收标准：**

| 序号 | Given | When | Then |
|------|-------|------|------|
| AC-1 | Q1 配置 queueTTL=86400000（24小时），阈值 10% | 倒计时剩余 ≤ 2.4 小时 | 控制台告警标识 + 告警通道通知 |
| AC-2 | 运维收到告警 | 重新绑定消费者或延长 TTL | 倒计时重置，告警解除 |

## 8. 非功能需求

### 7.1 性能需求

| 指标 | 要求 |
|------|------|
| TTL 检测延迟 | 队列 TTL 到期后，清理执行延迟 ≤ 60 秒 |
| 过期消息清理吞吐 | 后台清理线程 ≥ 10 万条/秒 |
| 对正常业务影响 | 清理线程 CPU ≤ 5%（单核），不影响正常投递延迟 |

### 7.2 容量需求

| 指标 | 要求 |
|------|------|
| TTL 配置数量 | 单集群 ≥ 10000 个队列同时配置 |
| 元数据存储 | 每队列增加 ≤ 100 字节，总增量 ≤ 1MB |

### 7.3 可靠性需求

| 指标 | 要求 |
|------|------|
| 元数据持久化 | TTL 配置随队列元数据同步持久化，Broker 重启后自动恢复 |
| 清理事务性 | 原子操作，不会出现"队列删了但消息残留" |
| 故障恢复 | Broker 重启后，TTL 倒计时从持久化的起始时间恢复，不重新计时 |

### 7.4 安全需求

| 指标 | 要求 |
|------|------|
| 权限控制 | TTL 配置修改需 admin 角色，普通用户只读 |
| 审计日志 | 所有 TTL 变更和自动清理操作记录审计日志 |
| 防误删 | TTL 到期时若检测到最近 1 分钟内有消费者心跳，跳过清理并告警 |

### 7.5 兼容性需求

| 指标 | 要求 |
|------|------|
| 版本兼容 | 向下兼容 V3.1 客户端 SDK，未设置 TTL 的队列行为不变 |
| 配置兼容 | 新增配置项默认值均为 0（不过期），升级无需改配置 |
| 平台兼容 | CentOS 7.6+、Kylin V10 SP2；Intel X86、海光X86、鲲鹏ARM |
