|------|------|

## 升级指引

### 升级路径

支持从V3.1.x直接升级至V3.2.0。不支持从V3.0.x直接升级，需先升级至V3.1.x。

### 升级步骤

1. **备份**：备份Broker的data目录和config目录
2. **停止服务**：按照先消费端、后生产端、最后Broker的顺序停止服务
3. **替换程序包**：将V3.2.0安装包解压覆盖至安装目录
4. **检查配置**：确认config目录中新增的TTL相关配置项使用默认值（无需修改）
5. **启动服务**：按照先Broker、后生产端、最后消费端的顺序启动服务
6. **验证**：登录管理控制台检查集群状态和队列状态正常

### 升级注意事项

- 升级过程预计停机时间约15分钟（单集群）
- 升级后配置文件向后兼容，无需修改现有配置
- 建议在业务低峰期进行升级
- 回退方案：如升级异常，将程序包还原为V3.1.x并使用备份数据恢复

# 消息队列自动过期清理 用户手册

## 1. 功能概述

### 1.1 场景说明

在UMQ长期运行中，部分业务系统因升级、迁移或下线，其使用的消息队列可能被遗留在服务器上。这些队列没有消费者在消费，但生产端可能仍在写入，导致消息持续堆积。时间长了，这些废弃队列会占用大量存储空间，还影响同集群中其他正常队列的性能。

消息队列自动过期清理功能让运维人员可以为队列和消息设置存活时间（TTL），系统自动识别并清理超时且无活跃消费者的队列和过期消息，不再需要人工逐一排查，同时通过安全保护机制避免误删在用的队列。

### 1.2 使用边界

| 使用建议 | 场景 | 说明 |
|----------|------|------|
| **推荐使用** | 业务系统下线后遗留的废弃队列清理 | 队列已无消费者且无业务价值，设置queueTTL后系统自动清理 |
| **推荐使用** | 临时调试/测试环境中创建的队列 | 设置较短的queueTTL可自动回收临时队列 |
| **推荐使用** | 具有时效性的消息（如行情快照） | 设置messageTTL可自动丢弃过期消息，节省存储 |
| **不建议使用** | 需要永久保存消息的归档类队列 | 归档队列的消息需长期保留，不应设置TTL。建议使用独立的消息归档服务 |
| **不建议使用** | 消费者会频繁短暂断连的场景 | 消费者临时断连不代表队列废弃。如需使用，请将queueTTL设置为足够长的时间（建议≥24小时） |

### 1.3 预期效果

- 运维队列清理工时从每月约8小时降至约0.5小时，减少94%
- 废弃队列占用的存储空间（约35GB）在TTL到期后自动释放
- 消除人工清理过程中的误删风险
- 清理废弃队列后，同集群正常业务队列的消息投递延迟恢复正常水平

## 3. 操作步骤

### 步骤1：登录管理控制台

登录UMQ管理控制台，导航到"队列管理"页面，找到需要配置TTL的目标队列。

### 步骤2：进入队列详情页

点击目标队列名称进入队列详情页。在详情页中可看到新增的"TTL配置"区域（位于页面中部）。

### 步骤3：设置队列TTL（queueTTL）

在"TTL配置"区域，找到"队列存活时间"输入框，设置队列的存活时间。

> **关键参数：** 队列存活时间（queueTTL） — 当队列在设定时间内无活跃消费者且无新消息写入时，系统自动删除该队列。建议设置为86400000（24小时）或更长。设置为0表示不过期。

### 步骤4：设置消息TTL（messageTTL）

在"TTL配置"区域，找到"消息存活时间"输入框，设置单条消息的存活时间。

> **关键参数：** 消息存活时间（messageTTL） — 消息从入队起超过设定时间后自动过期。过期消息不会被消费者接收，由后台线程异步清理。设置为0表示不过期。

### 步骤5：设置队列容量限制（可选）

如需限制队列的最大消息数或存储大小，在"容量限制"区域设置queueMaxLength和queueMaxLengthBytes。

### 步骤6：保存并确认

点击"保存"按钮。系统会弹出确认对话框，显示配置变更摘要。确认无误后点击"确定"。

**操作完成确认：** 保存后，"TTL配置"区域会显示"状态：已启用"和TTL倒计时（如果队列当前无消费者）。

---

## 4. 配置参数说明

| 参数名 | 默认值 | 单位 | 说明 | 注意事项 |
|--------|--------|------|------|----------|
| queueTTL | 0（不过期） | 毫秒 | 队列存活时间。队列在无消费者且无新消息后超过该时间自动删除。 | 设置过短可能导致消费者临时断连的队列被误清理。建议≥86400000（24小时）。活跃消费者重连后倒计时自动重置。 |
| messageTTL | 0（不过期） | 毫秒 | 单条消息存活时间。消息从入队起超时后不再投递给消费者。 | **注意：过期消息将被永久丢弃，无法恢复。** 请根据业务对消息时效性的要求合理设置。 |
| queueMaxLength | 0（不限制） | 条 | 队列最大消息数量。超过限制时按先入先出策略淘汰最旧的消息。 | 与messageTTL同时配置时，两个条件独立生效，先触发的先执行。 |
| queueMaxLengthBytes | 0（不限制） | 字节 | 队列最大存储字节数。超过限制时按先入先出策略淘汰最旧的消息。 | 建议根据磁盘容量规划合理设置，预留20%冗余空间。 |

## 5. 常见问题

**Q1：设置了queueTTL后，正在使用的队列会不会被误清理？**

A：不会。queueTTL的倒计时只在队列**同时满足**"无活跃消费者"和"无新消息写入"两个条件时才开始。一旦有新的消费者连接或新消息写入，倒计时立即重置并暂停。此外，即使TTL到期，系统在执行清理前还会进行最后一次活跃度检查，如检测到最近1分钟内有消费者心跳，会跳过清理并发出告警。

**Q2：设置messageTTL后，过期消息是立即被删除还是延迟删除？**

A：过期消息不会立即被物理删除，而是在两个时机被清理：1）消费者拉取消息时，过期消息被自动跳过不投递；2）Broker后台清理线程定期扫描并物理删除过期消息（扫描间隔默认60秒）。因此从设置messageTTL到消息被物理删除，最长可能有约60秒延迟。

**Q3：如何恢复被TTL清理掉的队列？**

A：TTL清理是不可逆操作，已清理的队列和消息无法恢复。因此建议：1）初次使用时先在测试环境验证TTL参数设置；2）为重要队列设置较长的queueTTL（如7天）；3）关注TTL即将过期的告警通知，在清理前确认队列确实不再需要。

**Q4：升级到V3.2后，现有队列会受到影响吗？**

A：不会。升级后所有现有队列的TTL参数默认为0（不过期），行为与升级前完全一致。您需要手动为需要自动清理的队列启用TTL功能。

## 2. 场景演示（约18分钟）

### 场景1：业务系统下线后的废弃队列自动清理

- **背景：** 假设清算系统旧版本已于上月下线，其订阅的3个消息队列已无消费者，消息持续堆积。
- **演示要点：**
  1. 在管理控制台展示这3个队列的状态（无消费者、消息数持续增长）
  2. 为这3个队列配置queueTTL=86400000（24小时）
  3. （使用模拟时间加速）展示24小时后队列状态变为"待清理"，系统发送告警通知
  4. 展示队列被自动清理后，存储空间释放、集群性能指标恢复
- **效果对比：** 之前需要人工排查+联系业务方确认+手动删除（耗时约2小时），现在一次性配置TTL策略后全自动完成

### 场景2：消息有效期管理（行情快照消息）

- **背景：** 行情系统每3秒推送一次IOPV快照数据，下游消费系统如果因升级重启有短暂中断，重连后不需要消费5分钟前的过期快照。
- **演示要点：**
  1. 为行情快照队列配置messageTTL=300000（5分钟）
  2. 展示消费者断连5分钟后重连，自动跳过过期消息，从最新的有效消息开始消费
  3. 展示后台清理线程自动清理过期消息，存储不会无限增长
- **效果对比：** 之前消费者重连后需要追赶大量无价值的过期消息（增加处理延迟），现在直接从有效消息开始消费

### 场景3：安全保护机制演示

- **背景：** 展示TTL的安全保护机制如何防止误删。
- **演示要点：**
  1. 为一个有活跃消费者的队列设置较短的queueTTL（如5分钟）
  2. 展示即使TTL到期，因检测到活跃消费者心跳，清理操作被跳过并产生告警
  3. 断开消费者后，展示倒计时从断开时刻重新开始（而非从设置时刻计算）
- **效果对比：** 系统自动区分"真的废弃"和"临时断连"，消除人工判断的不确定性

## 3. 操作指导（约18分钟）

### 操作环节1：通过管理控制台配置TTL

1. 登录UMQ管理控制台
2. 进入"队列管理"→ 选择目标队列 → 进入"详情"页面
3. 在"TTL配置"区域填写参数：
   - **queueTTL：** 输入存活时间（毫秒）。建议普通队列设为86400000（24小时），临时队列设为3600000（1小时）
   - **messageTTL：** 输入消息有效期（毫秒）。如不需要可保持为0
   - **易错点：** 单位是毫秒不是秒！24小时=86400000毫秒，不是86400
4. 点击"保存"→ 确认变更
5. 验证：查看"TTL状态"显示"已启用"

### 操作环节2：通过配置文件批量配置

1. 编辑Broker配置文件 `application.yml`
2. 添加TTL配置项：
   ```
   hs.bindings.input.[instanceId].queueTTL=86400000
   hs.bindings.input.[instanceId].messageTTL=0
   hs.bindings.input.[instanceId].queueMaxLength=0
   hs.bindings.input.[instanceId].queueMaxLengthBytes=0
   ```
3. 重启Broker服务使配置生效
4. **易错点：** 配置文件中的instanceId必须与队列绑定的实例ID一致

- 练习题目：为测试环境中的3个队列分别配置不同的TTL（1小时、12小时、24小时），验证TTL状态和倒计时显示
- 预期结果：管理控制台中3个队列分别显示对应的TTL剩余时间
- 参考时间：10分钟

## 5. 复杂场景案例（约12分钟）

### 案例1：多集群TTL差异化策略设计

- **业务背景：** 某券商有3个UMQ集群分别服务于交易系统（高敏感）、清算系统（中敏感）和通知系统（低敏感）。不同集群对队列清理的时间容忍度和安全要求差异很大。

- **挑战：**
  - 交易集群：消费者可能因为网络切换短暂断连（秒级到分钟级），queueTTL设得太短会误清理
  - 清算集群：日终清算有固定时间窗口，队列在非清算时段可能长时间无消费者
  - 通知集群：队列数量多但单个队列消息量小，大部分是短期使用

- **方案设计：**
  - 交易集群：queueTTL=604800000（7天），留足安全裕量，配合消费者心跳检测
  - 清算集群：queueTTL=172800000（2天），覆盖两个清算周期；messageTTL=86400000（24小时），清算数据超过1天后无业务价值
  - 通知集群：queueTTL=86400000（24小时），快速回收；queueMaxLength=100000，限制单队列堆积上限

- **关键决策：** TTL值的设定需要在"及时清理"和"防止误删"之间取得平衡。核心原则是：TTL应大于该类队列消费者最长的合理断连时间的2倍以上。

- **讨论问题：** 如果你们的环境中有定时任务类消费者（每天只在固定时段运行），queueTTL应该怎么设？（参考答案：TTL应>两个运行周期的间隔，如每天运行一次则TTL应>48小时）

### 案例2：TTL与消息重要性分级的结合

- **业务背景：** 同一个集群中，不同队列的消息重要性差异很大——交易指令消息不能有任何丢失，而监控指标消息过期后无价值。

- **挑战：** 如何为不同重要性的消息设计合理的TTL策略，同时避免配置复杂度过高？

- **方案设计：** 建立消息分级体系和对应的默认TTL模板：
  - S级（关键业务消息）：queueTTL=0（永不过期）、messageTTL=0（永不过期），依赖归档服务定期转储
  - A级（重要业务消息）：queueTTL=604800000（7天）、messageTTL=259200000（3天）
  - B级（一般业务消息）：queueTTL=86400000（24小时）、messageTTL=86400000（24小时）
  - C级（临时/监控消息）：queueTTL=3600000（1小时）、messageTTL=300000（5分钟）

- **经验总结：** 将TTL策略与消息分级绑定，形成标准化模板，避免逐个队列手动配置。新建队列时选择分级即可自动应用对应的TTL策略。

- **讨论问题：** 你们的业务中有哪些消息适合归入各个级别？S级消息除了不设TTL，还需要什么额外的保护措施？
