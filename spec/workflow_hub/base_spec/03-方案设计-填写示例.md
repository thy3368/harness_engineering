## 3. 方案概述

### 3.1 整体思路

本方案采用"懒删除 + 后台扫描"的混合策略实现消息TTL自动清理。核心理念是在不影响消息队列正常读写性能的前提下，以最低系统开销完成过期消息的识别和清理。懒删除保证消费路径上的过期消息被即时过滤，后台扫描兜底清理无人消费的僵尸队列中的堆积消息。

方案设计有三个原则：一是安全优先，引入保护期机制避免误删；二是可观测，清理过程全程记录审计日志并暴露监控指标；三是可配置，TTL 阈值和清理策略支持热更新，运维可按集群和队列粒度灵活调整。

### 3.2 系统架构 / 流程图

```
Producer ──写入消息──> Broker（附加TTL元数据）──存储──> MessageStore
                                                         │
Consumer ──拉取消息──> Broker ──读取──> MessageStore       │
                        │                                 │
                   [懒删除检查]                            │
                   过期则跳过并标记                         │
                                                         │
                   TTLScanner（后台线程）──定期扫描──> MessageStore
                        │                                 │
                   [过期检测]                              │
                   批量标记过期消息                         │
                        │                                 │
                   CleanupExecutor ──批量删除──> MessageStore
                        │
                   AuditLogger ──记录──> 审计日志
                        │
                   MetricsExporter ──上报──> 监控系统
```

各组件职责：
- **Broker**：消息读写主路径，集成懒删除检查逻辑，消费时过滤过期消息
- **TTLScanner**：后台扫描线程，按可配置的间隔扫描队列中的过期消息
- **CleanupExecutor**：清理执行器，负责批量删除过期消息，控制删除速率避免IO尖峰
- **AuditLogger**：审计日志记录器，记录每次清理的队列、消息数量、释放空间
- **MetricsExporter**：监控指标上报，包括清理数量、扫描耗时、存储释放量

#### 5.1.2 逻辑设计

**懒删除流程：**

1. Consumer 发起拉取消息请求
2. Broker 从 MessageStore 读取下一条消息
3. 检查消息的 `createTime + messageTTL` 是否小于当前时间
4. 若已过期，再检查是否处于保护期（`currentTime - expireTime < protectionPeriod`）
5. 保护期内的过期消息跳过删除，仅标记为 `EXPIRED_PROTECTED`
6. 超出保护期的过期消息标记为 `EXPIRED_DELETABLE`，跳过该消息继续读取下一条
7. 被标记的消息在下次后台扫描时批量删除

**后台扫描流程：**

1. TTLScanner 按配置间隔（默认 5 分钟）触发扫描任务
2. 获取当前集群的队列列表，按队列消息积压量降序排列
3. 逐队列扫描，读取队列头部消息的创建时间
4. 若头部消息已过期且超出保护期，启动该队列的批量清理
5. CleanupExecutor 按 `cleanupBatchSize` 分批删除，每批之间间隔 100ms，避免IO尖峰
6. 单次扫描周期内若清理总量达到集群级限额（默认 10 万条），暂停清理等待下次周期
7. 记录审计日志，上报监控指标

**过期检测算法：**

```
isExpired(message) = currentTimeMillis() > (message.createTime + queue.messageTTL * 1000)
isDeletable(message) = isExpired(message) && (currentTimeMillis() - getExpireTime(message) > queue.protectionPeriod * 1000)
```

#### 5.1.3 异常处理

| 异常场景 | 触发条件 | 处理策略 | 用户感知 |
|---------|---------|---------|---------|
| 扫描任务超时 | 单次扫描耗时超过扫描间隔的 80% | 中断当前扫描，记录已扫描进度，下次从断点继续 | 无感知，清理延迟一个周期 |
| 删除操作失败 | MessageStore 写入异常（如磁盘满） | 重试 3 次，间隔指数退避（1s/2s/4s），仍失败则跳过并告警 | 无感知，消息保留至下次清理 |
| TTL配置热更新冲突 | 并发修改同一队列的TTL配置 | 基于版本号的乐观锁，冲突时返回 409 状态码 | API返回冲突错误，需重试 |
| 保护期内误触发清理 | 时钟偏移导致保护期判断错误 | 保护期计算增加 5 分钟冗余，使用单调时钟避免时钟回拨影响 | 无感知 |
| 扫描线程异常退出 | 未捕获异常导致线程终止 | 看门狗线程每 30 秒检测扫描线程状态，异常退出后自动重启 | 无感知，最长 30 秒恢复 |

#### 5.2.2 数据迁移方案

1. **新增表**：queue_ttl_config 和 cleanup_audit_log 为新建表，无存量数据迁移
2. **元数据扩展**：message_metadata 表新增两个字段，使用 `ALTER TABLE ADD COLUMN` 在线变更，默认值填充，不阻塞读写
3. **TTL默认值初始化**：上线后通过运维脚本为全部约 1,200 个队列写入默认TTL配置（messageTTL=604800, protectionPeriod=3600）
4. **回滚方案**：若需回滚，queue_ttl_config 和 cleanup_audit_log 可直接删除；message_metadata 新增字段保留不影响原有逻辑
5. **数据校验**：迁移完成后检查 queue_ttl_config 记录数是否等于在线队列数，校验通过后启用扫描线程

## 6. 影响分析

| 影响范围 | 影响描述 | 应对措施 |
|---------|---------|---------|
| 对现有功能的影响 | 消费消息接口行为变更：过期消息将被自动跳过，消费者可能观察到消息不连续（offset跳跃）。查询队列详情接口响应结构新增字段。 | 消费侧新增响应头 `X-UMQ-Skipped-Expired` 告知跳过数量；队列详情接口新增字段为向后兼容的增量变更，旧版客户端忽略未知字段。 |
| 对现有场景的影响 | 部分业务方依赖消息的长期保留进行历史回溯，TTL清理可能误删这类消息。 | 保护期机制默认 1 小时缓冲；提供队列级 `cleanupEnabled=false` 开关，允许特定队列关闭自动清理；上线前通知各业务方确认队列TTL配置。 |
| 兼容性影响 | 新增 REST API 不影响现有接口签名。消费接口内部逻辑变更对 SDK 透明，但旧版 SDK（v2.3 以下）不识别 `X-UMQ-Skipped-Expired` 响应头。 | 响应头为可选信息，旧版 SDK 忽略无影响；建议在 Release Notes 中提示升级 SDK 以获得完整的过期消息感知能力。 |
| 性能影响 | 后台扫描线程在扫描期间会增加 MessageStore 的读IO，预估峰值增加约 15%；懒删除在消费路径上增加一次时间戳比较操作，耗时约 0.01ms/条。 | 扫描速率可配置，通过 `cleanupBatchSize` 和批间间隔控制IO占用；消费路径增加的比较操作对端到端延迟影响可忽略；上线前在预发环境进行 72 小时压测验证。 |

### 场景边界对齐结论

**纳入范围的场景：**

1. 队列消息超过TTL且无活跃消费者的自动清理场景（僵尸队列治理的核心场景）
2. 队列消息超过TTL但仍有消费者的懒删除场景（消费路径过期消息过滤）
3. 运维人员通过API手动触发特定队列清理的场景
4. 运维人员按集群维度配置TTL默认值和保护策略的场景

**明确排除的场景：**

1. 消费者主动确认（ACK）驱动的消息删除 —— 属于现有消费确认机制，不在本次TTL清理范围
2. 队列本身的自动销毁 —— 队列生命周期管理为独立需求，不在本期范围
3. 死信队列的TTL清理 —— 死信队列有独立的保留策略，本期不纳入

**边界判定依据：** 某交易系统运维团队确认当前痛点集中在僵尸队列的消息堆积，队列生命周期管理可后续规划。死信队列的保留策略由各业务方自行定义，不适合统一TTL。

### 收益预期对齐结论

**各方认可的收益指标：**

1. 存储空间释放：≥ 1.2TB（某交易系统运维团队基于实际僵尸队列数据评估，比需求阶段的 1.4TB 预估略保守，作为保底目标）
2. 集群存储利用率：从 82% 降至 60% 以下
3. 运维巡检时间：从每月 4 小时降至 30 分钟以内
4. 存储告警次数：每月减少 15 次以上

**度量方式：**

- 存储释放量：通过监控系统的集群存储指标前后对比
- 巡检时间：运维团队记录上线前后各 3 个月的巡检工时
- 告警次数：从告警平台导出上线前后各 3 个月的告警统计

**达成时间预期：** 全量上线后 30 天内完成首轮全量清理，60 天内收益指标稳定达标。

### 方案决策

| 决策项 | 决策结论 | 决策依据 |
|-------|---------|---------|
| TTL默认值 | 7 天（604,800 秒） | 某交易系统运维团队评估：生产环境中 90% 以上的正常消息在 24 小时内被消费，7天的TTL提供充足的缓冲期，既能清理僵尸消息又不影响正常业务 |
| 保护期默认值 | 1 小时（3,600 秒） | 为误配置场景提供紧急恢复窗口；运维团队确认 1 小时足够发现并修复配置错误 |
| 保护期下限 | 30 分钟（1,800 秒） | 防止业务方将保护期设置过短导致误删，30 分钟为强制最低值 |
| 技术方案选型 | 方案A（懒删除 + 后台扫描） | 实现复杂度低、风险可控，收益达成度满足预期 |
| 上线策略 | 灰度发布，默认关闭自动清理 | 安全优先，避免大规模误删；由运维团队逐集群开启 |
