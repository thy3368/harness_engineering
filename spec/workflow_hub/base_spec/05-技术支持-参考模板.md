# 技术支持环节 - 参考模板

| 元信息 | 说明 |
|--------|------|
| 适用环节 | 技术支持（售后/运维） |
| 涉及材料 | 事件回复单、技术支持报告、问题分析报告 |
| 质量要求 | L2-良好 |
| 引用规范 | 《产品价值表达统一规范》（SPEC-PV-001） |

> **核心定位：** 技术支持不只是解决问题，也是验证产品能力是否到位、文档指引是否充分的窗口。每个支持事件都值得反过来看：问题出在产品、文档还是用法？

---

## 子模板A：事件回复单

### 1. 基本信息

| 字段 | 内容 |
|------|------|
| 事件编号 | 【如 INC-YYYY-NNNN】 |
| 报告人/部门 | 【姓名及所属部门/团队】 |
| 报告日期 | 【YYYY-MM-DD】 |
| 产品/版本 | 【如 ProductX V3.2】 |
| 严重程度 | 【P1-紧急/P2-高/P3-中/P4-低】 |
| 当前状态 | 【已接收/分析中/已解决/已关闭】 |

> **严重程度定义：**
> - **P1-紧急：** 生产不可用，核心业务中断，无临时方案
> - **P2-高：** 核心功能受损，业务严重受限，有临时方案
> - **P3-中：** 非核心功能异常，业务可继续，有替代路径
> - **P4-低：** 轻微问题或改进建议，不影响业务

### 2. 价值维度分析

| 分析项 | 内容 |
|--------|------|
| 客户使用场景描述 | 【必填：什么业务场景下遇到的问题，含操作步骤、预期行为与实际行为的差异】 |
| 场景适用性判断 | 【必填：适用范围内 / 超出适用范围 / 边界模糊】 |
| 判断依据 | 【引用产品能力地图或场景导航中的定义】 |

> - **适用范围内：** 场景在产品设计覆盖范围内，产品应正确支持
> - **超出适用范围：** 场景超出产品设计意图，需引导客户理解产品定位
> - **边界模糊：** 场景处于产品能力边界，文档未明确覆盖

### 3. 问题描述

【详细描述问题：触发条件、错误表现、影响范围、复现步骤（如已确认）】

### 4. 原因分析

【技术根因：直接原因、根本原因、关联因素】

### 5. 解决方案

【临时措施、根本解决方案、客户操作指引】

### 6. 预防措施

【产品改进建议、文档完善建议、培训/知识库更新】

## 子模板B：技术支持报告（周期性报告）

### 1. 报告概览

| 字段 | 内容 |

### 2. 事件统计

#### 2.1 按严重程度分类

| 严重程度 | 事件数 | 已解决 | 处理中 | 平均解决时长 |
|----------|--------|--------|--------|-------------|
| P1-紧急 | | | | |
| P2-高 | | | | |

#### 2.2 按问题类型分类

| 问题类型 | 事件数 | 占比 | 典型事件编号 |
|----------|--------|------|-------------|
| 配置问题 | | | |
| 功能缺陷 | | | |
| 性能问题 | | | |
| 文档/指引不足 | | | |
| 使用方式不当 | | | |
| 其他 | | | |

### 3. 场景维度分析

> 将事件归类到产品能力地图中的能力域/场景，识别问题集中区域。

| 产品能力/场景 | 事件数 | 典型问题 | 改进建议 |
|--------------|--------|---------|---------|
| 【能力域名称】 | | 【最具代表性的问题】 | 【产品/文档/培训改进建议】 |

> 能力/场景名称与产品能力地图保持一致。难以归类的事件在备注中说明。

### 4. 趋势分析

【对比前一周期，分析：事件总量变化、严重程度分布变化、高频问题类型变化、场景维度分布变化、平均解决时长变化。】

### 5. 改进建议

【分类提出：
- **产品改进：** 需反馈到产品规划的功能/设计改进
- **文档完善：** 需补充或修订的内容
- **培训加强：** 需开展的培训主题
- **流程优化：** 支持流程本身的改进点】

## 子模板C：问题分析报告（深度分析）

### 1. 基本信息

| 字段 | 内容 |
|------|------|
| 报告编号 | 【如 PAR-YYYY-NNNN】 |
| 关联事件编号 | 【可多个，逗号分隔】 |
| 产品/版本 | |
| 分析人 | |
| 分析日期 | 【YYYY-MM-DD】 |

### 2. 问题描述

【结构化描述：
- 问题概述（一句话）
- 发生条件（触发场景、配置参数、负载条件等）
- 影响评估（范围、业务损失、数据影响等）
- 时间线（发现、升级、处理、解决的关键时间点）】

### 3. 根因分析

【建议用 5-Why 或鱼骨图等方法：
- 现象层：直接观察到的表现
- 技术层：导致问题的技术因素
- 设计层：产品设计或架构层面的不足
- 流程层：研发/测试/发布流程的疏漏
- 根本原因：一句话总结】

### 4. 价值闭环分析

> 从产品价值兑现角度审视根因，找出需要反馈到上游环节的改进点。

| 检查项 | 是否涉及 | 说明 |
|--------|---------|------|
| 根因是否涉及场景边界不清 | 【是/否】 | 【如"是"，指出能力地图或场景导航中缺失/模糊的定义】 |
| 根因是否涉及文档缺失 | 【是/否】 | 【如"是"，指出用户手册/配置指南中缺失的内容】 |
| 根因是否涉及收益未达预期 | 【是/否】 | 【如"是"，指出客户预期与实际的差距】 |
| 反馈建议 | -- | 【必填：向产品规划反馈的具体建议，含建议类型、内容、优先级】 |

### 5. 解决方案

【短期方案（已实施）、长期方案（计划实施）、实施计划、验证方法】

### 6. 预防措施

【产品层面、文档层面、测试层面、知识沉淀】

---

*支持事件中的改进建议应定期汇总反馈到产品规划。*
