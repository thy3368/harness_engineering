## 1. 产品定位

统一消息中间件 UMQ 是面向证券金融行业核心业务系统（交易、清算、风控）的企业级消息中间件，提供消息可靠投递、分区有序广播、全链路消息轨迹追踪及多协议接入能力，保障金融级业务消息的"不丢、不乱、可追溯"。

## 2. 价值表达三要素

### 2.1 解决什么问题（L3标准）

**问题一：核心业务消息丢失导致资金风险（P0）**

证券交易与清算中，业务消息（委托指令、成交回报、资金划拨通知）一旦丢失，直接造成资金差错或交易事故。使用通用开源消息中间件的券商系统，每年平均发生 3-5 次因消息丢失引发的资金差错事件，单次处理成本约 50 万元（含人工排查、资金追回、合规报告），极端情况可引发监管处罚。不解决的话，运营损失和合规风险将持续存在。

**问题二：消息乱序导致业务逻辑错误（P0）**

交易系统要求同一账户的委托、成交、撤单消息严格有序。通用消息队列在高并发场景（日均消息量超 5000 万条）下，消息乱序率约 0.3%-0.8%，导致下游风控误判、清算对账失败。当前每月因消息乱序产生的对账差异约 200-500 笔，每笔需人工核实，平均耗时 30 分钟。

**问题三：消息链路不可追踪，故障定位慢（P1）**

业务异常时，运维需要在多个系统间手动拼接消息流转路径来定位根因。平均故障定位时间 2-4 小时，交易时段内每多花 1 小时，潜在影响交易规模约 5000 万-2 亿元。缺乏端到端消息追踪能力是故障快速恢复的主要瓶颈。

### 2.2 适合什么场景（L3标准）

**场景一：证券交易指令传输（核心场景）**

- **目标用户：** 交易系统开发工程师、交易系统架构师
- **业务场景：** 投资者通过柜台/APP 下达委托指令，经交易前端接入后，需将指令消息可靠、有序地传递至撮合引擎、风控引擎、行情发布等下游系统。日均消息量 2000 万-1 亿条，峰值 TPS 10 万+。
- **使用前提：** 需部署 UMQ 集群（最少 3 节点），配置分区有序策略（按账户 ID 分区），启用同步双写模式。
- **为什么适合：** 分区有序广播保证同一账户消息严格有序，同步双写保证消息零丢失。

**场景二：日终清算批量消息处理**

- **目标用户：** 清算系统开发工程师、运维工程师
- **业务场景：** 每日收盘后，清算系统需在 2 小时窗口内完成全量交易数据归集、对账、资金清分。消息量 3000 万-8000 万条，要求高吞吐且不丢消息。
- **使用前提：** 需配置批量消费模式，建议消费端多线程并行处理，单分区消息保证顺序消费。
- **为什么适合：** 批量场景下吞吐量可达 80 万条/秒（单集群），支持消费进度精确回溯。

**场景三：实时风控事件流**

- **目标用户：** 风控系统架构师、风控开发工程师
- **业务场景：** 风控系统需实时接收交易事件流（委托、成交、持仓变动），在 5ms 内完成规则匹配并返回决策。要求低延迟、可靠投递、支持多消费组独立消费同一消息流。
- **使用前提：** 需启用低延迟模式（关闭批量聚合），配置独立消费组，建议风控系统与 UMQ 同机房部署。
- **为什么适合：** 低延迟模式 P99 延迟 < 2ms，支持多消费组广播。

**场景四：跨系统异步通知与事件驱动**

- **目标用户：** 后台系统开发工程师
- **业务场景：** 开户通知、资金变动通知、合规报送等非实时业务事件的异步传递，延迟容忍度秒级，但要求不丢消息、支持重试。
- **使用前提：** 标准配置即可，建议启用死信队列处理消费失败场景。
- **为什么适合：** 内置死信队列和消息重试机制，降低异步通知场景的开发复杂度。

**不适合的场景：**

- **超大规模日志采集（日均 50 亿条以上）：** UMQ 侧重消息可靠性而非极致吞吐，日志场景建议用 Kafka。
- **百万级 IoT 设备长连接：** UMQ 的连接管理模型针对服务端互联优化，大规模 IoT 场景建议用专用 IoT 消息平台。
- **微秒级超低延迟（P99 < 100us）：** 如高频撮合引擎内部通信，网络开销无法满足，建议用共享内存或 RDMA 方案。

### 2.3 带来什么收益（L3标准）

**收益一：消除消息丢失风险，降低资金差错损失**

- **量化指标：** 消息投递可靠性从 99.95%（开源方案）提升至 99.9999%（六个9）
- **业务价值：** 每年资金差错事件从 3-5 次降至 0 次，节省直接处理成本 150-250 万元/年，消除监管处罚风险
- **实现时间：** 上线即生效，首个完整季度后可全面评估

**收益二：消除消息乱序，减少人工对账成本**

- **量化指标：** 分区内消息乱序率从 0.3%-0.8% 降至 0%（严格有序保证）
- **业务价值：** 每月减少人工对账 200-500 笔，节省运维人力约 2-3 人/月，折合 8-12 万元/月
- **实现时间：** 上线即生效

**收益三：全链路追踪缩短故障定位时间**

- **量化指标：** 平均故障定位时间（MTTD）从 2-4 小时缩短至 15-30 分钟
- **业务价值：** 交易时段故障快速恢复，减少潜在交易影响约 80%；降低运维加班强度
- **实现时间：** 消息轨迹接入完成后 1 个月内可体现

**收益四：多协议统一接入，降低集成成本**

- **量化指标：** 消息集成方式从 3-5 种异构中间件统一为 1 种，新系统接入周期从平均 2 周缩短至 2 天
- **业务价值：** 降低中间件运维复杂度，节省运维成本约 30%-40%
- **实现时间：** 存量系统迁移完成后（预计 3-6 个月）全面体现

## 5. 选型指南

### 5.1 适用场景

- **金融级消息可靠性要求：** 消息零丢失是刚需，丢失会导致资金差错、合规风险或业务中断
- **消息有序性要求：** 同一业务实体（账户、订单）的消息需严格有序
- **全链路可追溯：** 需要对消息的生产、投递、消费全过程追踪和审计
- **多系统异构集成：** 需对接多种消息协议（AMQP、MQTT 等），希望统一中间件
- **金融监管合规：** 需要国密算法、消息审计等

### 5.2 不适用场景

- **超大规模日志/数据流（日均 50 亿条以上）：** 海量日志场景建议用 Kafka
- **百万级 IoT 设备长连接：** 建议用专用 IoT 消息平台（如 EMQX）
- **微秒级超低延迟通信（P99 < 100us）：** 建议用共享内存、RDMA 或 kernel bypass
- **简单进程间通信：** 同一主机两个进程间传少量消息，用 UMQ 过度设计了，用 Unix Domain Socket 即可

### 5.3 与同类方案对比

| 对比维度 | UMQ V3.2 | RabbitMQ 3.x | Apache Kafka 3.x |
|----------|--------|----------------|----------------|
| 定位 | 金融级可靠消息中间件 | 通用企业级消息代理 | 分布式流处理平台 |
| 消息可靠性 | 99.9999%（同步双写 + 事务消息） | 99.95%-99.99%（镜像队列） | 99.99%（ISR 副本） |
| 消息有序性 | 分区内严格有序（按业务键分区） | 单队列有序，多消费者需额外设计 | 分区内有序 |
| 消息追踪 | 内置端到端轨迹追踪 + 可视化面板 | 需 Firehose 插件 + 外部工具拼接 | 无内置，需外部 APM |
| 单集群吞吐量 | 80 万条/秒 | 5-10 万条/秒 | 200 万条/秒+ |
| P99 延迟（低延迟模式） | < 2ms | 1-5ms | 5-20ms |
| 协议支持 | AMQP、MQTT、自研高性能协议 | AMQP（原生）、MQTT（插件）、STOMP | 自研协议，Kafka Connect 生态 |

| 接入成本 | 金融行业 SDK + 最佳实践模板，2 天接入 | 社区文档丰富，1-3 天接入 | 需理解分区、偏移量等概念，3-7 天 |

| 典型短板 | 超大规模日志吞吐不如 Kafka；社区生态不如开源方案 | 高并发性能瓶颈；集群扩展能力有限 | 消息可靠性不如 UMQ；无内置有序广播；延迟较高 |

**选型建议：**

- 核心诉求是消息零丢失、严格有序、全链路追踪和金融合规 → **UMQ**
- 通用消息传递为主、性能要求适中、希望快速上手 → **RabbitMQ**
- 大规模数据流处理和日志采集、对吞吐有极高要求 → **Apache Kafka**

## 6. 技术原理概述

### 6.1 同步双写与消息零丢失机制

**核心思想：** 采用"同步双写 + WAL（Write-Ahead Log）"架构，消息在返回 ACK 之前必须持久化到至少两个独立存储节点。以牺牲部分写入吞吐量换取金融级可靠性。

**关键技术点：**

1. **WAL 预写日志：** 消息到达 Broker 后先写本地 WAL，再同步复制到副本节点 WAL。两份 WAL 都写成功才返回 ACK。WAL 采用顺序追加写入，磁盘 I/O 效率高。
2. **副本同步协议：** 基于 Raft 共识算法简化实现，单节点故障时消息不丢失。副本同步超时阈值可配（默认 500ms），超时后降级为异步并告警。
3. **事务消息：** 两阶段提交，生产者可将消息发送与本地数据库事务绑定。

**已知局限：**

- 同步双写下单分区写入吞吐约为异步模式的 70%（约 20 万条/秒 vs 28 万条/秒）
- 副本网络延迟 > 500ms 时降级为异步，存在极小的丢失窗口（约 500ms 的数据量）
- 事务消息的回查机制需要生产者端实现回查接口，增加了开发复杂度

### 6.2 分区有序广播机制

**核心思想：** 通过"业务键哈希分区 + 分区内顺序写入 + 消费者独占分区"三层机制，保证同一业务实体的消息全链路严格有序，同时通过多分区并行实现高吞吐。

**关键技术点：**

1. **业务键分区路由：** 生产者指定业务键（如账户 ID），通过一致性哈希路由到同一分区。扩缩容时仅约 1/N 的业务键需重新映射。
2. **分区内顺序写入：** 每个分区单线程顺序写入，消息按到达顺序分配严格递增的序列号。
3. **消费者独占分区：** 同一消费组内，每个分区仅分配给一个消费者，避免并发消费导致乱序。消费者故障时分区重新分配，从上次提交的消费位点继续。
4. **多消费组广播：** 不同消费组完全独立，各维护自己的消费位点，同一条消息可被多个消费组独立消费。

**已知局限：**

- 有序性在分区级别，跨分区无法保证全局顺序。需要全局有序只能用单分区，吞吐受限于 20-28 万条/秒
- 分区扩容会导致部分业务键映射变化，扩容期间（30 秒-2 分钟）可能短暂乱序。建议业务低峰期操作
- 消费者数量不应超过分区数，多余的消费者会空闲

### 6.3 端到端消息轨迹追踪

**核心思想：** 在消息的生产、Broker 中转、消费三个环节自动埋入轨迹数据（Trace Span），通过全局唯一 Message ID 串联完整链路。

**关键技术点：**

1. **轻量级埋点：** 轨迹数据以消息头扩展字段附着，不侵入消息体。每个 Span 记录时间戳、节点标识、处理耗时和状态码，约 200 字节/条。
2. **异步采集存储：** 轨迹数据通过独立异步通道采集，写入专用时序存储引擎，不影响消息主链路性能。支持按 Message ID、时间范围、生产者/消费者标识多维查询。
3. **可视化面板：** 管控台以时间轴形式展示消息在各节点的流转路径、耗时分布和异常标记，支持一键导出审计报告。

**已知局限：**

- 开启后消息写入延迟增加约 0.1-0.3ms（Span 序列化开销），极低延迟场景需评估
- 轨迹数据默认保留 7 天，超期自动清理。长期保留需配置外部归档存储
- 当前不支持跨集群消息链路串联，跨集群追踪需上层业务系统传递关联 ID

### 术语定义

| 术语 | 定义 |
|------|------|
| WAL（Write-Ahead Log） | 预写日志，消息在被正式处理前先写入的持久化日志，用于保证数据不丢失 |
| 分区（Partition） | 消息主题的逻辑分片，每个分区内消息严格有序，是并行处理和有序保证的基本单位 |
| 消费组（Consumer Group） | 一组协作消费同一主题的消费者实例集合，组内每个分区仅分配给一个消费者 |
| 消费位点（Offset） | 消费者在某个分区中已消费到的位置标记，用于断点续传和消费回溯 |
| 死信队列（Dead Letter Queue） | 存放多次消费失败的消息的专用队列，避免问题消息阻塞正常消费 |
| 事务消息（Transaction Message） | 支持与本地事务绑定的消息，保证本地事务与消息发送的原子性 |
| 同步双写（Synchronous Dual Write） | 消息同时写入主节点和副本节点，两者均确认后才返回 ACK |
| TPS（Transactions Per Second） | 每秒处理的事务数，衡量吞吐量的核心指标 |
| P99 延迟 | 99% 的请求在该延迟值以内完成，衡量尾部延迟表现 |
| ISR（In-Sync Replicas） | Kafka 中与 Leader 保持同步的副本集合，UMQ 中对应概念为"同步副本组" |
