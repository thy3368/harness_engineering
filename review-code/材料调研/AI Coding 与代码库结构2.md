# AI Coding 与代码库结构（金融行业）

## 场景信息

金融行业研发团队在既有代码库上引入 AI Coding（Agent 编码、Spec 驱动开发）的典型场景：AI 承担大量代码生成与改写，产出物直接进入会驱动资金、产生监管责任的核心系统。核心矛盾是——**如何在让 AI 高速产出的同时，守住"能上生产"的质量底线**。场景落点如下：

| 维度 | 场景描述 |
| --- | --- |
| 主体 | 金融行业研发团队（核心系统、账务/交易/风控等），在存量代码库上引入 AI Coding |
| 工作流 | 需求 → 可执行 spec（高级语言 DSL）→ AI 按 spec 生成/改写 → 质量门控 → 通过才上生产 |
| 代码库形态 | 多模块/微服务、分层清晰、依赖复杂、遗留系统与核心业务并存 |
| 核心约束 | 产出必须可解释、可回归、可审计；"生成即执行"不可行 |
| 上线判据 | 不是"Agent 写得快不快"，而是**门控是否全绿、spec 是否满足** |

一句话概括：金融场景的 AI Coding 不是让 Agent 自由写码，而是**以可执行 spec 驱动生成、以质量门控约束上线**——代码库结构要为此改造，把约束内建到仓库与管线里，让 Agent 在高压环境中安全作业。

## 影响分析

### 1. 代码库结构从"面向人"转向"面向人 + Agent"

- 仓库新增 `specs/`（唯一规则源，DSL 化的可执行 spec）、`AGENTS.md`、`CONSTITUTION.md`、`REVIEW.md`、`prompt-templates/` 等机器可读资产，形成"项目宪法 → 功能规格 → 审查清单"的约束链。
- README 从"给人看"变为 Agent 的上下文入口；上下文管理（分文件、分层记忆）成为代码库设计的一等公民。
- 沉淀为五类工程资产：规则、可执行 spec、提示词模板、契约、测试，各自有唯一存放位置，避免多份副本漂移。

### 2. 质量责任前移到"生成期"

- 代码库必须自带可执行判据（DSL spec + 契约 + 属性测试），让 AI 产出一开始就朝着可验收方向生成，而非事后补测。
- 生成代码天然"能通过测试、但不一定会在该失败时失败"，需变异测试（mutation testing）与静态校验兜底。
- 结论：**自动校验先于人工审查**，校验器是质量安全网，而非可选项。

### 3. 门控成为代码库/管线的一等结构

- 语法 lint → 架构门 → 功能测试 → 非功能测试，作为独立、可审计的闸门链嵌入 CI/CD，每道门都是"能否上生产"的判据节点。
- 门控全绿才上生产；任一失败回到生成/修改循环，形成闭环。


## 机会点

三个机会点构成一条完整闭环：**约束生成 → 把关上线 → 保障可解释**。可执行 spec 决定 AI 生成什么，门控决定什么能上生产，审计基座决定出了问题能否解释——三者缺一不可。

| 机会点 | 定位 | 一句话价值 |
| --- | --- | --- |
| 可执行 spec（高级语言 DSL） | 约束生成 | 让 AI 产出从一开始就朝可验收方向 |
| 门控（质量闸门） | 把关上线 | 门控全绿才允许上生产 |

### 1. 可执行 spec —— 约束 AI 生成什么

- **定义**：用高级语言 DSL（领域特定语言）表达、可被直接解析/执行/校验的规格，而非自然语言文档——自然语言只能被"读"，DSL 才能被"跑"。
- **形态**：契约 DSL（接口/数据契约）、属性测试与不变量、可执行约束断言（`assert position_limit_check(...)`）、形式化模型（如 TLA+）等。
- **在 AI 编码中的作用**：AI 按 spec 生成与改写，spec 即验收与门禁判据；执行中 spec 与代码不符时"先修 spec 再修代码"（Reverse Sync）。
- **金融价值**：一次编写，既能约束生成、又能自动化验收，可复用可回归。

### 2. 门控 —— 决定什么能上生产

- **定义**：一组自动化质量闸门，**门控全部通过才允许上生产**。
- **闸门链（自底向上）**：语法 lint → 架构门 → 功能测试 → 非功能测试。
- **在 AI 编码中的作用**：任一闸门失败即回到生成/修改循环，全绿才合流部署；是"能否上生产"的唯一判据。
- **金融价值**：把质量底线固化成可审计的结构，约束 AI 产出，防"为过而过的测试"。


### 三者关系与落地顺序

spec 是**标准**，门控是**裁判**，审计基座是**记录**：spec 越可执行，门控越有据可依；门控越严格，审计链越完整。建议落地顺序：**先做 spec + 门控**（解决"能不能安全用"），**再补审计基座**（解决"出了事能否交代"）。
