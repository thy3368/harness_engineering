一、背景与目标

起因：产品线要求支持 JDK 17，现有 SonarQube 版本无法适配，需部署新版 SonarQube。但升级涉及恒生规约插件、多分支插件等自研组件适配改造，改造成本高。技术平台才灵建议不再沿用 Sonar 老方案，推荐评估阿里开源的 Open Code Review。

决策：章总指示由黄华牵头，对代码扫描方案进行重新审视和技术选型，明确"哪些扫描由确定性工具做，哪些适合大模型"。

业务部门需求：调研中发现，财富部门（张森团队）已自发探索 LLM 驱动的业务逻辑代码扫描，章总此前看过其审查内容。说明纯静态扫描在业务逻辑层面存在系统性缺口，并非个别现象——这一需求是本次选型的重要输入。

目标：评估 Open Code Review 是否能替代或补充现有 SonarQube 方案，同时评估能否统一收敛各业务部门自研的 LLM 扫描工具，解决当前痛点并降低升级和维护成本。

二、业务部门对业务逻辑扫描的需求现状

章总明确指出："哪些扫描由确定性工具做，哪些适合大模型"是本次选型的核心问题。在调研中我们发现，多个业务部门已经自发探索了 LLM 驱动的业务逻辑代码审查，说明纯静态扫描在业务逻辑层面存在系统性缺口，这一需求并非个别现象。

2.1 财富部门：已自建 LLM 业务代码逻辑扫描工具

背景：财富部门张森团队基于 LLM 自研了一套业务代码逻辑扫描工具，已在部门内部使用。章总此前看过该工具的审查内容，评价为"有些用 Sonar 就行，有些是个人在本机上搞没必要集中"。

电话沟通确认（2026年8月）：与张森电话沟通后确认——

  • 财富工具确实是基于 LLM 做的业务代码逻辑扫描，与 OCR 技术方向一致
  • 张森表示他们也会评估 OCR，双方认为"确实有点像"
  • 后续路径：双方各自评估后对齐结论，重点对比规则覆盖度和审查质量
维度财富自研工具（张森团队）Open Code Review
技术方向 LLM 驱动业务逻辑扫描 确定性工程 + LLM 混合架构（方向一致）
生产验证 财富部门内部使用 阿里集团 2 年、2 万+ 用户、百万次审查
维护方式 依赖张森个人/小团队维护 开源社区持续维护，Apache-2.0 协议
规则管理 分散，缺少集中管控（章总评价"个人在本机上搞"） 四层优先级链（公司级→产品级→团队级→个人级），自动继承分发
CI 集成 需自研对接 原生支持 GitHub/GitLab/Gerrit/Bitbucket
Token 效率 未知（需对比评估） 通用 Agent 的 1/5~1/9
业务特定规则 可能有金融合规定制（金额精度、事务完整性、敏感数据脱敏等） 内置通用规则 + 自定义规则注入（需评估能否覆盖金融特定规则）

替换评估的关键问题：

  1. 规则覆盖度：财富工具有没有 OCR 不具备的金融业务特定规则？（如金额精度校验、事务完整性检查、敏感数据脱敏检查等）
  2. 审查准确率：财富工具的审查结果准确率如何？有没有做过标注对比？建议选 50-100 个 PR 做人工标注对比
  3. 改造成本：财富工具是否已接入效能平台/卡点平台？替换的对接改造量如何？OCR 输出标准 JSON 格式，对接成本相对可控

建议路径：双方各自评估后对齐结论，先做 2-3 周对比测试（同样的 diff 跑两个工具，对比 Precision/Recall），再决定是否替换。

2.2 纯静态扫描为何无法满足业务逻辑需求

章总提出"哪些扫描适合确定性工具，哪些适合大模型"——这个问题在业务部门已有答案：

适合确定性工具（SonarQube）适合 LLM Agent（OCR / 财富工具）
  • 代码覆盖率统计
  • 圈复杂度分析
  • 已知漏洞模式匹配（SQL 注入特征、XSS 特征）
  • 代码风格/规范检查
  • 技术债全景看板
  • 业务语义正确性判断（如转账金额是否校验 > 0）
  • 跨文件/跨模块数据流追踪（上游传 null → 下游 NPE）
  • 并发安全审查（锁顺序、死锁风险）
  • 上下文修复建议（不仅报位置，还给改法）
  • 增量 Diff 深度审查（PR 级实时审查）

核心结论：纯静态扫描的本质是"模式匹配"，做不到"语义理解"。大部分线上事故不是语法错误，而是业务逻辑错误——而业务逻辑审查恰恰是 SonarQube 的固有盲区，也是财富等部门自发探索 LLM 扫描的根本原因。OCR 的混合架构恰好把"理解代码意图并判断风险"交给 LLM，填补了这一缺口。

2.3 对选型的核心影响

  • 选型不只是"Sonar 还是 OCR"，还要考虑"已有业务部门自研 LLM 工具怎么办"
  • OCR 的四层规则优先级链（公司级→产品级→团队级→个人级）恰好解决章总说的"个人在本机上搞没必要集中"的问题——个人规则可注入但可追溯，集中规则自动继承
  • 如果 OCR 能覆盖财富等部门的业务特定规则，可以统一收敛为公司级标准方案，避免各业务部门重复造轮子
  • 如果不能完全覆盖，OCR 的自定义规则注入机制可以作为各业务部门业务特定规则的载体，统一平台 + 差异化规则

三、现有 SonarQube 方案五大痛点梳理

谢超从配管收集的问题归纳如下，按影响面排序：

痛点一：规则管理灵活性不足，制约多产品线定制需求

  • 规则配置仅支持公司级统一设定，各产品定制需人工逐条挑选并逐个 Sonar 项目手工配置，无法自动化继承与分发
  • 独立定制化需求只能单独部署 SonarQube 实例，运维成本高且资源重复建设

痛点二：扫描性能低下，影响开发交付效率

  • 仅恒生规约插件支持增量扫描，FindBugs 及核心引擎不支持，每次全量扫描，大型模块单次耗时约 1 小时
  • 社区版仅支持单线程处理分析报告，一个项目写入数据库期间其他项目全部排队
  • 无法满足"代码提交即触发"的 CI 卡点要求，只能降级为按日构建，问题发现滞后

痛点三：本地扫描与卡点扫描结果不一致

  • 开发本地通过 SonarLint/MCP 扫描需手动指定规则集，选错则"本地通过、卡点失败"频发
  • 要求用户明确指定 Sonar 项目名称才能保证一致，增加认知负担

痛点四：问题归因困难，影响问题闭环效率

  • 代码未修改却产出新问题，SonarQube 后台"新代码周期"判定逻辑不透明
  • 扫描问题无法定位到具体效能任务单，无法精准退回

痛点五：升级影响大

  • JDK 17 要求部署新版 SonarQube，涉及恒生规约插件、多分支插件适配改造
  • 效能平台、卡点平台取数逻辑同步升级，改造成本高、影响面大

4.3 核心架构：确定性工程 × LLM Agent 混合驱动

OCR 的核心创新在于将审查流程拆分为两部分——确定性工程负责"不能出错"的环节，LLM Agent 负责"需要理解"的环节：

Git Diff 输入
→
确定性工程
文件筛选 · 智能打包 · 规则匹配
→
LLM Agent
深度审查 · 上下文检索 · 缺陷判断
→
确定性工程
行级定位 · 评论反思 · 结果过滤
→
行级精度评论输出
确定性工程（硬约束）LLM Agent（动态决策）
  • 精准文件筛选：计算确定哪些文件需审查、哪些应过滤，确保不遗漏
  • 智能文件打包：关联文件（如中英文 properties）归并为同一审查单元，上下文隔离，天然支持并发
  • 细粒度规则匹配：基于模板引擎按文件特征匹配规则，消除信息噪声
  • 独立定位与反思模块：评论定位模块和反思模块独立校验位置和内容准确性
  • 场景化提示词：针对代码审查深度优化的 prompt 模板
  • 场景化工具集：从大规模线上数据沉淀的专属工具集
  • 动态上下文检索：读取完整文件、搜索代码库、对比多个变更文件
  • 深度审查判断：给出具体、有上下文的缺陷描述

4.6 规则管理：多层级配置

OCR 支持规则来源优先级，天然适配公司级 + 产品级分层管理：

优先级来源配置位置说明
1（最高）命令行指定--rule 参数临时覆盖
2项目级规则.opencodereview/rule.json提交到仓库，团队共享
3用户全局规则~/.opencodereview/rule.json个人偏好
4（最低）内置规则按文件类型自动匹配无需配置即可使用

项目级规则示例（.opencodereview/rule.json）：

{
  "rules": [
    {
      "path": "src/pay/**/*.java",
      "rule": "重点检查金额计算、错误处理和并发安全"
    },
    {
      "path": "**/*mapper*.xml",
      "rule": "检查 SQL 注入风险、参数错误和缺少闭合标签"
    },
    {
      "path": "src/**/*.{ts,tsx,js,jsx}",
      "rule": "检查 React Hooks 使用规范、TypeScript 类型安全、XSS 风险"
    }
  ],
  "exclude": ["**/generated/**", "vendor/**"]
}

五、逐条痛点对比：SonarQube vs Open Code Review

痛点一：规则管理灵活性不足

SonarQube 现状Open Code Review
  • 仅支持公司级统一规则，产品定制需逐项目手工配置
  • 独立需求需单独部署实例
  • 无规则集自动化继承与分发
  • 已解决 多层级规则配置：公司级 → 项目级 → 个人级，自动继承覆盖
  • 项目级规则文件 .opencodereview/rule.json 提交到仓库即生效
  • 无需额外部署实例，不同项目不同规则天然支持
  • 路径匹配 + 文件类型匹配双重过滤，灵活度高

痛点二：扫描性能低下

SonarQube 现状Open Code Review
  • 全量扫描，单次约 1 小时（大型模块）
  • 社区版单线程，项目间排队等待
  • 无法做 CI 卡点，只能按日构建
  • 已解决 天然增量扫描——基于 Git Diff，只审变更文件
  • 默认 8 路并发审查，文件打包后各 sub-agent 独立并行
  • 中等 PR 审查约 1-3 分钟，满足 CI 实时卡点
  • Token 消耗仅通用 Agent 的 ~1/9
  • 无需数据库，无排队等待问题

痛点三：本地与卡点扫描结果不一致

SonarQube 现状Open Code Review
  • 本地 SonarLint 需手动指定规则集，选错即不一致
  • 需明确指定 Sonar 项目名称
  • "本地通过、卡点失败"频发
  • 已解决 本地和 CI 使用同一份规则文件 .opencodereview/rule.json
  • 同一 CLI 工具、同一规则集、同一模型端点 → 结果天然一致
  • 无需指定项目名称，规则随仓库走
  • 委托模式（Delegation Mode）下甚至无需独立配置 API Key

痛点四：问题归因困难

SonarQube 现状Open Code Review
  • 代码未改却出新问题，判定逻辑不透明
  • 无法定位到效能任务单
  • 无法精准退回
  • 已解决 基于增量 Diff 审查——只看变更代码，未改不会报新问题
  • 行级精度评论，直接定位到具体代码行
  • JSON 格式输出，可对接效能平台实现任务单关联和精准退回
  • 每条评论含 severity（严重性）和 category（分类），支持路由策略

痛点五：升级影响大

SonarQube 现状Open Code Review
  • JDK 17 需部署新版 SonarQube
  • 恒生规约插件、多分支插件需适配改造
  • 效能平台、卡点平台取数逻辑需同步升级
  • 改造成本高、影响面大
  • 已解决 Go 编译二进制，无 JDK 依赖
  • npm 一键安装，无需部署服务端
  • 无数据库、无插件适配问题
  • 无 SonarQube 版本绑定问题
  • 但需对接 LLM 模型端点（需评估模型成本和安全合规）

业务逻辑扫描 不支持（模式匹配，无法理解业务语义） 原生支持（LLM 理解业务意图，可替代业务部门自研工具）
跨文件上下文 断裂（以文件为单位分析） 支持（动态上下文检索，追踪数据流）
修复建议 只报问题位置，无修复方案 报位置 + 给修复代码
数据安全 代码不外传，本地分析 需评估：代码 Diff 发送给 LLM 端点（可接私有部署模型；委托模式下不发送代码至第三方）
安全认证 — OpenSSF Gold + CodeQL 扫描 + Sigstore 签名
可观测性 内置 Web 仪表盘 OpenTelemetry 集成 + Session Viewer 会话回放

七、风险与限制

风险一：LLM API 成本与可用性

  • OCR 需配置 LLM 端点（OpenAI / Anthropic / 自建），每次审查产生 Token 消耗
  • 虽然 Token 消耗仅通用 Agent 的 ~1/9，但大规模使用仍需评估月度成本
  • 缓解措施：支持委托模式（复用已有编码 Agent 订阅，零额外 API 成本）、可接私有部署模型（如自建 Qwen/GLM 端点）

风险二：代码数据安全合规

  • 审查时代码 Diff 会发送至 LLM 端点，需评估是否符合公司数据安全要求
  • 缓解措施：OCR 仅发送变更文件的 Diff（非全量代码），可接公司私有部署的 LLM，数据不出内网；委托模式下 OCR 仅做文件选择和规则解析，审查由已有编码 Agent 执行，代码不经第三方
  • 需与安全团队确认模型选型和数据流向

风险三：召回率偏低（有意取舍）

  • OCR 的设计理念是"高精度、低噪声"，Recall 低于通用 Agent，可能漏报部分问题
  • 缓解措施：对于安全合规要求高的场景，可保留 SonarQube 做基线扫描，OCR 做增量深度审查，两者互补

风险四：缺少仪表盘与技术债管理

  • OCR 聚焦"增量审查 + 实时卡点"，不具备 SonarQube 的全量技术债看板、代码覆盖率、复杂度趋势等能力
  • 缓解措施：如需技术债全景看板，可保留 SonarQube 社区版做低频全量基线扫描（按周/月），OCR 做高频增量审查

风险五：项目成熟度

  • OCR 于 2026 年 5 月开源，社区生态仍在建设中
  • 阿里内部已验证 2 年，GitHub Stars 已达 18,000+，社区增长迅速
  • 已获 OpenSSF Best Practices Gold 认证，安全治理成熟度高
  • 缓解措施：Apache-2.0 协议可自主维护，不依赖上游更新节奏；可先在 1-2 个产品线试点

八、选型建议与实施路径

核心结论

Open Code Review 直接解决了现有 SonarQube 方案的五大痛点，特别是在增量扫描性能、规则多层级管理、本地/CI 一致性方面具有结构性优势。

关键认知：OCR 并非纯 LLM 工具，而是"确定性静态扫描 + LLM 语义审查"的混合架构。其内置确定性工程模块可完成文件筛选、规则匹配、行级定位等传统静态扫描能力（与 Sonar 重叠的部分），再由 LLM 在此基础上做业务语义理解、跨文件上下文追踪、修复方案生成——这是 Sonar 做不到的部分。换句话说，OCR 同时覆盖了"确定性扫描"和"大模型审查"两个维度。

但 OCR 不具备全量技术债看板、代码覆盖率、复杂度指标等工程化仪表盘能力——这些 Sonar 仍不可替代。

推荐方案：混合分层架构（OCR 为主 + SonarQube 为辅）

8.3 关于前端扫描插件升级的决策

建议：暂停前端 Sonar 扫描插件升级工作。

理由：

  • OCR 原生支持 JavaScript/TypeScript 扫描，内置 React Hooks、XSS、TypeScript 类型安全等前端规则
  • 如采用混合方案，前端增量审查由 OCR 负责，Sonar 仅做低频基线扫描，前端插件升级的紧迫性大幅降低
  • 如最终确认方案不变（不采用 OCR），再启动前端插件升级，联系李文博支持

前端插件升级的决策应等待选型结论后再定。

8.4 关于 JDK 17 升级引发的 Sonar 升级

如采用混合方案：

  • OCR 不依赖 JDK，JDK 17 升级对 OCR 零影响
  • Sonar 升级可降级为"按需升级"——仅当需要新版 Sonar 的基线扫描功能时才升级
  • 恒生规约插件、多分支插件的适配改造可暂缓，降低短期改造成本

8.5 关于业务部门自研 LLM 扫描工具的整合

背景：财富部门张森团队已自建 LLM 业务代码逻辑扫描工具，双方确认技术方向一致，后续各自评估后对齐结论。

场景处理方式理由
OCR 能覆盖财富业务特定规则 统一收敛为 OCR 公司级方案，财富部门特定规则迁移为 OCR 自定义规则 避免重复造轮子；四层规则优先级链天然支持业务部门差异；社区持续维护替代个人维护
OCR 不能完全覆盖金融特定规则 OCR 作为统一平台 + 财富特定规则通过 .opencodereview/rule.json 注入 统一平台 + 差异化规则；规则可追溯、可继承；财富部门不再独立维护工具
财富工具审查质量优于 OCR 财富工具继续使用，OCR 负责其他业务部门；后续评估是否将财富规则反哺 OCR 尊重已有积累；不强行替换；以审查效果为标准

建议行动：

  1. 对比测试（2-3 周）：选 50-100 个财富团队 PR，同样的 diff 跑 OCR 和财富自研工具，对比 Precision/Recall/审查质量
  2. 规则对齐：获取财富自研工具的规则清单，逐一比对 OCR 内置规则能否覆盖
  3. 各自评估后对齐结论：财富团队同步评估 OCR，双方交流评估结果后统一决策
  4. 其他业务部门：排查是否有类似自研 LLM 扫描工具的部门，统一纳入选型视野

8.6 LLM 模型选型与成本测算

OCR 需配置 LLM 端点，模型选型直接影响审查质量、成本和数据安全。三种方案对比：

方案 模型选项 成本参考 数据安全 适用阶段
方案A
私有部署		 自建 Qwen2.5-72B / GLM-4 / DeepSeek-V3 等 GPU 服务器成本（公司已有算力可复用），无按次计费 最优 代码不出内网 推荐试点
方案B
委托模式		 复用已有编码 Agent 订阅（Claude Code/Codex/Cursor） 零额外成本（复用已有订阅） 优 OCR 仅做文件选择，代码不经第三方 推荐试点
方案C
云端 API		 OpenAI / Anthropic / 阿里通义千问 API ~$0.01/次（GPT-4-mini）；DeepSeek 免费层零成本 需评估 Diff 发送至云端 仅适合非敏感项目验证

成本估算参考（方案A/C）：

  • 假设日均 200 个 PR/MR，每次审查消耗 ~5,000 Token（OCR 增量模式）
  • 方案A（私有部署）：复用已有 GPU 算力，月增成本≈电费+运维，边际成本趋近于零
  • 方案C（GPT-4-mini）：200 PR × 22 天 × 5,000 Token × $0.15/M ≈ $33/月（约 ¥240/月）
  • 方案C（DeepSeek 免费层）：免费，但有速率限制
  • 对比之前痛点：章总提到"技术平台给的 skill 扫代码很耗 token"——OCR 混合架构 Token 消耗仅通用 Agent 的 1/9，成本可控

建议：试点阶段优先用方案B（委托模式，零成本验证）或方案A（私有部署，数据安全最优），大规模推广时定方案A。

8.7 SVN 仓库处理方案

已知限制：OCR 依赖 Git >= 2.41 做 diff 生成、代码搜索和仓库操作，原生不支持 SVN。

方案处理方式能力保留适用场景
方案A
ocr scan 兜底		 SVN 仓库 checkout 到本地后 ocr scan .，不需要 Git 历史，可扫描任意目录 失去增量能力，仅全文件扫描 少量 SVN 仓库的历史代码审计
方案B
适配脚本		 SVN diff 输出转 Git diff 格式再喂给 OCR，定制一层适配脚本 保留增量审查能力 SVN 仓库需实时卡点
方案C
Sonar 兜底		 SVN 仓库继续用 Sonar 扫描，Git 仓库用 OCR 维持现状，不强行统一 推荐 务实方案

务实建议：如公司 SVN 仓库数量少且无实时卡点需求，方案C（Sonar 兜底）最简单；如有增量需求，方案B（适配脚本）开发量不大（SVN diff → Git diff 格式转换约 2-3 天开发量）。不必强求所有仓库统一工具。

8.8 效能平台/卡点平台对接方案

现有 Sonar 卡点依赖效能平台和卡点平台取数逻辑，OCR 替换后需对接改造：

对接项现有方式（Sonar）OCR 对接方式
审查结果输出 SonarQube 数据库 API 拉取 OCR JSON 输出（含 severity/category/行号/评论），直接在 CI 流水线中解析
MR 评论回贴 需自研适配逻辑 OCR 原生支持行级评论直接回贴 MR（GitLab/GitHub API）
卡点阻断 卡点平台从 Sonar 拉数判断 CI 中解析 OCR JSON，按 severity 过滤：critical/ blocker → 阻断合并
任务单关联 无法定位到效能任务单 OCR JSON 含 file + line + commit，可关联到具体提交 → 关联效能任务单 → 精准退回
SARIF 导入 不支持 OCR 支持 SARIF 输出，可导入 GitHub Code Scanning / 兼容 SARIF 的平台
数据可视化 Sonar Web 仪表盘 JSON → 效能平台报表；Session Viewer（ocr viewer）回放审查会话

改造量评估：OCR JSON 输出格式标准、结构清晰，对接改造量小于 Sonar 数据库迁移改造。建议阶段二（规则迁移）同步开发效能平台适配层，优先实现"MR 评论回贴 + 卡点阻断"两个核心能力。

8.9 回退方案与验收标准

回退方案

如 OCR 试点验证阶段不达标，按以下路径回退：

  • 回退触发条件：试点期间审查准确率 < 80%（误报率 > 20%），或 LLM API 成本超预算 2 倍，或安全团队不予通过
  • 回退动作：OCR 停用，恢复 Sonar 按日构建模式，前端插件升级重新启动（联系李文博），不影响现有流程
  • 风险可控：OCR 是"增量叠加"方案，不修改 Sonar 现有配置，回退只需关闭 OCR CI 步骤
阶段验收标准决策门槛不达标处理

  • 与财富工具对比测试有结论
