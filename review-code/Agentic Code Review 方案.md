# Agentic Code Review 方案

### 一、 整体目标

在研发提交代码后、测试开始前，通过让Agent同时阅读**“需求文档 + 设计文档 + 代码 + Git Diff”**，精准拦截业务逻辑缺陷。

*   帮助拦截研发未发现的研发问题
    
*   减少测试未覆盖到的场景
    
*   减少流入现场阶段的业务Bug。
    

---

### 二、 核心难点

**1. AI不懂恒生业务，人工复盘迭代没时间** 用开源进化机制，前提是得把规则和经验“教”给AI。但现实是：真实的业务规则极其复杂，很多是资深研发的“隐性经验”，根本无法完整地给开源工具说清楚；并且，一旦漏报了Bug，业务部门忙于迭代，**根本没有时间去长线复盘、分析原因再去调教AI**。这导致开源工具的“自进化”往往停滞不前。

**2. 探索路径多、Token 烧得快**

改了 A 处代码，可能导致 B 处业务崩溃。**AI 不懂产品全貌，只能广撒网式试探，探索路径长、Token 消耗高，深层关联仍容易漏。**需要底层的代码图谱与精准召回算法，让 AI 先懂产品、再顺藤摸瓜——探索路径更短，Token 更省，全局逻辑也看得更准。【有些可以通过完善AI资产库解决，有些仍然需要模型训练】

**3. AI报出大量的浅层bug**

**日常回流的报错反馈里，大量是无关紧要的噪声，大家早就麻了；真正能驱动进化的，是 关键 Bug 的缺陷反馈。**

*   AACR‑Bench （[https://github.com/alibaba/aacr-bench/tree/main](https://github.com/alibaba/aacr-bench/tree/main)）是**阿里巴巴开源、arXiv 2026 论文提出**，业界首个**多语言、仓库级（repository‑level）上下文的自动代码评审（Automatic Code Review, ACR）评测基准**，专门用来测评大模型做真实工程化代码审查的能力。

| 仓库级上下文 | 提供完整仓库上下文，但**没有做上下文粒度标注** | 核心亮点：每条真值评论标注**3 级上下文标签**<br>1.`Diff`仅看 hunk；2.`File`需要完整文件；3.`Repo`需要跨文件 / 全仓库上下文，专门衡量 Agent 跨文件检索能力 |
| 真值 (Ground Truth) 构建 | 原始 GitHub PR 评论，人工校验过滤；**没有 LLM 增强生成缺陷**；标注区分 “有问题 PR / 干净 PR”；5 位计算机研究生双标注，解决分歧arXiv | 原始 PR 评论 + **LLM 增强补全缺陷**（把 PR 里人类没发现的 bug 补出来，缺陷覆盖率提升 285%）；80 + 资深工业工程师双标注，分歧由专家小组裁定 |
| 设计侧重点 | **真实 PR 原始评论，不脑补额外缺陷；强于评估误报，适合评测传统静态 + LLM 评审** | **专门面向 Agentic Code‑Review**；大量需要读其他文件才能发现的缺陷；适合评测带工具调用、RAG 检索的 Agent 系统，就是 Open‑Code‑Review 配套评测集 |
| 缺陷来源 | 都是该 PR 内人类实际提出过的评审意见；不会生成原 PR 没有的 bug | 保留原始人类评论，同时**LLM 挖掘原 PR 没有被人类发现的隐性缺陷再人工核验**，真值更完备，但引入人工 + 模型合成样本 |

#### Agentic Code Review算法设计

【Loop】设计了一个主Agent+四个子Agent的模式。（先做静态文本review，等执行工具就绪，以工具形式加入到缺陷判别子Agent中，做动态测试review）

【工具】

（1）terminal执行工具，用于文件读写，grep查找等基础功能。

（2）测试造数工具，后期复用甄华春-测试造数工具。

（3）（等待基础建设）动态测试执行工具（输入测试数据+指定接口+测试用例，输出指定结构结果+日志）

【记忆-待定】初步思路：看看有没有历史缺陷（要强制格式化关键字段用于过滤+Memory Consolidation，重组需要使用D-Agent）作为参考，**采用动态few shot模式召回。**

【自进化模块设计-待定】初步思路：**沿用GAN的思路来做对抗，D-Agent使用优秀大模型来挑战，并生负样本/惩罚信号，G-Agent根据D的惩罚反馈生成经验记忆库，CR审查时按需召回（后续也可用作训练）。**

### 六、 论文关键结论参考

*   Code Monitor Red Teaming for Public-Test-Passing Code：这篇论文通过这套协议和压力测试揭示了一个冷酷的现实——**“通过了 CI 测试的代码 ≠ 安全/正确的代码”**。目前的弱 AI 验证器虽然能抓出一些低级错误，但在信息受限且面对擅长“应试”的代码生成器时，它们依然会放过大量的深层逻辑漏洞。要想解决这个问题，不仅仅需要更强的模型（如论文中提到 GLM-5.1 能挽回部分劣势），还需要在监控机制的设计上引入更深度的逻辑推理脚手架。
    
*   SWE-Review: Closing the Loop on Issue Resolution with Agentic Code Review：如果一个 Agent 像人类专家一样有清晰的直觉和规划，它很快就能找到代码的痛点并指出问题。相反，如果 Agent 缺乏这种“人类对齐”的直觉，它就会像无头苍蝇一样，不断地运行测试、疯狂抓取报错日志进行盲目的“过度验证”，这种行为轨迹最终大概率会导向失败的、或者充满幻觉的审查结果。工业界在采购或评测这类 Agent 时，需要把 **“达成成功 Review 所消耗的 Token 数/命令执行次数”** 作为核心指标，否则极其容易买到一个“虽然能找出 Bug，但能把公司破产的”高成本工具。
