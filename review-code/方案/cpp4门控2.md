# C++ 门控 4：负责接口、契约与数据兼容检查，拦截 API 签名变更、ABI 不兼容、返回值契约破坏、序列化协议非兼容变更，以及默认语义变化。


## 一、背景与目标

门控 4 管的是“别人已经依赖你的接口之后，你不能随手一改把别人搞崩”。

C++ 项目里，问题不只是在源码层面能不能编过。很多模块、动态库、服务、协议文件，都是被其他团队、其他进程、甚至线上老版本一起使用的。你删了一个函数、改了一个参数、调整了一个类的内存布局，自己这边可能编译通过，但依赖方一运行就崩。

所以这个门控要拦住几类高风险变化：

- API 签名被改了，调用方代码对不上。
- ABI 不兼容，老程序加载新库后运行出问题。
- 返回值契约变了，比如以前必须处理的结果被忽略。
- Protobuf 等序列化协议被改坏，老数据或老服务读不懂。
- 默认语义变了，接口名字没变，但行为和以前不一样。

一句话：门控 4 是为了防止“接口看起来只是小改，实际把上下游改崩”。

## 二、工具选型

| 维度 | 工具 | 大白话说明 |
|---|---|---|
| **ABI 兼容性** | abidiff（libabigail 2.4+） | 看新旧 `.so` / `.a` 的二进制接口有没有变坏，比如符号没了、函数签名变了、类型大小变了、虚函数表变了。它管的是“老程序还能不能安全加载新库”。 |
| **API/头文件兼容** | abi-compliance-checker / HeaderHunter | 看头文件里的公开接口有没有破坏性变化，比如函数参数、类布局、默认参数被改。它管的是“调用方重新编译时会不会炸”。 |
| **序列化协议兼容** | buf breaking（Protobuf） | 看 `.proto` 文件有没有做不兼容修改，比如字段编号改了、字段类型改了、rpc 签名改了。它管的是“新老服务、历史数据还能不能互相读懂”。 |
| **契约测试** | Pact-C++ | 让接口消费方把自己真正依赖的请求和响应写成契约，服务提供方每次改动都要验证。它管的是“接口实现有没有把调用方实际用法搞坏”。 |
| **返回值契约** | `[[nodiscard]]` + clang-tidy | 对必须处理的返回值打标记，再用静态检查拦住忽略结果的代码。它管的是“错误码、状态对象、optional 这类结果不能被随手丢掉”。 |
| **版本语义** | SemVer + cxx-abi 工具链 | 用版本号表达兼容承诺，再配合 ABI 检查结果做校验。它管的是“既然破坏兼容，就不能还假装只是小版本升级”。 |

## 三、ABI 兼容性检查流程

ABI 检查的核心做法很直接：拿主干上的老版本产物，和当前 MR 构建出来的新产物做对比。

```text
基线版本（main 分支最新 release .so）
        ↓ abidiff 对比
当前 MR 构建产物 .so
        ↓
变更分类：
  - Compatible（只新增符号，不影响老调用方）→ 通过
  - Incompatible（符号删除 / 签名变更 / 类型大小变化 / 虚函数表变化）→ 拦截，要求 bump SOVERSION
```

简单说：

- 只新增接口，一般可以放行。
- 删除老接口，要拦。
- 改函数参数、返回值、符号名，要拦。
- 改类或结构体布局，导致对象大小、字段偏移、虚函数表变化，要拦。
- 如果确实要破坏兼容，就要明确升级 SOVERSION，并同步更新说明文档。

## 四、Protobuf 兼容性规则（buf breaking）

Protobuf 最怕的是“字段表面还在，实际含义变了”。所以这里按老系统还能不能读懂来判断。

禁止的变更：

- 已经发布过的字段不能随便删。
- 字段编号（tag number）不能改，因为线上数据靠这个编号识别字段。
- 字段类型不能乱换，比如 `int32` 改成 `int64`、`string` 改成对象，都可能让老代码读错。
- 字段标签不能随便互转，比如 `required`、`optional`、`repeated` 之间乱改。
- `service` / `rpc` 方法签名不能随便改，否则调用方请求和响应会对不上。

如果字段不用了，优先走废弃流程，而不是直接删除或复用字段编号。

## 六、门禁阈值建议

### 6.1 分级拦截策略

| 等级 | 大白话叫法 | 典型问题 | 处理方式 |
|---|---|---|---|
| **Blocker** | 必须拦 | 编译失败、测试失败、ABI break、Critical 漏洞、安全 CVE | 立即拦截，禁止合入 |
| **Error** | 一般要拦 | clang-tidy error、cppcheck error、格式化不通过、覆盖率不达标 | 拦截，需修复或走豁免 |
| **Warning** | 新增要管 | 编译 warning（已升级为 error）、静态分析 warning | 做趋势管控，新增问题要拦 |
| **Info** | 只提示 | 建议性提示、代码风格偏好 | 不拦截，只展示给研发参考 |

### 6.2 门控 4 具体阈值

| 门控 | 拦截条件 | 豁免机制 |
|---|---|---|
| **4 接口契约** | abidiff 检测到 ABI break → 失败；buf breaking 检测到 Protobuf 非兼容变更 → 失败；Pact 契约不通过 → 失败 | ABI break 需同步 bump 主版本号并更新文档 |

这里的原则是：只要会让已发布接口的调用方、老二进制、老协议数据出问题，就不能静默合入。

## 七、落地口径

门控 4 不追求把所有接口变化都禁止掉，而是要求破坏兼容的变化必须被看见、被解释、被正确升级版本。

默认规则：

- 兼容新增，可以通过。
- 破坏兼容，默认拦截。
- 确认必须破坏兼容时，需要升级版本号、更新文档，并让依赖方有迁移预期。
