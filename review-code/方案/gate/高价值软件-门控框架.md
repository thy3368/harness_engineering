# AI coding之高价值软件门控系统

## 日抛软件与高价值软件的区别

在 AI coding 场景下，软件可以粗略分为两类：一类是日抛软件，一类是高价值软件。

日抛软件的核心目标是快速验证想法。它允许短周期试错，允许用临时代码换取速度，也允许在需求变化后直接重写。它通常不承载长期业务资产，不要求多人长期维护，也不需要持续演进几年甚至十几年。因此，日抛软件的质量策略可以偏轻：只要当前场景可运行、演示效果可接受、风险影响可控，就可以暂时接受结构不完整、测试不足、规范不统一的问题。

高价值软件不同。高价值软件通常承载核心业务流程、资金安全、客户生产环境、公司长期技术资产和组织协作效率。它不是一次性交付物，而是会被持续修改、持续集成、持续交付、持续运维的业务系统。此类系统一旦引入质量问题，影响不仅是单次功能失败，还会形成长期维护成本、架构腐化、测试负担、生产风险和后续 AI 开发的上下文污染。

AI coding 放大了两类软件之间的差异。AI 能快速生成大量代码，但生成速度不等于长期可维护性。对日抛软件而言，AI 生成代码即使存在局部不一致，也可能通过人工试用快速发现并丢弃。对高价值软件而言，AI 生成代码一旦缺少约束，就容易出现命名漂移、分层漂移、接口契约漂移、异常路径遗漏、测试基线缺失等问题。几轮需求之后，代码可能还能运行，但已经难以理解、难以测试、难以继续让 AI 正确修改。

因此，高价值软件不能只看“这次 AI 是否把功能写出来”，还必须看“这次变更是否仍然保持在系统的长期约束内”。门控系统的目标，就是把高价值软件必须长期遵守的约束显性化、自动化、流程化，让 AI 像一个需要被规范的开发人员一样，在编码过程中持续接受边界约束。

## 为什么高价值软件需要门控

高价值软件需要门控，不是因为开发团队不信任 AI，也不是因为要把研发流程复杂化，而是因为高价值软件的风险具有累积性和传导性。

第一，AI coding 的错误具有高频、低层、重复出现的特点。会议纪要中已经明确，当前优先要处理的是 AI 高频基础错误，例如要求未执行完全、恒真恒假分支、魔法数、接口未校验等。这类问题未必需要复杂语义推理，但如果没有硬门控，就会在每次生成、每次修改、每次提交中反复进入代码库。

第二，现有质量发现点明显偏后。9 大系统测试缺陷调研显示，缺陷大量集中在系统测试和集成测试阶段暴露，根因中实现错误占比最高，设计遗漏、需求错误/遗漏、设计与实现不符也占较高比例。这说明只依赖后置测试和人工评审，会让问题在开发链路后段集中爆发，修复成本高，定位成本高，也影响交付节奏。

第三，高价值软件的约束跨越文档、源码、测试和发布环境。单纯靠代码评审无法稳定覆盖需求完整性、架构边界、接口契约、Schema 兼容、测试基线、性能基线和发布制品一致性。门控的价值在于把这些约束分层管理：能计算的交给规则和工具，必须运行的交给测试，依赖语义判断的交给 LLM 辅助评审和人工确认。

第四，AI coding 要支持 long horizon task，必须控制漂移。长期在同一个项目中使用 AI 开发时，如果没有持续门控，AI 会逐步偏离原有架构、命名、模块边界和业务表达。短期看每次变更都像是局部可接受，长期看系统会失去统一性。门控的本质是为 AI 生成代码提供稳定轨道，让每次小变更都不破坏长期结构。

所以，高价值软件门控不是单个工具，而是一套研发质量约束体系。它既要能在开发阶段快速反馈，也要能在提交、合并、发布阶段形成卡点；既要覆盖确定性基础规则，也要逐步覆盖复杂语义风险；既要由公司统一建设公共能力，也要允许产品线补充业务特有规则。

## 门控的核心原则

- 源码是唯一事实

  高价值软件最终运行的是源码和构建产物，不是需求文档、设计文档或会议结论。需求和设计可以描述意图，但只有源码真正决定系统行为。因此门控必须以源码为最终验收对象，围绕源码结构、接口、测试和运行结果建立事实判断。

  这并不意味着忽视文档，而是要求文档约束最终能够落到源码事实上。例如架构设计中要求 use case 不直接访问数据库，门控就应转化为依赖规则检查；接口设计中要求错误码兼容，门控就应转化为契约测试或 Schema 兼容检查。

- 需求和设计是意图与约束

  需求和设计不是“事实”，但它们是判断源码是否正确的意图来源和约束来源。AI coding 常见问题不是语法不通，而是“看起来实现了，但没有按需求完整实现”“局部代码正确，但偏离设计边界”。因此，需求和设计需要被结构化沉淀，成为后续门控、测试生成和 LLM Review 的输入。

  在实践中，需求应至少明确业务规则、验收条件、异常路径和兼容要求；设计应至少明确分层边界、模块职责、接口契约、数据结构和关键非功能约束。否则后续的语义门控只能依赖人工经验，难以规模化复用。

- 优先计算型门控，后做概率型门控

  能用确定规则检查的问题，不应优先交给 LLM 判断。计算型门控结果稳定、可重复、可解释，适合作为硬拦截；概率型门控擅长理解语义和发现未知风险，但存在误报、漏报、解释不稳定和 Token 成本问题，更适合作为辅助评审和风险提示。

  当前阶段应优先建设公司级 Linter、编译构建、静态扫描、接口契约、测试基线等确定性能力。LLM Review 可以并行探索，但不应替代基础门控，更不应在规则尚未沉淀时直接作为大规模硬卡点。

- 优先左移，开发中反馈，提交前拦截，流水线兜底

  门控越靠后，修复成本越高。AI coding 的最佳反馈点不是合并后，也不是系统测试阶段，而是在 AI 生成代码后、开发者接受代码前、提交前。开发期反馈可以降低返工，提交前拦截可以避免低级问题进入仓库，流水线兜底可以保证统一基线。

  因此，同一条规则应尽量支持多处运行：IDE/本地命令用于即时反馈，pre-commit 或提交检查用于个人卡点，Merge Request/流水线用于团队卡点，发布流水线用于最终兜底。

- 公司统一规则 + 产品线扩展规则

  公司级规则负责通用、低争议、确定性强的问题，例如格式、命名、禁用 API、空指针风险、接口入参校验、模块依赖方向、测试覆盖率底线等。此类规则适合统一建设、统一治理、统一接入流水线。

  产品线规则负责业务域和技术栈差异，例如交易系统的资金不变量、订单状态流转约束、柜台接口兼容规则、特定中间件使用规范、历史客户环境兼容要求等。公司平台提供扩展机制和治理框架，产品线负责规则内容和业务解释。

## 门控的流程

- 开发期门控

  开发期门控面向 AI 生成代码后的即时反馈。它应尽量轻量、快速、可本地运行，重点覆盖 Lint、格式、类型检查、架构依赖、基础单测和常见缺陷模式。目标是在开发者采纳 AI 代码之前，就把明显错误暴露出来。

  例如，AI 生成 use case 时直接调用基础设施层数据库访问对象，开发期架构规则应立即提示分层违规；AI 新增接口但没有入参校验，Linter 或静态规则应直接提示；AI 修改 DTO 字段但没有同步契约测试，工具应提示接口契约风险。

- 提交前门控

  提交前门控是个人工作区进入代码库前的第一道硬卡点。它应覆盖低成本、高确定性的检查项，避免把基础问题交给后续流水线和评审人员处理。

  典型检查包括格式化、Lint、编译、受影响模块单测、依赖方向检查、敏感信息扫描、禁用写法检查等。对于 AI coding，可以额外增加“AI 高频错误规则包”，把历史缺陷中反复出现的基础错误固化为提交前规则。

- 合并前门控

  合并前门控面向团队共享分支，应比提交前更完整。它不仅检查当前提交是否局部正确，还要检查变更与主干代码、接口契约、模块边界和测试基线是否一致。

  合并前适合运行增量集成测试、契约测试、覆盖率差异检查、跨模块依赖检查、LLM 辅助 Review。LLM 在此阶段可重点检查需求实现覆盖、设计偏离、业务分支遗漏、异常路径遗漏等复杂语义问题，但建议先以提示和人工确认方式落地。

- 发布前门控

  发布前门控关注制品、环境和交付风险。它不是替代前面阶段，而是验证即将交付的版本是否满足生产可用条件。

  典型检查包括发布包一致性、制品清单完整性、部署冒烟、数据库脚本兼容、目标环境兼容、性能基线、安全扫描和回滚方案检查。缺陷调研中的 G9 类问题说明，发布、部署、环境类风险需要单独作为门禁管理，不能只归入代码质量。

- 线上缺陷反哺

  门控规则不能一次设计完成，应从线上缺陷、测试缺陷、人工 Review 问题中持续反哺。每个高频缺陷都应判断能否转化为门控：能规则化的进入 Linter 或静态扫描，能运行验证的进入测试基线，依赖语义判断的进入 LLM Review Prompt 或人工检查清单。

  反哺机制的关键是闭环：缺陷归因、规则设计、误报评估、灰度运行、硬卡点上线、效果复盘。没有闭环，门控会停留在“工具接入”；有闭环，门控才会逐步沉淀为组织级质量资产。

## 门控对象分层

### 文档型门控

文档型门控关注需求、设计和代码之间的意图一致性。它不应停留在检查“有没有文档”，而要逐步检查文档是否足够支撑开发、测试和评审。

- 需求

  需求门控重点检查业务规则是否明确、验收条件是否完整、异常路径是否描述、兼容要求是否说明、影响范围是否清楚。对高价值软件而言，需求缺失会直接传导为实现遗漏和测试遗漏。

- 架构设计

  架构设计门控重点检查模块边界、分层依赖、关键技术选型、数据流、状态流、错误处理、性能和安全约束是否明确。AI coding 场景下，架构设计还应提供可被工具识别的约束，例如允许依赖方向、禁止跨层调用、接口输入输出约定。

- 详细设计

  详细设计门控重点检查字段、分支、边界值、异常路径、状态迁移和接口细节。缺陷调研中详细设计评审阶段发现的问题占比较高，说明详细设计仍是发现复杂业务遗漏的重要环节。详细设计越结构化，后续测试生成、契约校验和 LLM Review 越有依据。

- 需求/设计/代码漂移检查

  漂移检查用于识别“文档说的是一套，代码实现是另一套”的问题。短期可通过 LLM 辅助分析需求、设计、diff 和测试用例之间的不一致；长期应把高频漂移模式转化为计算型规则，例如接口字段变更必须同步契约、状态枚举新增必须同步状态迁移测试、关键业务规则变更必须同步用例测试。

### 源码型门控

源码型门控是门控系统的主体，因为源码是唯一事实。源码型门控应同时覆盖代码规范、架构结构、功能正确性和非功能约束，形成从低阶确定性规则到高阶质量基线的分层体系。

- 语法规范 Lint

  Lint 是 AI coding 门控的第一优先级。它覆盖低争议、确定性强、适合硬拦截的问题，例如命名、格式、未使用变量、恒真恒假判断、魔法数、空分支、重复代码片段、接口入参未校验、禁用 API、日志和异常处理规范等。

  公司级 Linter 的价值不只是减少人工 Review 负担，更重要的是建立统一底线。AI 生成代码必须先通过这条底线，才能进入后续语义评审和测试验证。

- 领域架构规范

  领域架构规范用于保证代码结构长期可维护。AI 生成代码最容易为了局部功能绕过既有边界，例如把业务规则写进 Controller、让实体依赖基础设施、跨模块直接访问内部类、在用例层硬编码外部系统协议。此类问题短期能跑，长期会破坏可测性和可演进性。

    - 实体

      实体门控关注业务对象是否保持内聚，是否封装关键业务规则，是否避免依赖外部框架、数据库和远程服务。示例：订单实体只能表达订单状态和业务约束，不能直接调用行情服务或数据库 Mapper。

    - 用例

      用例门控关注业务流程编排是否清晰，是否通过接口依赖外部能力，是否具备可测试边界。示例：委托下单用例可以编排校验、风控、落单、通知，但不应直接拼 SQL 或直接依赖具体消息中间件客户端。

    - 接口

      接口门控关注 inbound/outbound 边界是否稳定，参数、返回值、错误码、超时、重试和兼容策略是否明确。示例：新增接口字段必须有默认值或版本策略，删除字段必须通过兼容性检查。

    - 分层

      分层门控关注依赖方向是否符合架构约束。典型规则是领域层不依赖基础设施层，应用层通过接口依赖外部能力，适配器层负责协议转换。此类规则适合用静态依赖分析硬拦截。

    - 分模块

      分模块门控关注模块职责是否清晰，是否存在越界访问和循环依赖。示例：交易模块不能直接访问资金模块内部表，应通过资金服务接口或领域事件协作。

    - 分子系统

      分子系统门控关注跨系统调用、数据同步、版本兼容和故障隔离。示例：柜台系统、投资系统、运营平台之间的接口变更，应通过契约测试和兼容性规则检查，而不是只依赖联调发现。

- 功能性

  功能性门控验证代码是否真正实现预期行为。它与 Lint 的区别在于，Lint 主要检查“写法是否合规”，功能性测试检查“行为是否正确”。

    - 单元测试

      单元测试优先覆盖实体、纯函数、用例内部规则和边界条件。AI coding 生成业务代码时，应同步生成或更新单元测试，尤其覆盖正常路径、边界值、异常输入和历史缺陷回归场景。

    - 集成测试

      集成测试关注模块之间、应用服务与基础设施之间的协作。缺陷调研中大量问题在跨模块集成测试暴露，说明接口契约、数据结构、状态联动和配置装配需要被更早、更自动化地验证。

    - E2E 测试

      E2E 测试关注完整业务流程，例如开户、委托、成交、清算、查询、撤单等端到端链路。它成本最高，不适合覆盖所有分支，但必须覆盖核心业务主路径和高风险回归路径。

- 非功能测试

  非功能测试用于保护高价值软件的生产可用性。AI 生成代码可能功能正确但引入性能退化、兼容性破坏、安全风险或可维护性下降，因此非功能约束也需要门控化。

    - 性能

      性能门控关注响应时间、吞吐、资源占用、延迟抖动和容量上限。示例：撮合、行情、风控、批量清算等高频或高容量场景，应设置性能基线，避免 AI 生成的低效循环、重复查询、无界缓存进入主干。

    - 兼容性

      兼容性门控关注操作系统、中间件、数据库、浏览器、客户现场版本、接口协议和数据结构演进。示例：数据库字段新增必须考虑默认值和升级脚本，消息结构变更必须兼容旧版本消费者。

    - 安全性

      安全性门控关注注入、越权、敏感信息泄露、日志脱敏、密钥管理和依赖漏洞。AI 生成代码容易遗漏权限校验和敏感字段处理，这类问题应尽量通过静态扫描、依赖扫描和安全测试前置发现。

    - 可维护性

      可维护性门控关注复杂度、重复度、模块耦合、公共抽象、命名一致性和测试可读性。它不能简单等同于代码风格，而是决定后续人和 AI 是否还能稳定理解并修改系统。

## 门控能力分型

### 计算型门控

计算型门控是指可以通过明确规则、程序执行、自动化测试、静态分析或度量指标完成的门控能力。它的特点是结果稳定、可重复、可解释，适合作为硬拦截。

计算型门控的优势是可规模化执行。只要规则定义清楚，同一项目、同一产品线、同一公司都可以重复使用，且结果不受评审人经验和模型输出波动影响。它适合承担质量底线：失败就是不能提交、不能合并或不能发布。

在 AI coding 中，计算型门控尤其重要。AI 可能每次都用不同写法完成相似任务，如果没有计算型约束，代码风格、依赖方向和接口约定会快速发散。计算型规则可以把“应该这样写”变成“只能这样过”。

典型能力包括：

- 编译
- Lint
- 类型检查
- 架构规则检查
- 单元测试
- 集成测试
- E2E 测试
- 覆盖率检查
- 性能基线检查
- 兼容性检查

典型示例包括：

- Linter 检查 AI 是否生成恒真恒假分支、未使用变量、空 catch、魔法数、禁用 API、接口入参未校验。
- 架构规则检查实体层是否依赖数据库访问对象、用例层是否绕过接口直接访问基础设施、模块之间是否出现循环依赖。
- 接口契约检查新增字段是否保持兼容、错误码是否符合约定、OpenAPI/IDL/Schema 与实现是否一致。
- 测试基线检查本次变更是否更新受影响模块单测、核心路径 E2E 是否通过、覆盖率是否低于团队底线。
- 性能基线检查关键接口 P95 响应时间、批处理耗时、内存占用是否相对基线退化。

### 概率型门控

概率型门控是指依赖 LLM 或其他概率模型进行判断的门控能力。它适合发现复杂语义问题、跨文档一致性问题、架构风险和潜在缺陷，但不宜在早期直接作为硬拦截依据。

概率型门控的价值在于处理难以形式化的问题。很多高价值软件缺陷并不是“代码违反某条固定语法规则”，而是“需求中的某个业务分支没有实现”“设计要求的异常路径没有覆盖”“代码虽然通过测试但状态流转不符合业务直觉”。这类问题需要理解上下文、比较文档、推断意图，正是 LLM 辅助评审可以发挥作用的区域。

但概率型门控不能被当作万能硬门禁。LLM 的判断会受到上下文完整性、Prompt 质量、模型版本、代码规模和领域知识的影响。它适合作为风险发现、人工 Review 辅助、规则沉淀来源，而不是在基础规则还未建立时直接承担核心卡点。

典型能力包括：

- LLM Code Review
- 需求/设计/代码一致性分析
- 缺陷模式挖掘
- 架构风险识别
- 复杂业务逻辑审查

典型示例包括：

- 对比需求、设计和 diff，识别 AI 只实现了正常路径但遗漏异常路径。
- 检查订单状态机变更是否破坏原有状态迁移语义。
- 根据历史缺陷模式提示本次改动可能缺少边界测试、回归测试或兼容说明。
- 对复杂模块重构进行架构风险识别，提示是否引入跨层依赖、职责混杂或隐性耦合。
- 在人工 Review 前生成高风险问题清单，让评审人员把精力放在语义和业务判断上。

### 计算型门控与概率型门控的优缺点及适用场景

- 计算型门控：适合规则明确、低误报、可自动执行、可硬拦截的问题
- 概率型门控：适合语义理解、风险提示、未知问题发现、辅助人工评审的问题

两类门控不是替代关系，而是先后关系和协作关系。计算型门控负责底线，概率型门控负责上限；计算型门控拦截已知问题，概率型门控发现未知风险；计算型门控适合直接卡点，概率型门控适合先提示、再沉淀、再规则化。

落地时应坚持一个原则：凡是 LLM Review 中反复发现、规则明确、误报可控的问题，都应逐步下沉为计算型门控。例如 LLM 多次发现“新增接口未校验必填字段”，初期可以作为 Review 提示，后续应沉淀为 Linter 或契约测试规则。这样概率型能力才不是一次性消耗 Token，而是持续产出组织规则资产。

## 落地优先级

### 第一阶段：公司级 Linter 硬门控

- 优先覆盖 AI 高频基础错误
- 优先建设低争议、确定规则、可自动化执行的检查项
- 公司统一建设通用规则
- 产品线补充业务与技术栈相关规则

第一阶段不追求大而全，重点是形成可见、可用、可硬拦截的最小闭环。公司级 Linter 应优先从 AI 高频基础错误入手，把当前人工 Review 和测试中反复发现的低阶问题前置到开发期和提交前。

建议优先规则包括：恒真恒假分支、空实现、未使用变量、异常吞噬、魔法数、重复代码、接口入参未校验、返回值未处理、空指针风险、资源未释放、日志未脱敏、禁用 API、敏感信息硬编码、测试断言缺失等。

治理方式上，公司统一维护基础规则包、接入方式、严重级别、豁免流程和统计看板；产品线维护业务规则包和技术栈扩展规则。规则上线应经历提示期、灰度期、硬拦截期，避免一次性引入大量误报影响研发节奏。

### 第二阶段：领域架构规则门控

- 分层规则
- 模块依赖规则
- 实体、用例、接口边界规则

第二阶段解决“代码能跑但结构变坏”的问题。AI coding 对高价值软件最大的长期风险之一，是为了完成局部需求而绕开既有架构边界。领域架构规则门控要把分层、模块、实体、用例、接口等结构约束转化为可检查规则。

优先落地的规则包括：领域层不得依赖基础设施层；Controller/Adapter 不承载核心业务规则；用例通过接口访问外部能力；跨模块只能访问公开接口；禁止循环依赖；禁止直接访问其他模块内部数据表；接口 DTO 与领域对象转换位置固定。

这部分规则应结合具体技术栈实现，例如通过依赖扫描、包路径规则、架构测试、编译期模块约束或自定义静态分析完成。它的目标不是限制实现自由，而是保证系统长期可测、可维护、可被 AI 持续理解。

### 第三阶段：测试与质量基线门控

- 单元测试
- 集成测试
- E2E 测试
- 覆盖率
- 性能基线

第三阶段解决“结构合规但行为未必正确”的问题。缺陷调研显示，运行测试类问题占比较高，尤其系统测试和集成测试是主要暴露阶段。因此，高价值软件必须建立分层测试基线，把核心行为尽量前移到自动化验证中。

单元测试优先覆盖领域实体、用例规则和纯业务判断；集成测试优先覆盖模块协作、数据库访问、消息交互和外部接口适配；E2E 测试优先覆盖核心业务主链路和历史高风险回归路径。覆盖率不应只看总量，还应关注关键模块、关键分支和本次变更影响范围。

性能基线应从核心接口和高频任务开始，不要求一次覆盖所有场景。对交易、行情、风控、批处理等高风险路径，应建立固定压测样本和退化阈值，防止 AI 生成的低效实现悄悄进入主干。

### 第四阶段：概率型辅助门控

- LLM Review
- 需求/设计/代码漂移分析
- 架构风险识别

第四阶段是在确定性门控稳定运行之后，建设概率型辅助能力。它的主要价值不是替代 Linter、测试和契约检查，而是覆盖当前难以规则化的语义问题。

LLM Review 应优先服务于人工评审效率：自动总结变更意图，指出需求覆盖风险、设计偏离风险、异常路径遗漏、测试缺口和架构风险。需求/设计/代码漂移分析可以先作为专项能力运行，用于发现高风险改动中的不一致，再把可重复模式沉淀为计算型规则。

这一阶段要谨慎设置硬卡点。建议先按“提示 -> 人工确认 -> 规则沉淀 -> 局部硬拦截”的路径推进。只有当某类 LLM 判断经过样本验证、误报可控、规则边界清楚时，才考虑转化为硬门控。
