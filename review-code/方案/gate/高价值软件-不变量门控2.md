# AI coding之不变量门控

## 不变量门控解决什么问题

AI coding 可以快速生成大量业务代码，但它并不天然理解哪些业务约束是绝对不能被破坏的。普通语法错误、格式问题、空指针风险可以通过通用 Lint 和测试发现；但高价值软件中更危险的问题，往往是代码能运行、测试也可能通过，却悄悄破坏了资金、交易、清算、风控或合规规则。

不变量门控要解决的，就是把这些“永远不能被打破”的业务约束显性化、结构化、自动化，并嵌入开发、提交、合并、发布和线上运行全过程。

对 AI coding 来说，不变量门控尤其重要：

- 防止 AI 为了完成局部功能绕过核心业务规则
- 防止多轮修改后状态机、资金流、接口契约逐步漂移
- 防止需求、设计、代码、测试之间只保持表面一致
- 防止重复调用、并发、异常恢复、补偿流程破坏核心业务事实
- 将业务专家、风控、合规沉淀的规则转化为可检查、可复用的工程资产

## 业务不变量的定义及相关方法论

### 业务不变量的定义

业务不变量是业务规则中“无论代码如何修改、流程如何重试、系统如何并发、异常如何发生，都必须始终成立”的约束。

它不是普通的校验条件，也不是某个测试用例里的预期结果，而是业务成立的底层事实。一旦被破坏，系统可能不会立刻崩溃，但会造成资金损失、账务不平、合规违规、客户权益受损或生产事故。

典型例子：

- 同一笔业务流水只能生效一次
- 一笔转账的出账金额必须等于入账金额与手续费之和
- 订单已完全成交后不能再撤单成功
- 清算结果不能重复入账
- 非合格投资者不能购买只面向合格投资者的产品

### 业务不变量与技术不变量

| 维度 | 技术不变量 | 业务不变量 |
|---|---|---|
| 关注对象 | 数据结构、类型、状态、引用完整性 | 资金、交易、清算、风控、合规 |
| 定义来源 | 架构师、开发团队、技术规范 | 业务方、产品、风控、合规、监管要求 |
| 常见表达 | 非空、唯一、状态枚举合法、依赖方向正确 | 资金守恒、幂等、额度限制、适当性、清算平衡 |
| 违反后果 | 程序异常、数据不一致、可维护性下降 | 亏钱、错账、重复扣款、违规、生产事故 |
| 门控方式 | Lint、类型检查、架构规则、单元测试 | 领域模型约束、属性测试、对账、契约测试、风控规则 |

两者不是割裂关系。很多业务不变量最终也要落成技术不变量，例如唯一索引、状态机、数据库约束、接口契约和自动化测试。但它们的出发点不同：技术不变量回答“程序结构是否正确”，业务不变量回答“业务事实是否仍然成立”。

### 不变量、规则、校验、测试用例的区别

- 不变量：长期成立的业务事实，例如“同一业务流水不能重复入账”
- 规则：对不变量的业务表达，例如“收到重复流水号时返回原处理结果”
- 校验：某个执行点上的防护动作，例如“入账前检查流水号是否已存在”
- 测试用例：对某个场景的验证，例如“重复提交同一流水，账户余额只变化一次”

不变量门控的重点不是把所有校验堆在一起，而是先识别核心不变量，再决定它应该在领域模型、数据库、测试、流水线、监控中的哪个位置被保护。

### 相关方法论

- 事件风暴：从业务事件中识别“事件发生前后必须成立”的事实
- DDD 聚合：把聚合内部必须一致的不变量收敛到聚合根保护
- 状态机建模：把订单、清算、审批等状态流转约束显式化
- 属性测试：用随机输入验证“任意情况下都必须成立”的性质
- 契约测试：保证系统间接口字段、错误码、幂等语义和版本兼容不漂移
- 对账机制：在运行时持续验证资金、交易、渠道、核心账之间的一致性
- 缺陷反哺：把线上事故、系统测试缺陷和人工 Review 问题沉淀为新不变量或新门控规则

## 金融领域常见业务不变量

### 资金类不变量

- 资金守恒：系统内资金总量不能凭空增加或减少
- 借贷平衡：会计分录中借方金额与贷方金额必须平衡
- 余额非负：账户余额不能低于允许的下限，除非业务明确支持授信或透支
- 重复扣款禁止：同一业务流水、支付单、清算单不能重复扣款
- 手续费一致：扣款金额必须等于入账金额、手续费、税费等金额项之和
- 冻结解冻一致：冻结金额、解冻金额、实际扣减金额之间必须可追溯且不超额

### 交易类不变量

- 订单状态合法流转：订单只能沿允许状态迁移，不能从终态回到处理中状态
- 成交数量约束：累计成交数量不能超过委托数量
- 撤单与成交互斥：已完全成交的订单不能再撤单成功
- 价格和数量边界：委托价格、数量、最小变动单位必须符合交易规则
- 买卖方向一致：交易方向不能在订单生命周期中被篡改
- 幂等处理：重复报单、重复撤单、重复回报不能造成重复业务效果

### 清算类不变量

- 先记账后清算或按系统约定顺序执行，不能出现逆序破坏
- 日终轧差必须平衡，差异必须为零或进入明确的差异处理流程
- 清算结果不能重复入账
- 清算批次、清算日期、业务流水之间必须可追溯
- 补偿、冲正、红冲不能造成资金重复变化

### 风控合规类不变量

- 超过额度的交易必须拦截或进入审批
- 命中黑名单、反洗钱名单、禁售名单的客户必须拦截
- 特定产品只能销售给满足适当性要求的客户
- 大额交易、敏感操作、权限变更必须留痕
- 用户只能操作自己有权限访问的账户、产品和业务单据
- 合规规则不能被普通业务参数或前端字段绕过

### 接口协作类不变量

- 请求幂等：同一业务请求重复发送，最终业务效果一致
- 消息有序：依赖顺序的业务事件不能被乱序消费后破坏状态
- 回执一致：外部渠道回执、内部订单状态、客户可见状态必须一致
- 版本兼容：接口新增字段、枚举、错误码不能破坏旧调用方
- 超时重试安全：网络超时、重试、补偿不能导致重复执行
- 外部系统差异可解释：渠道账、核心账、客户账之间的差异必须可定位、可追溯

## 不变量如何从需求进入源码

业务不变量如果只写在需求文档或会议纪要里，很容易在 AI coding 的多轮变更中丢失。有效的不变量门控，必须让不变量从需求进入源码、测试和运行时观测。

### 需求阶段

需求中应明确标出核心业务规则、异常路径、边界条件和合规红线。对高风险规则，应使用稳定编号管理，例如：

- INV-FUND-001：同一入账流水只能成功入账一次
- INV-ORDER-001：累计成交数量不能超过委托数量
- INV-CLEAR-001：清算批次不能重复入账

编号的价值在于后续可以关联设计、代码、测试、监控和缺陷。

### 设计阶段

设计阶段要决定不变量由谁保护：

- 聚合内部不变量，由实体或聚合根保护
- 跨聚合不变量，由用例、领域服务、Saga 或事务边界保护
- 跨系统不变量，由接口契约、消息协议、对账和补偿机制保护
- 运行时不变量，由监控、告警、熔断和人工处理流程保护

设计文档不应只描述流程，还应明确不变量的保护点、失败策略和恢复策略。

### 编码阶段

源码中应把不变量固化到稳定位置：

- 值对象：金额、费率、账号、日期等基础概念构造时校验
- 实体和聚合根：封装状态流转、余额变化、数量变化等核心规则
- 用例层：控制事务边界、幂等处理、跨对象一致性
- 数据库约束：唯一索引、外键、CHECK 约束作为最后防线
- 接口契约：明确字段兼容、错误码、幂等键、重试语义

AI 生成代码时，门控要重点检查它是否绕过了这些稳定保护点。

### 测试阶段

测试要围绕不变量组织，而不是只围绕正常流程组织：

- 单元测试验证实体和值对象的不变量
- 用例测试验证事务、幂等、状态流转和异常路径
- 集成测试验证数据库、消息、外部接口协作
- 属性测试验证任意输入下的资金守恒、数量边界、状态合法性
- 回归测试覆盖历史不变量缺陷

### 运行阶段

有些不变量无法只靠提交前检查完全保证，必须在线上持续验证：

- 实时或准实时对账
- 重复交易拦截统计
- 资金差异告警
- 清算批次异常告警
- 关键状态机异常迁移告警
- 灰度期间核心指标熔断

## 业务不变量分别适合放在哪些类型的门控中

### 开发期门控

开发期门控目标是让 AI 生成代码后尽快暴露不变量风险。它应轻量、快速、可本地运行。

适合放在开发期的检查：

- 实体和值对象单元测试
- 状态机测试
- 属性测试的小样本运行
- 架构依赖检查，防止绕过领域模型直接改表或改字段
- Lint 检查禁用 API、魔法数、硬编码状态、空异常处理
- 本地不变量规则扫描，例如“修改余额的方法必须经过账务服务”

### 提交前门控

提交前门控是个人工作区进入代码库前的硬卡点，适合覆盖低成本、高确定性的不变量检查。

适合放在提交前的检查：

- 受影响模块单元测试
- 幂等测试
- 状态流转测试
- 关键业务规则回归测试
- 唯一索引、数据库迁移脚本静态检查
- 不变量编号与测试用例关联检查
- 禁止直接操作核心账务表、订单状态字段、清算结果字段的规则检查

### 合并前门控

合并前门控面向团队共享分支，应覆盖跨模块、跨接口、跨文档的一致性。

适合放在合并前的检查：

- 集成测试
- 契约测试
- 关键业务 E2E 测试
- 覆盖率差异检查
- 需求、设计、代码、测试之间的不变量覆盖检查
- LLM 辅助 Review，重点检查异常路径、边界条件、状态迁移和业务规则遗漏
- 历史缺陷模式匹配，提示是否复现曾经的不变量破坏问题

### 发布前门控

发布前门控关注生产可用性，不替代前面阶段，而是验证即将发布的版本是否仍满足核心业务约束。

适合放在发布前的检查：

- 清算和对账演练
- 数据库升级脚本兼容性验证
- 回滚方案与补偿方案检查
- 性能基线检查，避免高频交易、批量清算、实时风控退化
- 灰度策略、熔断策略、监控指标检查
- 外部渠道、核心系统、运营后台之间的版本兼容检查

### 线上运行门控

线上运行门控本质是运行时不变量检查。它不能等价于普通监控，而是直接围绕业务事实建立指标。

适合放在线上的检查：

- 资金差异实时告警
- 重复流水拦截率异常告警
- 清算批次重复执行告警
- 订单异常状态迁移告警
- 渠道账、核心账、客户账对账差异告警
- 关键合规拦截规则命中和绕过监控
- 灰度期间核心不变量异常时自动熔断或回滚

## 计算型不变量门控与概率型不变量门控

### 计算型不变量门控

计算型不变量门控是可以通过明确规则、程序执行、静态分析、自动化测试或指标阈值稳定判断的门控。

适合做硬拦截的场景：

- 唯一索引缺失
- 状态枚举非法流转
- 单元测试或属性测试失败
- 接口契约不兼容
- 数据库迁移脚本破坏约束
- 关键表被非白名单模块直接修改
- 资金对账差异超过阈值
- 性能基线明显退化

计算型门控的优势是稳定、可重复、可解释，适合作为不变量保护的底线。

### 概率型不变量门控

概率型不变量门控依赖 LLM 或其他模型进行语义判断，适合发现难以形式化的不变量风险。

适合做辅助评审的场景：

- 需求写了业务规则，但代码没有实现
- 设计中定义了状态流转，但 diff 绕过了状态机
- 新增异常路径后没有补充补偿逻辑
- 业务规则从实体漂移到了 Controller 或基础设施层
- 测试只覆盖正常路径，没有覆盖重复请求、超时、并发和冲正
- 修改清算、交易、账务代码但没有说明影响哪些不变量

概率型门控不宜在早期直接作为硬拦截。更合理的方式是先做风险提示和人工确认，再把高频、明确、低误报的问题沉淀成计算型规则。

### 两类门控的协作关系

不变量门控应坚持“计算型守底线，概率型找风险”的原则。

- 已知、明确、低争议的不变量，用计算型门控硬拦截
- 复杂、跨文档、跨模块的不变量，用概率型门控辅助发现
- LLM 多次发现的同类问题，应沉淀为 Lint、架构规则、测试或契约检查
- 人工 Review 不应重复检查机器可以稳定判断的问题，而应聚焦业务语义、取舍和异常处置

## 不变量门控的落地优先级

### 第一阶段：识别并编号核心不变量

先从高风险业务域开始，不追求一次覆盖所有规则。

优先识别：

- 涉及资金变化的不变量
- 涉及客户权益的不变量
- 涉及交易状态的不变量
- 涉及清算入账的不变量
- 涉及合规和权限的不变量
- 历史生产事故和系统测试缺陷暴露过的不变量

每条不变量应有编号、业务解释、适用范围、违反后果和责任模块。

### 第二阶段：把不变量写进源码

将核心不变量落到稳定代码结构中：

- 值对象保护基础合法性
- 实体和聚合根保护内部一致性
- 用例层保护跨对象、跨服务流程一致性
- 数据库约束兜底唯一性和基础一致性
- 接口契约保护跨系统协作一致性

这一阶段的重点是避免不变量只存在于文档和口头知识中。

### 第三阶段：沉淀测试与 CI 门控

围绕不变量补齐自动化验证：

- 为每条核心不变量建立至少一个自动化测试入口
- 对幂等、状态机、金额计算、清算入账建立回归测试
- 将低成本测试放到提交前，高成本测试放到合并前或夜间流水线
- 将关键不变量失败设置为硬拦截

### 第四阶段：引入 LLM 语义审查

LLM Review 重点用于检查需求、设计、代码、测试之间的不变量漂移。

典型输入包括：

- 本次需求或设计说明
- 不变量清单
- 代码 diff
- 相关测试变更
- 历史缺陷模式

典型输出包括：

- 本次变更影响了哪些不变量
- 是否绕过了已有保护点
- 是否缺少异常路径、并发、重试、补偿测试
- 是否需要业务、风控或合规人工确认

### 第五阶段：线上监控与缺陷反哺

上线后持续验证不变量是否仍然成立，并把问题反哺回门控体系。

闭环流程：

- 线上异常或测试缺陷归因到具体不变量
- 判断是否已有门控覆盖
- 没有覆盖则补充测试、规则、监控或 Review Prompt
- 对误报、漏报和拦截效果做复盘
- 将成熟规则从提示升级为硬卡点

## 典型反模式与治理闭环

### 典型反模式

- 只在需求文档里写业务规则，源码中没有稳定保护点
- 只测正常路径，不测重复请求、并发、超时、补偿、冲正
- 把资金、订单、清算状态直接暴露给外部模块修改
- 依赖人工 Review 记住所有业务红线
- 用 LLM Review 替代确定性测试和静态规则
- 不变量失败只告警不阻断，导致规则长期失效
- 线上事故修完代码后，没有沉淀为新门控

### 治理闭环

不变量门控不是一次性建设，而是持续演进的质量资产。

有效闭环应包括：

- 不变量清单：明确编号、解释、责任模块和风险等级
- 保护点清单：明确每条不变量在源码、数据库、测试、监控中的落点
- 门控策略：明确哪些阶段提示、哪些阶段硬拦截
- 例外机制：高风险例外必须有业务、技术、风控或合规确认
- 度量指标：统计拦截次数、误报率、漏报率、线上缺陷反哺数量
- 规则演进：把高频人工判断沉淀为自动化规则

最终目标是让不变量从“少数专家脑中的经验”变成“源码和流水线共同守护的事实”。对于高价值软件，尤其是金融核心系统，不变量门控是 AI coding 从能写代码走向能长期维护核心业务系统的关键能力。
