## 业务不变量（Business Invariant）

### 一、定义

**业务不变量 = 业务规则中"永远不能被打破"的那些约束。**

通俗说：不管代码怎么改、需求怎么迭代、并发多高、异常怎么发生，有一些业务事实是"绝对不能变"的。一旦变了，就不是这个业务了，或者会出资金/合规事故。

它和"技术不变量"的区别：

| 维度 | 技术不变量 | 业务不变量 |
|---|---|---|
| 关心什么 | 数据结构、状态机、引用完整性 | 业务规则、合规要求、资金安全 |
| 谁定义 | 架构师/开发 | 业务方/风控/合规 |
| 违反后果 | 程序崩溃、数据不一致 | 亏钱、违规、监管处罚 |
| 例子 | "订单状态只能从待支付→已支付" | "同一笔交易不能被结算两次" |

### 二、金融核心系统的典型业务不变量

金融系统里这类约束特别多，因为直接管钱：

1. **资金守恒**：账户借贷必相等，一笔转账的扣款总额 = 入账总额 + 手续费，系统内资金总量不变。
2. **幂等性**：同一笔交易（用业务流水号标识）无论被调用多少次，最终效果只生效一次。重复扣款、重复结算都是违反不变量。
3. **余额非负（或不超透支额度）**：账户余额不能低于允许的下限。
4. **计息/费率约束**：利率不能超过法定上限，罚息计算基数不能包含罚息本身（复利禁区）。
5. **清算时序**：必须先记账后清算，不能逆向；日终轧差必须平衡。
6. **合规红线**：大额交易必须留痕、反洗钱名单必须拦截、特定产品只能卖给合格投资者。
7. **对账一致性**：核心账、客户账、渠道账三方必须对平，差异必须为零或在可解释范围内。

### 三、相关方法论

#### 1. 识别与建模：从业务规则中"提炼不变量"

- **事件风暴（Event Storming）**：把业务事件全部摆出来，找那些"不管事件怎么发生都必须成立"的断言。
- **领域驱动设计（DDD）中的不变量**：聚合根的核心职责就是保护其内部不变量，跨聚合的不变量用领域服务或Saga协调。
- **合规/风控规则反推**：监管文件、风控策略里写死的"禁止/必须"，几乎都是不变量。

#### 2. 编码落地：把不变量写进代码，而不是文档

- **断言（Assertion）**：在关键操作前后用 `assert` 或显式校验守住不变量。Java 里可用 `assert`，生产环境建议用显式校验 + 异常。
- **值对象（Value Object）**：把"金额""利率""账号"做成不可变值对象，构造时即校验，从源头杜绝非法值。
- **状态机封装**：状态流转逻辑收敛在领域模型内部，外部不能直接改字段。
- **数据库约束兜底**：唯一索引（防重复）、CHECK约束（余额非负）、触发器（复杂校验）作为最后一道防线。

#### 3. 测试保障：不变量是测试的"金矿"

- **不变量测试（Invariant Testing）/ 属性测试（Property-Based Testing）**：不写具体用例，而是写"对于任意输入，X必须成立"，然后让工具随机生成大量输入去暴力验证。Java 生态有 `jqwik`，Python 有 `hypothesis`。
- **混沌工程 / 故障注入**：在并发、超时、重试、宕机恢复等极端场景下，验证不变量是否仍然成立。金融系统尤其要测"重复请求""网络抖动后重试""主备切换"。
- **对账作为运行时不变量检查**：日终/实时对账本质就是在生产环境持续验证资金守恒不变量。

#### 4. 门控机制：在CI/CD中守住不变量

这正是你提到的"特殊类别门控"的落地方式：

- **静态分析规则**：自定义规则扫描代码，比如"修改账户余额的方法必须经过余额校验服务""直接操作账务表的SQL必须在白名单内"。
- **架构守护测试（ArchUnit）**：用测试断言"账务领域对象不能被非账务服务直接修改""不变量校验类必须被所有写操作调用"。
- **变更影响分析**：PR涉及不变量相关代码时，自动要求业务/风控评审，强制关联不变量编号。
- **灰度+实时监控**：上线后对不变量相关指标（对账差异率、重复交易拦截数）做实时告警，一旦偏离立即熔断。

### 四、一句话总结

> 技术不变量回答"程序对不对"，业务不变量回答"业务还是不是那个业务"。金融核心系统的门控之所以要单独拎出"业务不变量"这一类，是因为它违反了不会立刻崩，但会悄悄亏钱、违规——所以必须用建模、编码、测试、门控四层一起守。
