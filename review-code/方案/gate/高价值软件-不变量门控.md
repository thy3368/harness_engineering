# AI coding之垂直类门控-业务不变量

## 不变量门控解决什么问题

AI coding 可以快速生成大量业务代码，但它并不天然理解哪些业务约束绝对不能被破坏。普通语法错误、格式问题、空指针风险可以通过通用
Lint 和测试发现；高价值软件里更危险的问题，往往是代码能运行、测试也可能通过，却悄悄破坏资金、交易、清算、风控或合规规则。

不变量门控要解决的，就是把这些“永远不能被打破”的业务约束显性化、结构化、自动化，并嵌入开发、提交、合并、发布和线上运行全过程。

对金融核心系统而言，不变量门控的价值主要在于：

- 防止 AI 为完成局部功能绕过核心业务规则
- 防止多轮修改后状态机、资金流、接口契约逐步漂移
- 防止需求、设计、代码、测试之间只保持表面一致
- 防止重复调用、并发、异常恢复、补偿流程破坏核心业务事实
- 将业务专家、风控、合规经验转化为可检查、可复用的工程资产

## 业务不变量的定义

业务不变量是业务规则中“无论代码如何修改、流程如何重试、系统如何并发、异常如何发生，都必须始终成立”的约束。它不是普通校验条件，也不是某个测试用例里的预期结果，而是业务成立的底层事实。一旦被破坏，系统可能不会立刻崩溃，但会造成资金损失、账务不平、合规违规、客户权益受损或生产事故。

典型例子：

- 同一笔业务流水只能生效一次
- 一笔转账的出账金额必须等于入账金额与手续费之和
- 订单已完全成交后不能再撤单成功
- 清算结果不能重复入账
- 非合格投资者不能购买只面向合格投资者的产品

### 与技术不变量的关系

| 维度   | 技术不变量               | 业务不变量                  |
|------|---------------------|------------------------|
| 关注对象 | 类型、状态、数据结构、引用完整性    | 资金、交易、清算、风控、合规         |
| 定义来源 | 架构师、开发团队、技术规范       | 业务方、产品、风控、合规、监管要求      |
| 常见表达 | 非空、唯一、状态枚举合法、依赖方向正确 | 资金守恒、幂等、额度限制、适当性、清算平衡  |
| 违反后果 | 程序异常、可维护性下降         | 亏钱、错账、重复扣款、违规、生产事故     |
| 门控方式 | Lint、类型检查、架构规则、单元测试 | 领域约束、属性测试、对账、契约测试、风控规则 |

两者不是割裂关系。很多业务不变量最终也要落成技术不变量，例如唯一索引、状态机、数据库约束、接口契约和自动化测试。但它们的出发点不同：技术不变量回答“程序结构是否正确”，业务不变量回答“业务事实是否仍然成立”。

### 从不变量到门控规则

不变量、规则、校验和测试用例应保持层次清晰：

- 不变量：长期成立的业务事实，例如“同一业务流水不能重复入账”
- 规则：对不变量的业务表达，例如“收到重复流水号时返回原处理结果”
- 校验：某个执行点上的防护动作，例如“入账前检查流水号是否已存在”
- 测试用例：对某个场景的验证，例如“重复提交同一流水，账户余额只变化一次”

不变量门控的重点不是把所有校验堆在一起，而是先识别核心不变量，再决定它应该在领域模型、数据库、测试、流水线、监控中的哪个位置被保护。

常用方法包括事件风暴、DDD 聚合、状态机建模、属性测试、契约测试、对账机制和缺陷反哺。它们共同服务于一个目标：从业务事件、领域对象、接口协作和线上缺陷中提炼稳定事实，并转化为可执行的工程约束。

## 金融领域常见业务不变量

### 资金

- 资金守恒：系统内资金总量不能凭空增加或减少
- 借贷平衡：会计分录中借方金额与贷方金额必须平衡
- 重复扣款禁止：同一业务流水、支付单、清算单不能重复扣款
- 冻结解冻一致：冻结、解冻、实际扣减金额必须可追溯且不超额

### 交易

- 订单状态合法流转：订单只能沿允许状态迁移，不能从终态回到处理中状态
- 成交数量约束：累计成交数量不能超过委托数量
- 撤单与成交互斥：已完全成交的订单不能再撤单成功
- 幂等处理：重复报单、重复撤单、重复回报不能造成重复业务效果

### 清算

- 清算顺序必须符合系统约定，不能逆序破坏账务事实
- 日终轧差必须平衡，差异必须为零或进入明确的差异处理流程
- 清算结果不能重复入账
- 补偿、冲正、红冲不能造成资金重复变化

### 风控合规

- 超过额度的交易必须拦截或进入审批
- 命中黑名单、反洗钱名单、禁售名单的客户必须拦截
- 特定产品只能销售给满足适当性要求的客户
- 大额交易、敏感操作、权限变更必须留痕

### 接口协作

- 请求幂等：同一业务请求重复发送，最终业务效果一致
- 消息有序：依赖顺序的业务事件不能被乱序消费后破坏状态
- 回执一致：外部渠道回执、内部订单状态、客户可见状态必须一致
- 超时重试安全：网络超时、重试、补偿不能导致重复执行

## 不变量如何进入门控

业务不变量如果只写在需求文档或会议纪要里，很容易在 AI coding 的多轮变更中丢失。有效的不变量门控，必须让不变量从需求进入设计、源码、测试和运行时观测。

### 从需求进入源码

需求阶段应明确核心业务规则、异常路径、边界条件和合规红线，并使用稳定编号管理高风险规则，例如：

- INV-FUND-001：同一入账流水只能成功入账一次
- INV-ORDER-001：累计成交数量不能超过委托数量
- INV-CLEAR-001：清算批次不能重复入账

设计阶段要决定不变量由谁保护：聚合内部不变量由实体或聚合根保护；跨聚合不变量由用例、领域服务、Saga
或事务边界保护；跨系统不变量由接口契约、消息协议、对账和补偿机制保护；运行时不变量由监控、告警、熔断和人工处理流程保护。

编码阶段应把不变量固化到稳定位置：值对象保护金额、费率、账号、日期等基础概念；实体和聚合根封装状态流转、余额变化、数量变化；用例层控制事务边界、幂等处理和跨对象一致性；数据库约束作为最后防线；接口契约明确字段兼容、错误码、幂等键和重试语义。AI
生成代码时，门控要重点检查它是否绕过这些稳定保护点。

### 门控阶段映射

| 阶段  | 目标                 | 适合检查的不变量门控                                    |
|-----|--------------------|-----------------------------------------------|
| 开发期 | 快速暴露 AI 生成代码中的局部风险 | 实体和值对象单元测试、状态机测试、小样本属性测试、架构依赖检查、禁用 API 扫描     |
| 提交前 | 个人工作区进入代码库前的硬卡点    | 受影响模块测试、幂等测试、状态流转测试、数据库迁移静态检查、不变量编号与测试关联检查    |
| 合并前 | 验证跨模块、跨接口、跨文档一致性   | 集成测试、契约测试、关键 E2E、覆盖率差异、LLM 辅助 Review、历史缺陷模式匹配 |
| 发布前 | 验证即将发布版本仍满足核心业务约束  | 清算和对账演练、升级脚本兼容性、回滚与补偿方案、性能基线、灰度和熔断策略          |
| 线上  | 持续验证运行时业务事实        | 资金差异告警、重复流水告警、清算批次异常、订单异常状态迁移、对账差异、合规绕过监控     |

### 计算型与概率型门控

计算型不变量门控可以通过明确规则、程序执行、静态分析、自动化测试或指标阈值稳定判断，适合作为硬拦截。例如唯一索引缺失、状态枚举非法流转、单元测试或属性测试失败、接口契约不兼容、数据库迁移破坏约束、关键表被非白名单模块直接修改、资金对账差异超过阈值。

概率型不变量门控依赖 LLM 或其他模型进行语义判断，适合发现难以形式化的不变量风险。例如需求写了业务规则但代码没有实现，设计定义了状态流转但
diff 绕过状态机，新增异常路径后没有补偿逻辑，业务规则从实体漂移到 Controller，测试只覆盖正常路径，修改清算、交易、账务代码但没有说明影响哪些不变量。

两类门控应坚持“计算型守底线，概率型找风险”：已知、明确、低争议的不变量用计算型门控硬拦截；复杂、跨文档、跨模块的不变量用概率型门控辅助发现；LLM
多次发现的同类问题，应沉淀为 Lint、架构规则、测试或契约检查。

## 落地优先级

### 1. 识别并编号核心不变量

先从高风险业务域开始，不追求一次覆盖所有规则。优先识别涉及资金变化、客户权益、交易状态、清算入账、合规权限，以及历史生产事故和系统测试缺陷暴露过的不变量。每条不变量应有编号、业务解释、适用范围、违反后果和责任模块。

### 2. 把不变量写进源码

将核心不变量落到稳定代码结构中：值对象保护基础合法性，实体和聚合根保护内部一致性，用例层保护跨对象和跨服务流程一致性，数据库约束兜底唯一性和基础一致性，接口契约保护跨系统协作一致性。重点是避免不变量只存在于文档和口头知识中。

### 3. 沉淀测试与 CI 门控

围绕不变量补齐自动化验证：为每条核心不变量建立至少一个自动化测试入口；对幂等、状态机、金额计算、清算入账建立回归测试；将低成本测试放到提交前，高成本测试放到合并前或夜间流水线；将关键不变量失败设置为硬拦截。

### 4. 引入 LLM 语义审查

LLM Review 重点检查需求、设计、代码、测试之间的不变量漂移。典型输入包括本次需求或设计说明、不变量清单、代码
diff、相关测试变更和历史缺陷模式；典型输出包括本次变更影响了哪些不变量、是否绕过已有保护点、是否缺少异常路径/并发/重试/补偿测试、是否需要业务或合规确认。

### 5. 线上监控与缺陷反哺

上线后持续验证不变量是否仍然成立，并把问题反哺回门控体系。线上异常或测试缺陷应归因到具体不变量，再判断是否已有门控覆盖；没有覆盖则补充测试、规则、监控或
Review Prompt；成熟规则从提示升级为硬卡点。

最终目标是让不变量从“少数专家脑中的经验”变成“源码和流水线共同守护的事实”。对于高价值软件，尤其是金融核心系统，不变量门控是
AI coding 从能写代码走向能长期维护核心业务系统的关键能力。
