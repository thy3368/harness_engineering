## 有，这套 8 门控背后至少叠了 **5 套方法论**，我拆开说。

---

### 1. 左移测试（Shift-Left Testing）——最底层的逻辑

**核心法则**：缺陷越晚发现，修复成本指数级增长（1:10:100 法则）。

| 发现阶段 | 修复成本倍数 | 对应门控 |
|---|---|---|
| 编码时发现 | 1x | 门控1（IDE实时提示） |
| CI 编译时发现 | 10x | 门控2-4 |
| 测试环境发现 | 100x | 门控6-7 |
| 线上发现 | 1000x+ | 门控8（最后一道防线） |

**8 门控的本质就是把"能往左放的检查全往左放"**，能在写代码时发现的绝不拖到测试环境。

---

### 2. 测试金字塔（Test Pyramid）——决定每层放多少量

Mike Cohn 提出的经典模型：

```
        / 端到端测试 \        ← 少量、慢、贵（门控6、8）
       /  集成测试    \       ← 中量（门控6、7）
      /   单元测试     \      ← 大量、快、便宜（门控2）
     / 静态分析/lint    \     ← 全量、毫秒级（门控1、3、4）
    ─────────────────────
```

**门控的数量和顺序就是金字塔的映射**：越底层的检查跑的越频繁、覆盖越全；越顶层的检查越重、只在关键节点跑。

---

### 3. 纵深防御（Defense in Depth）——为什么要多层而不是一层

从安全领域借来的思路：**没有任何单层检查是 100% 有效的，多层叠加才能把逃逸率压到极低。**

举个例子：一个"空指针崩溃"要逃到线上，需要同时闯过：
- 门控2：编译器没报（`-Wnull-dereference` 没覆盖到）
- 门控3：Clang SA 没分析出来（路径太复杂）
- 门控5：OCR 语义审查没注意到
- 门控7：沙箱执行没复现这个分支

每一层拦截率假设 90%，四层叠加后逃逸率 = 0.1⁴ = **0.01%**。这就是多层门控的价值。

---

### 4. 按"缺陷引入阶段"分层——门控边界怎么划的

**缺陷是在哪个阶段引入的，就在哪个阶段拦截。** 这是门控边界划分的核心原则：

| 缺陷引入阶段 | 引入什么问题 | 对应门控 |
|---|---|---|
| 写代码时 | 命名乱、格式差、硬编码 | 门控1 |
| 编码/编译时 | 类型错、编译告警、没写测试 | 门控2 |
| 逻辑实现时 | 可疑比较、恒真分支、内存泄漏 | 门控3 |
| 接口设计时 | API 语义变了、返回值契约破坏 | 门控4 |
| 方案设计时 | 隐含语义变化、范围外修改 | 门控5 |
| 模块集成时 | 端到端链路不通 | 门控6 |
| 异常场景 | 特定数据组合才触发的 bug | 门控7 |
| 业务规则 | 客户透支、交易异常 | 门控8 |

**这就是为什么不能随便合并或拆分**——每个门控对应一个独立的"缺陷引入阶段"，阶段不同，检查手段和工具链就不同。

---

### 5. 检查手段正交性（Orthogonality）——为什么是 8 个不是 10 个

**正交 = 两种手段覆盖的缺陷类型不重叠。** 8 个门控用了 8 种本质不同的检查手段：

| 门控 | 检查手段 | 能不能被其他手段替代？ |
|---|---|---|
| 1 | 模式匹配（正则/AST） | 不能 |
| 2 | 编译器类型系统 + 测试执行 | 不能 |
| 3 | 数据流/控制流静态分析 | 不能 |
| 4 | 契约 diff / ABI 对比 | 不能 |
| 5 | LLM 语义理解 | 不能（确定性工具做不了） |
| 6 | 端到端集成测试执行 | 不能 |
| 7 | 沙箱动态实验复现 | 不能（静态分析发现不了） |
| 8 | 业务规则引擎/专项检查 | 不能（技术工具不懂业务） |

**手段穷尽了，就是 8 个。** 再多加一个门控，必然和现有某个手段重叠（比如把"安全"从门控3拆出来，还是用 SonarQube 那套规则，没有本质区别）。

---

### 一句话总结

> **左移决定"往前放"，金字塔决定"每层放多少"，纵深防御决定"要多层"，缺陷阶段决定"边界在哪"，正交性决定"一共几层"——五套方法论叠在一起，自然就推出了 8 个门控。**
