问题一：OCR Token 效率如何？

章工提问

结论：效率很高，是 OCR 混合架构的核心设计目标

为什么 OCR 省 Token？三个关键机制

通用 Agent 的问题

  • 把整个 diff 糊给 LLM，"什么都让 LLM 干"
  • 每次审查都重新构建完整上下文
  • 大 diff 容易超出 Token 上限
  • 对话式审查反复来回，Token 翻倍

OCR 的优化机制

  • 确定性工程前置：文件筛选、规则匹配、任务拆分由程序完成，只有"需要 LLM 理解的部分"才送大模型
  • 三层记忆压缩：冻结/压缩/活跃三区上下文管理，突破 Token 限制，不重复传上下文
  • 场景优化提示词：针对代码审查场景深度微调的 Prompt 模板，减少无效 Token 消耗
  • Goroutine 并发：子任务并行拆分，每个文件独立审查，避免上下文交叉膨胀

阿里内部验证规模：2 万+活跃用户，执行超 100 万次审查任务，采用率超 30%。Token 成本在生产环境中已验证可控。

一句话回应章工：OCR Token 效率是通用 Agent 方案的 1/5~1/9，建议接私有部署模型（如 DeepSeek），成本可控且数据安全。章总之前提到的"skill 扫代码很耗 token"的问题，OCR 的混合架构正是针对性解决方案。

问题二：支持 SVN 不？

章工提问
OCR 支持 SVN 不？
回应

结论：原生不支持，但有 workaround，不影响整体选型

OCR 的核心设计依赖 Git >= 2.41，通过 git diff 获取代码变更、代码搜索和仓库操作。这是其增量审查能力的基石，因此原生不支持 SVN。

SVN 仓库的两个应对方案

方案 A：ocr scan 全文件扫描

ocr scan . 全文件扫描模式不需要 git 历史，可以扫描任意目录。

  • SVN 仓库 checkout 到本地后直接运行
  • 失去增量能力，但能做全量代码审查
  • 适合存量代码审计、定期基线扫描
  • 零改造成本

方案 B：SVN diff 适配

将 svn diff 输出转换为 Git diff 格式，再喂给 OCR。

  • 保留增量审查能力
  • 需要定制一层适配脚本
  • 开发量不大（格式转换），但需维护
  • 适合仍有大量 SVN 仓库的场景

务实建议：先确认公司还有多少 SVN 仓库在活跃使用。如果 SVN 仓库已不多（大部分已迁移 Git），这部分继续用 Sonar 兜底即可；Git 仓库用 OCR。不必为少量 SVN 仓库强求统一方案，避免过度设计。

一句话回应章工：OCR 原生不支持 SVN（依赖 Git diff），但 SVN 仓库可用 ocr scan 全文件扫描兜底，或继续用 Sonar。不影响 Git 仓库的主流程选型。

问题三：财富张森大模型业务扫描可否替换？

章工提问

电话沟通结论（2026-08-06 与张森确认）：财富的工具确实是基于 LLM 做的业务代码逻辑扫描，技术方向与 OCR 一致。张森表示他们也会评估 OCR，双方认为确实有点像。下一步双方各自评估后对齐结论。

后续评估路径

双方各自评估 → 对齐结论，重点对比以下三个方面：

  1. 规则覆盖度：财富工具有没有 OCR 不具备的金融业务特定规则？不能覆盖的，能否通过 OCR 的自定义规则注入（四层优先级链）来补充？
  2. 审查质量对比：拿同样的 diff 跑两个工具，对比 Precision/Recall 和误报率。建议选 50-100 个 PR 做标注对比。
  3. CI 接入成本：财富工具是否已接入 CI 卡点？OCR 输出标准 JSON 格式，对接成本相对可控，但需要评估适配层开发量。

章总之前的核心关切

章总说："有些用 sonar 就行，有些是个人在本机上搞没必要集中。"——这句话揭示的问题恰恰是规则没有分层管理：

  • "有些用 sonar 就行" → 这些是确定性规则，Sonar 或 OCR 的确定性工程模块都能做
  • "个人在本机上搞" → 这些是个人定制的审查规则，没有集中管理，换人就丢了

OCR 的四层规则优先级链（公司级→产品级→团队级→个人级）恰好解决这个问题：集中规则自动继承，个人规则可注入但可追溯。财富自研工具如果缺少这个能力，替换为 OCR 是有价值的。

一句话回应章工：已与张森电话确认，财富工具确实是基于 LLM 做的业务代码逻辑扫描，与 OCR 技术方向一致，张森也认为"确实有点像"。双方将各自评估 OCR 后对齐结论。方向一致意味着替换的技术阻力不大，核心看规则覆盖度和审查质量的对比结果。

问题四：Sonar 和 OCR 都是怎么触发的？

章工提问
Sonar 和 OCR 都是怎么触发的？
回应

结论：Sonar 是定时任务（按日构建），OCR 是事件驱动（PR/MR 提交即触发）——OCR 正好解决了"发现滞后"的痛点

Sonar 触发方式

  • 定时任务（按日构建）：配置 cron 定时触发全量扫描
  • CI 流水线触发：Maven/Gradle 插件在构建时扫描
  • 手动触发：在 SonarQube Web 界面手动执行
  • 不支持增量：每次都是全量扫描
  • 问题发现滞后：白天写的代码，第二天才知道问题
  • 扫描耗时长：大型模块单次约 1 小时
  • 单线程排队：一个项目扫描时其他项目等待

OCR 触发方式

  • PR/MR 提交自动触发（事件驱动）
  • 评论触发重审：/open-code-review
  • 本地手动：ocr review（工作区变更）
  • 分支对比：ocr review --from main --to feature
  • 单提交审查：ocr review --commit abc123
  • 全文件扫描：ocr scan .（不需要 git 历史）
  • CI 定时兼容：也可配 cron 跑 ocr scan
  • 增量审查：只审 diff，1-3 分钟出结果

关键区别：Sonar 的定时全量扫描模式是"事后体检"——代码已经合并了，第二天才发现问题，还要回头修。OCR 的事件驱动增量扫描是"门禁检查"——代码合并前就拦住问题，从流程上卡住问题代码上线入口。

一句话回应章工：Sonar 是定时任务全量扫描（按日构建，问题发现滞后，约1小时/次）；OCR 是事件驱动增量扫描（PR/MR 提交即触发，1-3分钟出结果，可直接做 CI 卡点）。OCR 也能兼容定时模式（CI cron + ocr scan），但核心价值在于实时增量审查。

问题五：Sonar 哪些可以被 OCR 代替？

章工提问
Sonar 哪些可以被 OCR 代替？
回应

结论：不是全部替代，是分层互补。OCR 代替增量审查和安全检测（约 70%），Sonar 降级为低频基线扫描

逐能力对比

能力 Sonar OCR 结论
增量代码审查（PR 级） 不支持 天然增量 OCR 代替
已知漏洞检测（NPE/SQL注入/XSS/线程安全） 规则匹配 LLM + 规则 OCR 代替（更精准）
代码安全审查 支持 支持 OCR 代替
代码规范检查 支持 支持 OCR 代替
前端扫描（JS/TS/HTML/CSS） 新版不支持 LLM 天然支持 OCR 代替（解决前端插件问题）
跨文件上下文审查 不支持 支持 OCR 代替
修复方案建议 只报位置 报位置 + 给修复 OCR 代替
代码覆盖率统计 支持 不支持 Sonar 保留
圈复杂度分析 支持 不支持 Sonar 保留
重复代码检测 支持 不支持 Sonar 保留
技术债全景看板 支持 不支持 Sonar 保留
规则集自动化继承分发 不支持 四层优先级链 OCR 代替

对现有痛点的影响：

  • 前端插件升级→ OCR 天然支持 JS/TS，前端 Sonar 插件升级可暂停，等选型结论出来再定
  • JDK 17 升级影响→ OCR 是 Go 二进制，无 JDK 依赖，Sonar 降级为低频后升级紧迫性大幅降低
  • 扫描性能→ 高频审查走 OCR 增量（1-3 分钟），Sonar 全量扫描只在低频基线时跑
  • 本地/CI 不一致→ OCR 同一规则文件 + 同一 CLI，本地和 CI 天然一致

一句话回应章工：OCR 代替 Sonar 的增量审查、安全检测、代码规范、前端扫描部分（约占日常扫描 70%）；Sonar 降级为低频基线扫描，保留覆盖率、复杂度、重复代码、技术债看板（约 30%）。两者分层互补，不是替代关系。前端 Sonar 插件升级建议先暂停。

总结与行动建议

章工提问 核心回应
1. Token 效率 通用 Agent 的 1/5~1/9，建议接私有部署模型，成本可控数据安全

建议的下一步行动

  1. 暂停前端 Sonar 插件升级：OCR 天然支持 JS/TS，等选型结论出来再定，避免无效投入

  5. 制定分层方案实施计划：OCR 为主（高频增量）+ Sonar 为辅（低频基线），分阶段推广
