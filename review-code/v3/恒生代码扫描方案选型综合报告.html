一、业务触发背景（本次方案调研导火索）

1. JDK17 升级刚需

公司各产品线正批量推进 JDK17 版本升级，JDK8 已终止官方维护，存在长期安全漏洞风险；同时新版 SpringBoot3、Spring6 等主流业务框架强制依赖 JDK17，业务技术栈迭代刚需倒逼基础设施适配升级。

2. 旧版 SonarQube 无法适配

现有旧版 SonarQube 无法解析、扫描 JDK17 编译的业务代码，必须进行 SonarQube 大版本升级，由此引发全链路适配改造工作。

3. 当前适配现状

Java、C/C++ 语言自研扫描插件已完成新版本 Sonar 适配升级，仅前端扫描插件未升级，且新版 Sonar 暂无适配的前端扫描能力。

4. 行业趋势

业内多数企业已逐步淘汰传统 Sonar 纯静态扫描方案，传统方案架构老旧、迭代滞后，主流趋势转向确定性静态规则扫描 + 大模型 AI 代码评审的混合方案，代表工具为阿里开源 Open Code Review。

5. 业务部门已有探索

财富部门（张森团队）已自发探索 LLM 驱动的业务代码逻辑扫描，章总此前看过其审查内容。说明纯静态扫描在业务逻辑层面存在系统性缺口，并非个别现象——这一需求是本次选型的重要输入。

核心认知：OCR 并非纯 LLM 工具，而是"确定性静态扫描 + LLM 语义审查"的混合架构。其内置确定性工程模块完成文件筛选、规则匹配、行级定位（与 Sonar 重叠的能力），再由 LLM 在此基础上做业务语义理解、跨文件上下文追踪、修复方案生成（Sonar 做不到的能力）。以下先以矩阵一览七大痛点的破局结论，再逐条展开。

二、七大痛点矩阵（核心结论一览）

核心结论

OCR 的"确定性静态扫描 + LLM 语义审查"混合架构，不是逐条打补丁，而是从架构层面系统性解决了现有 SonarQube 七大痛点。每一条痛点的解决都不是"优化"，而是"消除"——规则管理从手动配置变为自动继承，扫描性能从小时级变为分钟级，本地/CI 一致性从"依赖人"变为"架构保证"，问题归因从"不透明"变为"行级+根因+修复方案"，JDK17 升级从"必须全链路改造"变为"零影响"，业务逻辑盲区从"完全不可检"变为"LLM 语义理解"，前端扫描从"等插件/自研"变为"LLM 天然支持"。

痛点 Sonar 现状 OCR 破局 本质变化
1. 规则管理 1 层统一，手动配置，定制需独立部署 4 层自动继承，JSON 随仓库管理 手动 → 自动
2. 扫描性能 全量 ~1h，单线程排队，每日定时 增量 1-3min，8 路并发，提交即触发 小时级 → 分钟级
3. 本地/CI 一致 手动选规则，选错则不一致 同一 CLI + 同一规则文件，天然一致 依赖人 → 架构保证
4. 问题归因 不透明，无根因，无修复，无任务单关联 行级精度 + 根因 + 修复方案 + JSON 输出 不透明 → 可追溯闭环
5. JDK17 适配 必须升级 Sonar + 适配插件 + 改造平台 零 JDK 依赖，Sonar 降级为可选 必须改造 → 零影响
6. 业务逻辑扫描 模式匹配，业务逻辑 bug 全漏，无修复方案 LLM 语义理解，识别业务缺陷 + 给修复代码 不可检 → 语义审查
7. 前端扫描 新版无插件，扫描真空，新框架永远滞后 LLM 天然支持 JS/TS/前端框架，零适配 等插件 → 原生支持

关键决策建议

  • 前端 Sonar 插件升级立即暂停——OCR 原生支持 JS/TS，等选型结论出来再定
  • Sonar 升级从"必须"变为"可选"——采用混合方案后，Sonar 降级为低频基线扫描，升级紧迫性消除
  • 先试点验证（2-3 周）——选 1-2 个产品线接入 OCR，对比准确率和误报率
  • 同步推进财富张森团队对齐——双方各自评估 OCR 后对齐结论，避免重复建设

01规则管理灵活性不足，多产品线定制成本极高

SonarQube 现状

  • 仅支持公司级统一扫描规则，无层级化规则集管理能力
  • 各产品线如需定制扫描规则，必须人工逐条筛选规则、逐个 Sonar 项目手动配置
  • 无法实现规则集的自动化继承、批量分发、差异化覆盖
  • 业务部门专属定制需求，只能通过独立部署一套 SonarQube 实例实现
  • 造成服务器资源重复建设、运维成本翻倍
Sonar 现状

公司级规则 → 手动配置到每个 Sonar 项目 → 产品定制需单独部署实例

OCR 方案

公司级规则 → 产品级规则自动继承 → 个人规则注入可追溯 → 零额外实例

OCR 解决方案：四层规则优先级链，自动继承 + 差异化覆盖

OCR 内置 四层规则优先级链（公司级 → 产品级 → 团队级 → 个人级），规则配置以 JSON 文件形式提交到代码仓库，自动继承分发，无需手动逐项目配置。

层级配置方式覆盖关系
公司级 全局配置文件，所有项目生效 基线规则，不可被覆盖
产品级 .opencodereview/rule.json 提交到产品仓库根目录 继承公司级 + 追加/裁剪产品规则
团队级 仓库子目录配置文件 继承上层 + 差异化覆盖
个人级 开发者本地 ~/.opencodereview/rule.json 仅本地生效，不污染团队规则

技术机制

  • 规则即代码：规则配置文件随代码仓库版本管理，有变更记录、可 Code Review、可回滚
  • 自动继承：子层级自动继承父层级规则，无需重复配置；子层级可追加新规则或关闭继承的特定规则
  • 差异覆盖：产品级可针对自身技术栈裁剪不适用规则（如前端项目关闭 Java 专属规则），无需额外部署实例
  • 自定义规则注入：支持通过 Prompt 注入业务特定规则（如金融合规检查），LLM 在审查时自动执行

定制成本逐项目手动配置 / 独立部署实例JSON 文件 随仓库管理
资源开销每个定制需求 = 1 套 Sonar 实例零额外实例
变更追溯数据库配置，无版本记录Git 版本管理

结论：OCR 的四层规则优先级链直接解决了"规则管理灵活性不足"问题——产品定制从"独立部署实例"降级为"提交一个 JSON 文件"，运维成本归零，变更可追溯。

02扫描性能薄弱，严重制约研发交付效率

SonarQube 现状

  • 仅自研恒生规约插件支持增量扫描，FindBugs 插件、Sonar 核心分析引擎均不支持增量模式
  • 每次代码扫描均为全量扫描，大型业务模块单次扫描时长可达 1 小时以上
  • 无法满足代码提交即扫描的 CI 流水线卡点要求，目前只能降级为每日定时构建扫描
  • 代码缺陷、规约问题发现严重滞后
  • 社区版仅支持单线程处理扫描报告，单项目占用数据库资源期间，其余所有项目扫描任务排队阻塞
Sonar 现状

全量扫描 ~1 小时 → 每日定时 → 问题次日才发现 → 单线程排队阻塞

OCR 方案

增量 Diff 审查 1-3 分钟 → 提交即触发 → 问题实时发现 → 8 路并发无阻塞

OCR 解决方案：基于 Git Diff 的天然增量 + 多路并发

OCR 的设计前提就是增量审查——它不扫描整个代码库，而是基于 git diff 只分析本次变更涉及的文件，再通过确定性工程模块做文件筛选和规则匹配，最后将"需要 LLM 理解的部分"送大模型。

维度SonarQubeOCR
扫描模式全量扫描（整库）增量 Diff（仅变更文件）
单次耗时大型模块 ~1 小时1-3 分钟 / PR
并发能力社区版单线程，排队阻塞8 路并发（可配置），无阻塞
触发方式每日定时构建提交即触发（PR/MR 事件驱动）
发现问题时机次日（滞后）实时（1-3 分钟内）
CI 卡点不支持（太慢）原生支持（可直接阻断合并）

技术机制：为什么 OCR 能做到 1-3 分钟？

  1. 文件级筛选（确定性工程）：先通过 Git Diff 拿到变更文件列表，自动过滤掉测试文件、配置文件、文档等无需审查的文件——不是所有 diff 都送 LLM
  2. 规则预匹配（确定性工程）：对变更文件先跑确定性规则匹配（如正则检测硬编码密钥、TODO 标记等），命中的直接出结果，不送 LLM
  3. 任务拆分 + 并发调度（确定性工程）：将需要 LLM 审查的文件拆分为独立任务，8 路并发发送，默认并发数 8（可配置）
  4. 三层记忆压缩（LLM 侧）：对大文件采用冻结/压缩/活跃三分区策略，Token 预算 MAX_TOKENS = 58,888，突破上下文窗口限制
  5. 只送 Diff 不送全量：LLM 只看变更行及其上下文，不是整个文件，Token 消耗仅为通用 Agent 的 1/5~1/9

性能基准（阿里内部生产数据）

指标SonarQube 社区版OCR提升
单次扫描耗时~60 分钟（大型模块）1-3 分钟20-60 倍
并发能力1 路（串行排队）8 路（可配置）8 倍
问题发现延迟T+1（次日）T+0（实时）从天到分钟
CI 卡点可行性不可行（太慢）可行（分钟级）从不能到能

结论：OCR 的增量架构从根上解决了性能问题——从"全量扫描 1 小时、每日定时、问题次日才发现"变为"增量审查 1-3 分钟、提交即触发、问题实时发现"，且支持多路并发无阻塞。这使得 CI 流水线卡点从"不可行"变为"原生支持"。

03本地扫描与CI卡点扫描结果不一致，沟通排障成本高

SonarQube 现状

  • 开发人员本地通过 SonarLint、MCP 工具扫描时，需手动选择、下载对应规则集
  • 人工选择错误即会出现"本地扫描通过、流水线卡点失败"的高频问题
  • 需开发人员手动熟记对应 Sonar 项目名称才能保证规则一致性
  • 提升了开发使用门槛，增加研发沟通、问题排障的冗余成本
Sonar 现状

本地手动选规则 → 选错则结果不一致 → 需记住项目名 → "本地通过、卡点失败"

OCR 方案

同一 CLI + 同一规则文件 → 本地/CI 天然一致 → 规则随仓库走 → 零认知负担

OCR 解决方案：同一 CLI + 同一规则文件 = 天然一致

OCR 的核心设计原则是"一套工具，一个规则文件，到处一致"。本地和 CI 用的是同一个 ocr CLI 工具，读的是同一份提交在仓库里的 .opencodereview/rule.json 规则文件——不存在"选错规则集"的可能。

维度SonarQubeOCR
本地工具SonarLint / MCP（独立工具）ocr review（与 CI 同一 CLI）
规则来源手动从 Sonar 服务端下载仓库内 JSON 文件（自动读取）
一致性保障依赖人工选择正确天然一致（同一文件）
认知负担需记住 Sonar 项目名零（cd 到仓库直接跑）
不一致概率高（人为出错）零（架构保证）

技术机制

  • 规则即代码：规则文件 .opencodereview/rule.json 随仓库提交，git clone 即拿到正确规则——无需从服务端下载
  • 同一 CLI：本地 ocr review 和 CI 中的 ocr review 是同一个二进制程序，执行逻辑完全一致
  • 同一 LLM 端点：本地和 CI 指向同一个模型端点，审查逻辑一致
  • 本地预览模式：开发者在提交前运行 ocr review 即可看到与 CI 卡点完全相同的审查结果，提前修复
  • 委托模式兼容：如果开发者本地已有编码 Agent（如 Cursor / Claude Code），OCR 可委托其执行审查，无需独立配置 API Key

第2步找到对应 Sonar 项目名（需记住）ocr review
第3步下载规则集到本地查看结果（1-3 分钟）

第5步运行本地扫描—
不一致风险高（选错即不一致）零（架构保证）

结论：OCR 从架构层面消除了"本地与 CI 不一致"的可能性——不是通过流程规范约束人，而是通过"同一 CLI + 同一规则文件"让不一致在技术上不可能发生。开发者从"记住项目名、手动下载规则、祈祷选对"变为"cd 到目录、跑一条命令"。

04问题归因困难，缺陷闭环效率低下

SonarQube 现状

  • 平台基于版本增量管控扫描问题，但存在代码无变更却新增扫描问题的异常场景
  • Sonar 后台"新代码周期判定、代码依赖传播分析"等核心逻辑不透明，技术团队无法快速定位问题根因
  • 扫描产出的代码缺陷无法关联具体效能任务单
  • 问题整改、退回追责无法精准落地，缺陷闭环链路断裂
Sonar 现状

判定逻辑不透明 → 无法定位根因 → 无法关联任务单 → 闭环断裂

OCR 方案

行级定位 + 根因解释 → JSON 结构化输出 → 关联 MR/任务单 → 精准退回

OCR 解决方案：行级精度 + 根因解释 + 结构化输出

维度SonarQubeOCR
问题定位精度文件级 + 行号（有时不准）行级精确 + 上下文引用
根因解释无（只报规则名和描述）LLM 生成根因说明
修复建议无（只报位置）LLM 生成修复代码
"幽灵问题"代码未变却新增问题（判定逻辑不透明）基于 Diff，未变更的代码不产生新问题
输出格式数据库存储，取数需适配标准 JSON / Terminal / SARIF
任务单关联无法关联JSON 含 MR ID / Commit / 文件 / 行号
问题退回无法精准退回MR 评论回贴 + 卡点阻断

技术机制

1. "幽灵问题"根治

Sonar 的"幽灵问题"（代码未变却新增问题）根源在于其"新代码周期"判定逻辑不透明——它可能因为依赖传播、分支合并、配置变更等触发重新分析。OCR 基于 git diff 工作，只审查变更的代码行，未变更的代码不会产生新的审查结果——从机制上消除了"幽灵问题"。

2. 行级精度 + 根因解释

OCR 的 LLM 不仅告诉你"第 42 行有问题"，还会解释为什么是问题：

{
  "file": "src/TransferService.java",
  "line": 42,
  "severity": "critical",
  "type": "business_logic",
  "title": "转账金额未校验正数",
  "description": "transfer() 方法接收 amount 参数未校验 > 0，允许负数转账",
  "root_cause": "调用方 AccountController.transfer() 直接透传用户输入，未做边界校验",
  "fix_suggestion": "在方法入口增加 if (amount <= 0) throw new BizException(...)",
  "affected_files": ["src/TransferService.java:42", "src/AccountController.java:78"]
}

3. 任务单关联 + 精准退回

  • MR 评论回贴：审查结果以行级评论直接贴到 MR 对话区，@提交者，提交者即时收到通知
  • JSON 结构化输出：包含 MR ID、Commit SHA、文件路径、行号、严重级别——可对接效能平台做任务单关联
  • CI 卡点阻断：critical 级别问题直接阻断 MR 合并，问题退回到提交者，闭环链路完整
  • SARIF 输出：可导入 GitHub Code Scanning，也可对接自研看板

结论：OCR 从三个层面解决了"问题归因困难"：① 基于 Diff 工作根治"幽灵问题"；② LLM 生成根因说明和修复方案，不再是"只报位置不给方案"；③ JSON 结构化输出 + MR 评论回贴，打通"发现→定位→通知→修复→退回→验证"完整闭环。

SonarQube 现状

  • 为适配业务 JDK17 升级，需强制升级 SonarQube 大版本

Sonar 现状

  • 恒生规约插件、多分支插件的适配改造可暂缓，降低短期改造成本
  • 从"被动式高成本改造"变为"主动式选型优化"——不是被 JDK 推着走，而是主动选择更优方案

06不支持业务逻辑扫描，缺陷检测存在结构性盲区

SonarQube 现状

  • SonarQube 本质是模式匹配工具——检查"代码是否符合已知规则"，而非"代码逻辑是否正确"
  • 能检测 SQL 拼接用户输入（模式），但检测不了"转账接口允许金额为负数"（业务语义）
  • 能报"B 文件有空指针风险"，但无法关联"A 文件传了 null"跨文件追踪数据流
  • 死锁、竞态条件、资源泄漏等运行时行为完全探测不到
  • 大量误报导致告警疲劳——开发者开始忽略所有告警，真正的问题被淹没
  • 只报位置，不给修复方案——开发还要自行判断"怎么改"
  • 大部分线上事故不是语法错误，而是业务逻辑错误——而这恰恰是 Sonar 的固有盲区
Sonar 现状

模式匹配 → 业务逻辑 bug 全漏 → 跨文件断裂 → 运行时盲区 → 高误报 → 无修复方案

OCR 方案

LLM 语义理解 → 识别业务逻辑缺陷 → 跨文件追踪 → 并发模式识别 → 低误报 + 修复代码

OCR 解决方案：LLM 语义理解填补业务逻辑审查盲区

OCR 的 LLM 不是"替代"确定性扫描，而是在确定性规则匹配之上增加一层语义理解——理解代码的意图、追踪数据流、识别业务逻辑缺陷，这正是纯静态扫描做不到的部分。

维度SonarQube（纯静态）OCR（确定性 + LLM）
能力本质模式匹配语义理解
业务逻辑缺陷完全漏报LLM 识别（理解代码意图）
跨文件上下文以文件为单位，数据流断裂跨文件追踪（理解调用链）
并发/死锁问题完全沉默LLM 识别模式
误报率高（无法区分上下文）低（理解数据来源和意图）
修复能力只报位置报位置 + 修复代码
新框架适应需写新插件（永远滞后）LLM 天然理解

技术机制：LLM 在审查中做的 5 件事

  1. 业务语义判断：理解"这是一个转账方法，应该校验金额 > 0"——不需要预置规则，LLM 从代码上下文推断业务意图
  2. 跨文件数据流追踪："getUser() 来自 selectById，可能返回 null → 调用方需要加 null check"——追踪调用链而非孤立分析单文件
  3. 并发模式识别："两个方法以相反顺序获取同一对锁 → 潜在死锁"——理解 synchronized 块的交互模式
  4. 可信源区分："userId 是 Long 类型来自内部系统" vs "userId 是 String 来自用户输入"——精准区分，降低误报
  5. 修复方案生成：不仅报问题，还给出"建议改为 PreparedStatement 参数化查询"的具体修复代码，可直接采纳

代码示例：同一段代码的双工具分析结果

// TransferService.java —— 看起来"合规"的生产代码
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountDao.debit(fromId, amount);   // 借方扣款
    accountDao.credit(toId, amount);    // 贷方入账
}
分析结果SonarQubeOCR
Issues 数量0（合规通过）3 + 修复方案
问题1：金额未校验正数未发现Critical：amount 未校验 > 0，允许负数转账
问题2：事务未保证原子性未发现High：debit 和 credit 非原子操作，中间异常导致资金不平
问题3：精度风险未发现Medium：BigDecimal 未指定 RoundingMode，除法可能抛异常
修复方案无给出加了校验 + 事务注解 + RoundingMode 的完整修复代码

SonarQube 报告 0 issues，代码"合规通过"——但它遗漏了三个会在生产环境引发事故的业务逻辑缺陷。这不是 SonarQube 的 bug，而是纯静态扫描的固有边界。

结论：业务逻辑缺陷是纯静态扫描的固有盲区，也是大部分线上事故的根源。OCR 的 LLM 语义理解恰好填补了这一缺口——不是在 Sonar 规则上打补丁，而是从"模式匹配"升级到"语义理解"。这也是财富等部门自发探索 LLM 扫描的根本原因：Sonar 满足不了业务逻辑审查需求。

07前端扫描插件缺失，新版Sonar无适配能力

SonarQube 现状

  • Java、C/C++ 语言自研扫描插件已完成新版本 Sonar 适配升级
  • 仅前端扫描插件未升级，且新版 Sonar 暂无适配的前端扫描能力
  • 前端代码（JavaScript/TypeScript/HTML/CSS）目前处于扫描真空期
  • 前端框架快速迭代（React Hooks、Vue3 Composition API、Next.js SSR），Sonar 规则永远滞后
  • 每出一个新框架、新语言特性，都需要有人写新规则/插件——永远在追赶
  • 即使升级，也只是适配当前框架版本，未来框架更新仍需持续投入
Sonar 现状

新版 Sonar 无前端插件 → 前端扫描真空 → 等社区/自研 → 新框架仍需适配 → 永远追赶

OCR 方案

LLM 天然理解 JS/TS/前端框架 → 无需插件 → 新框架零适配 → 前端插件升级可立即暂停

OCR 解决方案：LLM 天然理解前端，无需专用插件

维度SonarQubeOCR
前端扫描能力新版缺失，需等插件/自研原生支持，无需插件
JS/TS 支持依赖专用插件LLM 天然理解
React/Vue/Angular需各框架专用规则包LLM 读懂框架约定

技术机制：为什么 LLM 不需要前端插件？

  • LLM 在训练时"读过"海量 JavaScript/TypeScript 代码——包括 React、Vue、Angular、Next.js 等主流框架
  • 它理解框架的约定和最佳实践（如 React Hooks 规则、Vue3 Composition API 模式），不需要显式编码为规则
  • 新框架发布后，只要社区有代码示例，LLM 就能理解——不需要等扫描工具出插件
  • 自定义前端规则通过 .opencodereview/rule.json Prompt 注入，写一段 JSON 描述即可，不需要开发插件

关键决策：前端 Sonar 插件升级应立即暂停

  • 如果选型结论是采用 OCR（混合方案），前端 Sonar 插件升级完全没有必要——OCR 原生覆盖前端
  • 即使选型结论是保留 Sonar，前端插件的升级也需要等待社区或自研，周期长、成本高
  • 建议：在选型结论出来之前，暂停前端 Sonar 插件升级工作，避免投入后因方案变更而浪费
  • 前端代码扫描真空期可由 OCR 的 ocr scan 全文件扫描模式临时填补

结论：前端扫描插件问题是 Sonar"规则永远滞后于技术演进"的典型缩影。OCR 的 LLM 天然理解前端语言和框架，无需专用插件，新框架零适配。前端 Sonar 插件升级应立即暂停，等选型结论出来再定——如果采用 OCR，这笔升级投入可以完全省去。

改造量评估：OCR JSON 输出格式标准、结构清晰，对接改造量小于 Sonar 数据库迁移改造。建议阶段二同步开发效能平台适配层，优先实现"MR 评论回贴 + 卡点阻断"两个核心能力。

4.7 回退方案

回退触发条件：试点期间审查准确率 < 80%（误报率 > 20%），或 LLM API 成本超预算 2 倍，或安全团队不予通过。

回退动作：OCR 停用，恢复 Sonar 按日构建模式，前端插件升级重新启动（联系李文博），不影响现有流程。

风险可控：OCR 是"增量叠加"方案，不修改 Sonar 现有配置，回退只需关闭 OCR CI 步骤。

Q1
OCR Token 效率如何？
回应

结论：效率很高，是 OCR 混合架构的核心设计目标

对比维度 通用 Agent 方案（如直接让 Claude Code 审 diff） Open Code Review
Token 消耗 基准值（100%） 约 1/5 ~ 1/9（降低 80%~89%）
审查精确度（Precision） 较低（误报多） 显著更高（阿里官方基准）
平均审查时间 较慢 更短（1-3 分钟/PR）

为什么 OCR 省 Token？

通用 Agent 的问题

  • 把整个 diff 糊给 LLM，"什么都让 LLM 干"
  • 每次审查都重新构建完整上下文
  • 大 diff 容易超出 Token 上限

OCR 的优化机制

  • 确定性工程前置：文件筛选、规则匹配、任务拆分由程序完成，只有"需要 LLM 理解的部分"才送大模型
  • 三层记忆压缩：冻结/压缩/活跃三区上下文管理，不重复传上下文
  • Goroutine 并发：子任务并行拆分，避免上下文交叉膨胀

一句话回应：OCR Token 效率是通用 Agent 方案的 1/5~1/9，建议接私有部署模型（如 DeepSeek），成本可控且数据安全。章总之前提到的"skill 扫代码很耗 token"的问题，OCR 的混合架构正是针对性解决方案。

Q2
OCR 支持 SVN 不？
回应

结论：原生不支持，但有 workaround，不影响整体选型

OCR 的核心设计依赖 Git >= 2.41，通过 git diff 获取代码变更。因此原生不支持 SVN。

平台触发方式状态
GitHub ActionsPR 事件自动触发原生支持
GitLab CIMR 事件自动触发原生支持
Gerrit + JenkinsCI 流水线集成原生支持
Bitbucket PipelinesCI 流水线集成原生支持
SVN—不支持

SVN 仓库的两个应对方案

方案 A：ocr scan 全文件扫描

ocr scan . 不需要 git 历史，可以扫描任意目录。SVN 仓库 checkout 到本地后直接运行。失去增量能力，但能做全量代码审查。零改造成本。

方案 B：SVN diff 适配

将 svn diff 输出转换为 Git diff 格式再喂给 OCR。保留增量审查能力，需定制适配脚本。开发量不大，但需维护。

务实建议：先确认公司还有多少 SVN 仓库在活跃使用。如果 SVN 仓库已不多，继续用 Sonar 兜底即可；Git 仓库用 OCR。不必为少量 SVN 仓库强求统一方案。

一句话回应：OCR 原生不支持 SVN（依赖 Git diff），但 SVN 仓库可用 ocr scan 全文件扫描兜底，或继续用 Sonar。不影响 Git 仓库的主流程选型。

Q3
财富张森大模型业务扫描可否替换？
回应

电话沟通结论（2026-08-06 与张森确认）：财富的工具确实是基于 LLM 做的业务代码逻辑扫描，技术方向与 OCR 一致。张森表示他们也会评估 OCR，双方认为确实有点像。下一步双方各自评估后对齐结论。

维度财富自研工具（张森）Open Code Review
技术架构 基于 LLM 的业务代码逻辑扫描 确定性工程 + LLM Agent 混合架构
方向一致性 技术方向一致，双方确认"确实有点像"
生产验证 财富部门内部使用 阿里集团 2 年、2 万+用户、百万次审查

CI 集成 需自研对接 原生支持 GitHub/GitLab/Gerrit/Bitbucket

后续评估路径——双方各自评估 → 对齐结论：

  1. 规则覆盖度：财富工具有没有 OCR 不具备的金融业务特定规则？不能覆盖的，能否通过 OCR 的自定义规则注入来补充？
  2. 审查质量对比：拿同样的 diff 跑两个工具，对比 Precision/Recall 和误报率。建议选 50-100 个 PR 做标注对比。
  3. CI 接入成本：财富工具是否已接入 CI 卡点？OCR 输出标准 JSON 格式，对接成本相对可控。

章总说："有些用 sonar 就行，有些是个人在本机上搞没必要集中。"——OCR 的四层规则优先级链恰好解决这个问题：集中规则自动继承，个人规则可注入但可追溯。

一句话回应：已与张森电话确认，财富工具基于 LLM 做业务代码逻辑扫描，与 OCR 方向一致。双方各自评估后对齐结论。方向一致意味着替换技术阻力不大，核心看规则覆盖度和审查质量的对比结果。

Q4
Sonar 和 OCR 都是怎么触发的？
回应

结论：Sonar 是定时任务（按日构建），OCR 是事件驱动（PR/MR 提交即触发）

Sonar 触发方式

  • 定时任务（按日构建）：配置 cron 定时触发全量扫描
  • CI 流水线触发：Maven/Gradle 插件在构建时扫描
  • 手动触发：在 SonarQube Web 界面手动执行
  • 不支持增量：每次都是全量扫描
  • 问题发现滞后：白天写的代码，第二天才知道问题
  • 扫描耗时长：大型模块单次约 1 小时
  • 单线程排队：一个项目扫描时其他项目等待

OCR 触发方式

  • PR/MR 提交自动触发（事件驱动）
  • 评论触发重审：/open-code-review
  • 本地手动：ocr review（工作区变更）
  • 分支对比：ocr review --from main --to feature
  • 单提交审查：ocr review --commit abc123
  • 全文件扫描：ocr scan .（不需要 git 历史）
  • CI 定时兼容：也可配 cron 跑 ocr scan
  • 增量审查：只审 diff，1-3 分钟出结果

关键区别：Sonar 的定时全量扫描是"事后体检"——代码已经合并了，第二天才发现问题。OCR 的事件驱动增量扫描是"门禁检查"——代码合并前就拦住问题，从流程上卡住问题代码上线入口。

一句话回应：Sonar 是定时任务全量扫描（按日构建，问题发现滞后，约1小时/次）；OCR 是事件驱动增量扫描（PR/MR 提交即触发，1-3分钟出结果，可直接做 CI 卡点）。OCR 也能兼容定时模式，但核心价值在于实时增量审查。
