# 产品版本记录编写规范（Markdown 版）
## **1. 总则**

### **1.1** **编写目的**

让用户/实施/运维/客户**一眼看懂版本价值、快速定位需求/缺陷、明确能否升级、知道如何升级**。

### **1.2** **适用范围**

产品发布、版本管理、升级指南、客户交付、内部研发同步。

---

## 2. 单版本信息结构（强制标准）
### 【VX.Y.Z】版本标题（一句话概括价值）

**版本价值说明**：建议3条以内，核心说明用户收益

**发布日期**：YYYY-MM-DD

**发布类型**：□ 基线 □ 增量 □ EI □ 补丁 

**新特性与需求清单（用户最关心价值）**

| 需求ID           | 特性/需求名称                | 价值说明（用户视角）                                         | 对应模块                          | 参考文档     |
| ---------------- | ---------------------------- | ------------------------------------------------------------ | --------------------------------- | ------------ |
| 必须填写，可追溯 | 简洁、业务化，不使用技术术语 | 特性价值以及明确“用户得到什么好处”（如：更快、更稳、更简单、支持XX场景） | 明确前端/后端/接口/监控/部署/运维 | 相关文档说明 |

**缺陷修复清单**

| 缺陷ID       | 缺陷标题             | 影响范围                                     | 影响程度    | 触发条件                           | 修复说明                          | 修复版本               | 参考文档     |
| ------------ | -------------------- | -------------------------------------------- | ----------- | ---------------------------------- | --------------------------------- | ---------------------- | ------------ |
| 必须唯一可查 | 写现象，不写技术细节 | 明确：哪些版本、哪些部署模式、哪些功能受影响 | □低 □中 □高 | 简单清晰，便于用户判断自己是否遇到 | 写“修复了XXX问题”，不要写代码逻辑 | 明确从哪个版本开始修复 | 相关文档说明 |

- **影响程度**
  - 低：界面显示、偶现、不影响业务
  - 中：功能异常、部分用户不可用
  - 高：业务中断、数据错误、服务不可用

**升级必要性**：□ 可选升级 □ 建议升级 □ 强制升级

并写明升级原因：强制升级（如：存在高危缺陷）；建议升级（如：新功能、性能提升）；可选升级（如：仅修复极个别场景问题）

**是否兼容**：

- **向前兼容**：□ 完全兼容 □ 部分兼容 □ 不兼容（需注意）
- **配置兼容**：□ 全兼容 □ 需修改 □ 不兼容
- **接口兼容**：□ 全兼容 □ 部分废弃 □ 不兼容
- **数据库兼容**：□ 无需变更 □ 需执行SQL □ 数据结构变更

**升级影响**：

- 影响模块：________________________
- 是否重启：□ 无需重启 □ 需重启服务 □ 需重启节点
- 是否停机：□ 无需停机 □ 需短暂停机 □ 需停机窗口
- 是否数据迁移：□ 不需要 □ 需要（自动） □ 需要（手动）

**升级注意事项**（强制：避免升级事故）

说明升级前置条件、风险、禁止升级场景

**升级步骤与方式**（标准化）

说明版本对应不同部署方式的升级步骤以及升级验证方法

**配套文档**（强制：可追溯、可交付）

| 文档名称 | 文档版本 | 适用版本 | 说明                     |
| -------- | -------- | -------- | ------------------------ |
| 部署手册 | ________ | VX.Y.Z   | ________________________ |
| 运维手册 | ________ | VX.Y.Z   | ________________________ |
| 接口文档 | ________ | VX.Y.Z   | ________________________ |
| 最佳实践 | ________ | VX.Y.Z   | ________________________ |
| FAQ文档  | ________ | VX.Y.Z   | ________________________ |

- **填写要求**
  - 每个版本必须明确**对应哪版文档**，禁止“最新文档”
  - 说明列写：文档更新了什么内容
  - 高：业务中断、数据错误、服务不可用

## 3. 编写规范（强制执行）
### 3.1 通用要求
1. **所有条目必须可追溯**：需求ID、缺陷ID、文档版本必填
2. **用户视角编写**：不说技术黑话，不说底层逻辑
3. **影响范围必须明确**：不写“部分影响”，写清楚影响哪些版本/环境/功能
4. **价值必须显性化**：用户必须一眼知道“我能获得什么”
5. **风险必须前置**：⚠️ 标注，禁止隐藏升级风险

### 3.2 字段填写强制规则
- **版本号**：统一 `VX.Y.Z` 格式
- **发布日期**：统一 `YYYY-MM-DD`
- **影响程度**：只能选低/中/高
- **升级必要性**：只能选可选/建议/强制
- **价值说明**：每条≤30字，业务化、收益化
- **缺陷影响**：必须写清楚“哪些版本、哪些场景受影响”
- **文档**：必须与版本同步更新，禁止滞后

### 3.3 禁止出现内容
- 模糊描述：“优化了性能”“修复了一些问题”
- 技术术语堆砌：“重构了XX模块”“优化了GC策略”
- 无依据结论：“应该没问题”“可能影响”
- 缺失风险：不写重启、不写备份、不写兼容
