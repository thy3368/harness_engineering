# 产品版本记录规范检查点（AI检查版）
| 检查维度      | 检查项         | 检查规则                                                     | 类型（强制/可选） |
| ------------- | -------------- | ------------------------------------------------------------ | ----------------- |
| 基础信息      | 版本号格式     | 版本号是否遵循 `VX.Y.Z` 统一格式,严格匹配 `VX.Y.Z` 格式，无自定义变体（如V1.0、1.0.0） | 强制              |
| 基础信息      | 发布日期格式   | 发布日期是否遵循 `YYYY-MM-DD` 统一格式,日期格式无偏差，无“2024.05.01”“2024-5-1”等不规范写法 | 强制              |
| 基础信息      | 发布类型选择   | 是否勾选基线/增量/EI/补丁其中一类,仅勾选一类，无多勾选、漏勾选情况 | 强制              |
| 版本价值      | 版本价值说明   | 核心说明用户收益，以用户视角描述收益（如更快、更稳、支持XX场景），无技术黑话 | 强制              |
| 版本价值      | 新特性价值说明 | 每条需求的价值说明明确“用户得到什么好处”,无模糊描述（如“优化了性能”），纯业务化、收益化表达 | 强制              |
| 需求/缺陷追溯 | 需求ID填写     | 新特性清单中需求ID必填且可追溯，无空值                       | 强制              |
| 需求/缺陷追溯 | 缺陷ID填写     | 缺陷修复清单中缺陷ID唯一且可查，无重复ID、无空值，可关联到缺陷管理系统对应条目 | 强制              |
| 缺陷修复      | 缺陷标题       | 仅描写业务现象，不包含技术细节，无“修复XX接口空指针问题”等技术化描述 | 强制              |
| 缺陷修复      | 缺陷影响范围   | 明确受影响的版本、部署模式、功能，无“部分影响”“可能影响”等模糊表述，范围具体可落地 | 强制              |
| 缺陷修复      | 缺陷影响程度   | 仅选择低/中/高其中一类，无多选择、无自定义程度描述（如“中高”） | 强制              |
| 缺陷修复      | 缺陷触发条件   | 简单清晰，便于用户判断是否遇到，无复杂技术逻辑描述，用户可直接对照自身场景 | 强制              |
| 升级决策      | 升级必要性     | 仅选择可选/建议/强制其中一类，并写明原因，原因与选项匹配（如强制升级需注明“存在高危缺陷”） | 强制              |
| 兼容性        | 向前兼容       | 选择完全兼容/部分兼容/不兼容其中一类，无模糊表述，不兼容需标注“需注意” | 强制              |
| 兼容性        | 配置兼容       | 选择全兼容/需修改/不兼容其中一类，选项唯一，需修改需明确修改范围 | 强制              |
| 兼容性        | 接口兼容       | 选择全兼容/部分废弃/不兼容其中一类，选项唯一，部分废弃需注明废弃接口名称 | 强制              |
| 兼容性        | 数据库兼容     | 选择无需变更/需执行SQL/数据结构变更其中一类，选项唯一，需执行SQL需注明SQL文件名称/内容 | 强制              |
| 升级影响      | 影响模块       | 明确填写受升级影响的模块，无空值、无“相关模块”等模糊表述     | 强制              |
| 升级影响      | 是否重启       | 选择无需重启/需重启服务/需重启节点其中一类，选项唯一，无“视情况而定”等表述 | 强制              |
| 升级影响      | 是否停机       | 选择无需停机/需短暂停机/需停机窗口其中一类，选项唯一         | 强制              |
| 升级影响      | 是否数据迁移   | 选择不需要/需要（自动）/需要（手动）其中一类，选项唯一，手动迁移需注明操作步骤（可选补充） | 强制              |
| 升级保障      | 升级注意事项   | 说明升级前置条件、风险、禁止升级场景，无缺失，风险项需标注⚠️，禁止场景明确具体 | 强制              |
| 升级保障      | 升级步骤与方式 | 说明不同部署方式的升级步骤及验证方法，步骤标准化，验证方法可落地（如“检查XX接口返回值是否正常”） | 强制              |
| 文档配套      | 配套文档填写   | 明确文档名称、版本、适用版本、更新说明，无“最新文档”表述，每个文档版本与产品版本一一对应，说明列填写文档更新内容 | 强制              |
| 通用规范      | 无模糊描述     | 无“优化了性能”“修复了一些问题”等表述，所有描述具体、可量化、可验证 | 强制              |
| 通用规范      | 无技术术语堆砌 | 无“重构XX模块”“优化GC策略”等技术黑话，全文以业务视角编写，非技术人员可理解 | 强制              |
| 通用规范      | 无无依据结论   | 无“应该没问题”“可能影响”等不确定表述，所有结论有明确依据（如缺陷ID、测试报告） | 强制              |
| 通用规范      | 升级风险前置   | 所有升级风险均前置标注，无隐藏，风险项无遗漏，高危风险需重点标注⚠️ | 强制              |
| 补充优化      | 手动迁移步骤   | 需手动数据迁移时，补充详细操作步骤，步骤清晰，包含前置检查、操作指令、验证方法 | 可选              |
| 补充优化      | 回滚方案       | 补充版本升级失败后的回滚步骤，回滚步骤可落地，包含回滚前置条件、操作流程、验证标准 | 可选              |
