## 模块一：架构分析讨论与组织

> 本模块是双周报的最重要部分。架构活动的主要内容是 **"架构分析讨论"**，发生在形成设计文档**之前**；这里要回答："本周期我组织起来了哪些设计前的讨论？关键点/难点是否讨论清楚了？"

**1.1 本周期组织/参与的架构分析讨论**

| 议题 | 关联需求/模块 | 讨论时机（设计前/设计中/设计后） | 参与人员 | 关键点与难点 | 讨论结论与决策 | 后续 Action | 负责人 |
| ---- | ------------- | -------------------------------- | -------- | ------------ | -------------- | ----------- | ------ |
|      |               | 设计前 / 设计中 / 设计后         |          |              |                |             |        |

> 填写要求：
> 1. **优先列"设计前"的讨论**——这是架构的首要责任。"设计后"的讨论（即评审）应当只是确认动作。
> 2. "关键点与难点"必须具体到技术点，不能写"方案讨论"这类笼统词。
> 3. 若本周期组织的讨论以"设计后评审"为主，需在 1.3 中说明原因与改进计划。

**1.2 设计前讨论覆盖率**

## 模块二：S/A 级需求 WBS（关键点、难点、阶段性进展）

> 本模块只列 **S 级和 A 级**需求，逐项展开 WBS。让管理层一眼看清：每个高难度需求的关键点是什么、当前推进到哪一步。

**2.1 S/A 级需求 WBS 清单**

| 需求编号 | 需求名称 | 难度等级（S/A） | 关键点（业务/技术目标） | 难点（必须预先验证的） | 当前阶段性进展 | 下阶段动作（双周内） | 计划完成时间 | 风险 |
| -------- | -------- | --------------- | ----------------------- | ---------------------- | -------------- | -------------------- | ------------ | ---- |
|          |          |                 |                         |                        |                |                      |              |      |

> 说明：
> - **难度等级定义**：**S级**：涉及核心架构变更/跨域；**A级**：单域架构调整；**B级**：模块级设计；**C级**：常规迭代。B/C 级需求不在本模块展开，仅汇总在模块四的合规检查中。
> - **关键点**：要做成什么（业务价值与技术目标）。
> - **难点**：为什么难（哪些能力/性能/兼容性是瓶颈）。难点必须能映射到模块三的预研动作。
> - **阶段性进展**：用动词+里程碑描述，例如"已完成原型验证 / 已输出概设 V0.5 / 主备切换通路已联调通过"。

## 模块三：难点预研与验证

> 难点不能只写在 WBS 里就完了，**必须在设计阶段做预先验证**。本模块对模块二中的每一个"难点"列出预研动作与结论。

**3.1 难点预研与验证记录**

| 关联需求/难点 | 预研方式（预研代码/查资料/原型验证/标杆对比/POC） | 预研结论 | 是否能达成目标 | 残留风险 | 后续动作 | 责任人 |
| ------------- | ------------------------------------------------- | -------- | -------------- | -------- | -------- | ------ |
|               |                                                   |          | 是 / 否 / 部分 |          |          |        |

> 填写要求：
> 1. 一条难点只要还在"在研"，就要在本表里出现，直到 **"是否能达成目标 = 是"** 后方可结束。
> 2. **"是否能达成目标 = 否"或"部分"** 的难点，必须配套写明残留风险与后续动作。
> 3. "查资料 / 原型验证"也是合法的预研方式，关键是对结论与目标可达性给出明确判断。
