# CRES/UFT 专家分析 Skill

## 1 描述

针对 CRES/UFT 文件提供专业的代码分析能力，识别文件结构、伪代码逻辑、内存操作和错误处理机制。

## 2 分析目标

深入理解 CRES/UFT 文件的业务逻辑和数据流，识别关键机制（事务处理、内存操作、批量处理）的使用情况，发现潜在问题（事务嵌套、错误处理缺失）。

## 3 适用条件

适用于 CRES/UFT 相关文件：
- `.uft` - 标准服务文件
- `.uftatomservice` - 原子服务文件
- `.uftfunction` - 函数文件
- `.uftatomfunction` - 原子函数文件
- `.uftstructure` - 结构定义文件
- `.uftfactorservice` - 因子服务文件
- `.uftfactorfunction` - 因子函数文件
- `.uftlogicservice_template` - 逻辑服务模板文件

## 4 核心知识库

### 4.1 基础识别

#### 4.1.1 文件类型识别

| 扩展名 | 类型 | 特点 |
|--------|------|------|
| `.uftservice` | 逻辑服务文件 | 包含业务逻辑服务（LS_前缀） |
| `.uftfunction` | 逻辑函数文件 | 包含逻辑函数（LF_前缀） |
| `.uftatomservice` | 原子服务文件 | 包含原子服务（AS_前缀） |
| `.uftatomfunction` | 原子函数文件 | 包含原子函数（AF_前缀） |
| `.uftfactorservice` | 因子服务文件 | 包含因子服务（RS_前缀） |
| `.uftfactorfunction` | 因子函数文件 | 包含因子函数（RF_前缀） |
| `.uftstructure` | 结构定义文件 | 定义数据结构和组件 |

#### 4.1.2 文件结构识别

```xml
<?xml version="1.0" encoding="UTF-8"?>
<business:Service 
  xmlns:business="http://www.hundsun.com/ares/studio/uft/business/1.0.0"
  chineseName="服务名称"
  description="服务描述"
  objectId="对象ID"
  id="唯一ID">
  
  <inputParameters id="param_name" uuid="..."/>
  <outputParameters id="result_name" paramType="COMPONENT" type="..." uuid="..."/>
  <internalParams id="internal1" name="..." paramType="NON_STD_FIELD" type="HsChar32" uuid="..."/>
  
  <code>
    // 伪代码内容
  </code>
</business:Service>
```

关键标签：
- `inputParameters` - 输入参数
- `outputParameters` - 输出参数
- `internalParams` - 内部参数
- `code` - 伪代码逻辑

#### 4.1.3 行内注释禁止规则

**规则：禁止在代码行中间添加注释（行内注释），会导致编译报错**

```yaml
# ❌ 错误：行内注释导致编译报错
inter_code = @inter_code_temp,  // 委托代码对应的证券内码

# ✅ 正确：注释移到代码上方作为独立注释行
// 委托代码对应的证券内码（供股权的内码），用于插入委托表
inter_code = @inter_code_temp,

# ✅ 正确：函数调用参数注释应放在函数调用上方
// 配股权益证券的stock_type（通常是1-股票，不是87）
// 原委托方向（9-配股认购）
// 撤成业务类型
[AF_权益可用_交易端可用处理][
  stock_type = @uft_cstockinfo.stock_type,
  entrust_direction = @uft_centrusts.entrust_direction,
  busin_pro_type = '6',
]
```

#### 4.1.4 命名规范识别

- 服务命名：`LS_/AS_/LF_/AF_/RS_/RF_模块名_功能描述`
- 参数命名：下划线分隔小写（`login_company`）
- 常量命名：`CNST_` 前缀 + 大写字母

> 完整命名规范、Object ID范围、数据类型体系 → `cres-rules/05-naming-structure.md`

### 4.2 语法速查

- **调用**：`[功能名称][输入参数列表][输出参数列表]`
- **参数引用**：`@参数名`，赋值 `@var = @expr`
- **宏调用**：`[宏名称][参数列表][输出列表]`
- **条件判断**：C风格 `if (条件) { }`，`unlikely()` 用于参数校验
- **报错返回**：`<W>[报错返回][ERR_XXXXXXX]`

> 完整语法规则（变量声明、循环、SQL嵌入、函数定义等）→ `cres-rules/01-syntax.md`

### 4.3 核心机制摘要

#### 4.3.1 事务处理

- **禁止嵌套**：事务块内调用的函数不能再包含 `[事务处理开始]`，否则当前事务被回滚
- **自动回滚**：分支导致 `[事务处理结束]` 未执行时，函数退出自动提交或回滚；报错时无需显式 `[事务回滚]`
- **调用链传递**：上级开事务后，下级不能再开事务；文档应标注"⚠️ 本服务可能被上级事务包裹"

> 完整事务规则与示例 → `cres-rules/03-mechanisms.md` §1

#### 4.3.2 并发加锁

- **立即加锁**：获取记录后必须立即 `[修改记录][表名][]` 空加锁，不能在业务判断之后
- **先锁指令表**：委托表有 `ins_id > 0` 时，必须先锁 `uft_cinstruction` 再锁委托表
- **统一顺序防死锁**：指令表 → 委托表 → 委托关系表 → 持仓表 → 资产单元表 → 成交表
- **委托表类型识别**：必须根据 `entrust_table_type` 识别委托表，禁止硬编码

> 完整加锁规则、委托表类型映射、各接口加锁速查 → `cres-rules/03-mechanisms.md` §2

#### 4.3.3 M 标记（双用途）

**用途1：批量容错** — `<M>[操作]` + `[处理失败]{ [继续执行] }`，单条失败不阻塞批量流程。

**用途2：记录存在性检查** — 必须使用 `<M>[获取记录]` + `[继续执行]`，否则记录为空时直接报错返回，后续 `[记录为空]` 分支无法执行。典型场景："存在则更新，不存在则插入"。

> 完整 M 标记规则与代码示例 → `cres-rules/03-mechanisms.md` §3

#### 4.3.4 while(true) 循环保护

- 必须实现9种保护机制（总条数限制、本次返回条数、EOF判断、**定位串比较**、error_no检查、同步调用失败、最大循环次数、解包器字段检查、记录跳过处理）
- **定位串比较最关键**：调用前置机接口前后比较定位串，相同则终止防死循环
- 必须定义内部变量：`prev_position_str`、`position_str_before`、`max_loop_count`、`loop_count` 等

> 完整保护机制清单与代码模板 → `cres-rules/03-mechanisms.md` §4

#### 4.3.5 内部变量定义

- 所有代码中使用的临时变量必须在 `<internalParams>` 中定义，否则 UFTDB 工具无法识别
- 必须属性：`id`（变量名）、`name`（中文描述）、`paramType="NON_STD_FIELD"`、`type`（数据类型）、`uuid`

> 完整定义规则与示例 → `cres-rules/03-mechanisms.md` §5

### 4.4 宏系统摘要

| 类别 | 常用宏 | 说明 |
|------|--------|------|
| **事务控制** | `[事务处理开始]` `[事务处理结束]` `[事务回滚]` | 禁止嵌套 |
| **内存操作** | `[获取记录-无拷贝]` `[插入记录]` `[修改记录]` `[删除记录]` | 全内存操作 |
| **遍历操作** | `[遍历记录开始-无拷贝]` `[遍历记录结束-无拷贝]` `[遍历记录为空]` | 循环遍历 |
| **流程控制** | `[正常返回]` `[继续执行]` `[处理成功]` `[处理失败]` | 分支控制 |
| **记录判断** | `[记录为空]` `[记录不为空]` `[记录赋值]` | 存在性检查 |
| **日志记录** | `[记录日志][级别][错误号][信息][字段]` | EVENT/ERROR/WARNING/DEBUG |
| **异步调用** | `[异步调用因子]` `[异步调用因子(多参数)]` | 因子异步 |
| **时间操作** | `[获取时间(毫秒)]` `[获取时间(微秒)]` | 计时 |

> 完整宏参数、签名、使用模式（含服务级标准流程）→ `cres-rules/02-macros.md`

### 4.5 典型模式摘要

| 模式 | 场景 | 关键要点 |
|------|------|---------|
| **事务处理** | 需要原子性的数据修改 | 获取→加锁→修改→提交，禁止嵌套 |
| **遍历处理** | 批量查询/修改记录 | 遍历→条件判断→修改，处理遍历为空 |
| **数据导出** | 导出查询接口 | `<E>` 保护 + `<M>` 外部数据 + continue |
| **撤单** | 撤销委托 | 委托关系表→委托表(立即加锁)→业务处理 |
| **成交** | 委托成交回报 | 指令表(先锁)→委托表(后锁)→业务处理 |

> 完整代码模板与详细步骤 → `cres-rules/04-patterns.md`

### 4.6 加锁规则摘要

- **加锁时机**：获取记录后立即加锁，禁止业务判断后再加锁
- **指令表优先**：`ins_id > 0` 时先锁 `uft_cinstruction` 再锁委托表
- **防死锁顺序**：指令表 → 委托表 → 委托关系表 → 持仓表 → 资产单元表 → 成交表
- **委托表识别**：根据 `entrust_table_type` 动态选择，禁止硬编码

> 完整加锁规则、委托表类型映射表、各接口加锁速查 → `cres-rules/03-mechanisms.md` §2

### 4.7 内部变量与 while(true) 保护

- 内部变量必须在 `<internalParams>` 定义（`id`/`name`/`paramType="NON_STD_FIELD"`/`type`/`uuid`）
- while(true) 循环必须实现9种保护机制，定位串比较最关键

> 完整规则与代码模板 → `cres-rules/03-mechanisms.md` §4-5

## 5 分析重点

### 5.1 关键检查点

#### 5.1.1 事务嵌套检查

**检查内容**：
- `[事务处理开始]` 是否被正确闭合
- 事务块内调用的函数是否包含事务处理
- 是否存在事务嵌套风险

**识别方法**：
```yaml
# 在事务块内搜索
[事务处理开始]
  ... 
  [调用函数]  # 检查该函数内部是否有[事务处理开始]
  ...
[事务处理结束]
```

#### 5.1.2 错误处理完整性

**检查内容**：
- 每个可能失败的操作是否有 `[处理失败]` 块
- 批量操作是否使用了 M 标记
- 错误日志是否记录了关键参数

**识别方法**：
```yaml
# 检查是否有遗漏
[获取记录-无拷贝][...]
# 缺少：[处理失败] { ... }

# 检查批量操作
[遍历记录开始-无拷贝][...]
  [AS_可能失败的操作][...]  # 缺少：<M> 包装
[遍历记录结束-无拷贝]
```

#### 5.1.3 内存操作正确性

**检查内容**：
- 是否使用了正确的内存操作宏
- 参数传递是否正确
- 输出参数是否被正确赋值

#### 5.1.4 参数引用正确性

**检查内容**：
- 所有 `@参数名` 是否已定义
- 参数类型是否匹配
- 参数作用域是否正确

### 5.2 常见问题识别

#### 5.2.1 事务嵌套问题

**问题模式**：
```yaml
[事务处理开始]
  [AS_某原子服务][...]  # 该原子服务内部包含事务处理
[事务处理结束]
```

**影响**：当前事务被回滚，数据不一致。

**修复建议**：重构原子服务，移除内部事务处理。

#### 5.2.2 批量处理缺少容错

**问题模式**：
```yaml
[遍历记录开始-无拷贝][...]
  [AS_可能失败的操作][...]  # 没有 M 标记
[遍历记录结束-无拷贝]
```

**影响**：单条记录失败会阻塞整个批量处理。

**修复建议**：添加 M 标记和错误处理。

#### 5.2.3 错误处理缺失

**问题模式**：
```yaml
[获取记录-无拷贝][对象][条件][输出]
# 没有 [处理失败] 块
```

**影响**：错误无法被捕获和处理，导致流程异常。

**修复建议**：添加标准错误处理模式。

#### 5.2.4 M 标记过度使用

**问题模式**：
```yaml
<M>[遍历记录开始][...]  # 遍历操作预期不会失败
```

**影响**：性能下降，保护机制冗余。

**修复建议**：移除不必要的 M 标记。

#### 5.2.5 日志级别不当

**问题模式**：
```yaml
# 批量处理中使用 ERROR 级别
<M>[操作][...]
[处理失败]
{
  [记录日志][CNST_DLOGERROR][][单个记录处理失败][...]  # 应该用 WARNING
}
```

**影响**：日志过多，影响监控和诊断。

**修复建议**：批量处理中使用 WARNING 级别。

#### 5.2.6 加锁时机过晚

**问题模式**：
```yaml
[获取记录][uft_cneeqentrusts][...]
# ❌ 先进行业务处理，此时记录未加锁
[AS_股转交易_撤单处理][...]
# ❌ 在业务判断后才加锁
if(@tmp_entrust_status == 'b')
{
  [修改记录][uft_cneeqentrusts][...]
}
```

**影响**：获取记录到加锁之间存在时间窗口，其他接口可能同时修改同一记录，导致数据不一致。

**修复建议**：获取记录后立即 `[修改记录][表名][]` 空加锁，然后再进行业务判断。

#### 5.2.7 指令表加锁缺失

**问题模式**：
```yaml
# ❌ 委托表有 ins_id > 0，但只锁委托表未锁指令表
[获取记录][uft_centrustrelation.uft_cneeqentrusts]
[修改记录][uft_cneeqentrusts][]
# 缺少：[修改记录][uft_cinstruction][]
```

**影响**：其他接口（撤成、撤单）可能同时修改指令表，导致指令成交数量计算不准确。

**修复建议**：如果 `ins_id > 0`，先 `[修改记录][uft_cinstruction][]` 再锁委托表。

#### 5.2.8 表更新顺序不一致导致死锁

**问题模式**：
```yaml
# 接口A：先锁委托表再锁指令表
[修改记录][uft_centrusts][]
[修改记录][uft_cinstruction][]

# 接口B：先锁指令表再锁委托表
[修改记录][uft_cinstruction][]
[修改记录][uft_centrusts][]
# ❌ 两个接口锁定顺序不同 → 死锁
```

**影响**：循环等待导致死锁。

**修复建议**：所有接口统一顺序——先锁指令表再锁委托表。

#### 5.2.9 while(true) 循环缺少保护机制

**问题模式**：
```yaml
while(true)
{
    # ❌ 没有最大循环次数限制
    # ❌ 没有定位串比较保护
    # ❌ 没有error_no检查
    [同步调用][...][...]
    # 如果定位串不变，会陷入死循环
}
```

**影响**：系统资源耗尽、服务不可用。

**修复建议**：实现全部9种保护机制（见 §4.8），特别是定位串比较保护和最大循环次数限制。

#### 5.2.10 获取记录缺少 M 标记和继续执行

**问题模式**：
```yaml
# ❌ 需要判断记录是否存在，但没有<M>标记
[获取记录][uft_centrustrelation(uft_uniq_entrustrelation_srlno)][...]
# ❌ 记录为空时直接报错返回，后续[记录为空]分支无法执行
[记录为空][uft_centrustrelation]
{
    # 这个分支永远无法执行
}
```

**影响**：需要"存在则更新，不存在则插入"的逻辑无法正确执行。

**修复建议**：使用 `<M>[获取记录][...]` + `[继续执行]`，确保记录为空时继续后续逻辑。

## 7 工具推荐

### 7.1 分析阶段

1. **Read** — 读取 CRES/UFT 文件内容，识别文件结构和伪代码
2. **Grep** — 搜索特定宏或模式的使用情况（如 `[事务处理开始]`、`<M>` 标记）
3. **structdb.py** — 查询数据结构、字典枚举值、错误码、字段引用关系

### 7.2 检查阶段

1. **Grep / rg** — 搜索事务处理、M 标记等关键模式，检查命名规范
2. **structdb.py dict/errorno** — 验证字典值和错误码是否与源码引用一致
3. **Read** — 逐文件检查伪代码语法的正确性、参数引用完整性

### 7.3 报告阶段

1. **Write** — 生成服务文档（9章节 markdown）
2. **Mermaid** — 在文档中绘制数据流图和调用关系图（flowchart/sequenceDiagram）
3. **check:quality** — 运行 `bun run check:quality --path <文件>` 验证文档质量
