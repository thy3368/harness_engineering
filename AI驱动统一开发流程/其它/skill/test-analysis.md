# 调用链路测试分析 Skill

## 1 描述

基于 design2/trace_chains 中的调用链路文档，用路径驱动法分析链路级集成测试用例，产出结构化的测试分析文档和内存表数据需求清单。

## 2 适用条件

- 已有调用链路文档（trace_chains/ 下）
- 调用链路文档包含 §4 决策节点和 §5 测试场景矩阵
- 需要为该链路生成链路级集成测试分析

## 3 核心方法：路径驱动法

### 3.1 原理

从调用链路的决策节点出发，沿每条分支路径推导测试场景。只组合同一执行路径上的决策节点，避免跨路径笛卡尔积爆炸。

### 3.2 核心概念

| 概念 | 定义 |
|------|------|
| **决策节点** | 代码中 if/switch/条件分支的判断点，决定执行走向 |
| **分支** | 决策节点的某个取值方向（如 operator_type=='2' → 运维分支） |
| **执行路径** | 从链路入口到某个出口，经过的决策节点分支组合 |
| **路径覆盖** | 每条执行路径至少被一个测试用例覆盖 |

### 3.3 路径枚举的精简原则

1. **只组合同一执行路径上的决策节点**：D1的分支决定了后续会经过哪些节点，不会走的节点不参与组合
2. **等价分支合并**：如果两个市场分支的测试数据构造方式相同（如上期/中金/能源走同一代码路径），只选一个代表
3. **独立维度正交**：D6(option_occupy_deposit信号)与D5(market_no)独立，只需在最常用市场分支上验证B6a一次
4. **前置校验单独覆盖**：异常/校验分支（如D2无权限、D3 asset_id缺失）单独成路径，不与计算路径组合

## 5 工作流程：先规划再执行

**强制规则**：收到测试分析请求后，必须先规划任务（TodoWrite），再逐步执行。禁止一次性输出完整分析文档。

### 5.1 总体流程

```
收到请求 → 读取调用链文档 → 规划子任务(TodoWrite) → 按依赖顺序逐步执行 → 整合产出
```

### 5.2 规划阶段（必须先做）

收到测试分析请求后，立即执行：

1. **读取调用链文档**：获取 §4 决策节点和 §5 测试场景矩阵，评估规模
2. **估算路径数量**：根据决策节点数和分支数，估算执行路径数量
3. **创建 TodoWrite 任务列表**：按 Step 1-6 拆分为子任务，标注依赖关系
4. **确认规划**：向用户展示任务列表和预估，确认后再开始执行

### 5.3 子任务定义

#### Step 1: 决策节点提取

**输入**：调用链路文档（trace_chains/ 下的 md 文件）
**操作**：
1. 读取调用链文档 §4 关键决策节点
2. 按执行路径上的顺序编号为 D1, D2, ...
3. 每个节点的分支编号为 B{n}{a/b/c...}
4. 识别哪些节点在同一执行路径上（D1的分支决定了后续经过哪些节点）

**产出**：§2 决策节点表

#### Step 2: 执行路径枚举

**输入**：§2 决策节点表
**操作**：
1. 按"只组合同一执行路径上的节点"原则枚举路径
2. 前置校验分支（异常/报错）单独成路径
3. 核心计算路径按精简原则组合（等价合并、独立维度正交）
4. 填写路径覆盖矩阵

**产出**：§3 执行路径枚举

#### Step 3: 路径详细分析

**输入**：§3 路径枚举 + 调用链文档 §3 数据流转矩阵
**操作**（每条路径执行一次，可并行）：
1. 根据决策条件组合，推导预期行为
2. 从数据流转矩阵提取该路径的关键输出字段
3. 反向推导内存表数据需求：要走这条路径，哪些表的哪些字段必须有特定值
4. 用 structdb 查询确认字段类型和字典值

**工具使用**：
```bash
python3 scripts/structdb.py struct <表名>          # 查看表结构和字典值
python3 scripts/structdb.py search <关键词>          # 搜索相关结构
python3 scripts/structdb.py refs <表名>             # 查看引用关系
```

**产出**：§4 路径详细分析

**并行化**：路径数 ≤ 5 时在当前任务中顺序完成；路径数 > 5 时按组分派子任务并行执行，每组 3-5 条路径。

#### Step 4: 内存表数据需求汇总

**输入**：§4 各路径的数据需求
**操作**：
1. 合并所有路径涉及的内存表
2. 每张表标注：哪些路径需要、哪些字段需要特定值
3. 用 structdb 补充字段类型和字典值
4. 生成字段交叉引用表

**产出**：§5 内存表数据需求汇总

#### Step 5: 测试用例清单与覆盖度分析

**输入**：§4 路径分析 + §5 数据需求
**操作**：
1. 每条路径映射为一个测试用例
2. 填写入参要点、预期输出要点、前置数据要点
3. 计算路径覆盖率和分支覆盖率
4. 标记未覆盖项

**产出**：§6 测试用例清单 + §7 覆盖度分析

#### Step 6: 文档整合与索引更新

**输入**：Step 1-5 的产出
**操作**：
1. 按模板组装完整文档
2. 写入 design2/test_cases/{域}/{子模块}/TC_{ID}_{名称}.md
3. 更新 design2/test_cases/_index.md 全局索引

**产出**：最终测试分析文档

### 5.4 子任务依赖图

```
Step 1 (决策节点提取)
  └── Step 2 (路径枚举)
        ├── Step 3-1 (PATH-01 分析) ──┐
        ├── Step 3-2 (PATH-02 分析) ──┤
        ├── Step 3-3 (PATH-03 分析) ──┤  可并行
        ├── ...                       ├──
        └── Step 3-N (PATH-N 分析) ──┘
              └── Step 4 (数据需求汇总)
                    └── Step 5 (用例+覆盖度)
                          └── Step 6 (文档整合)
```

### 5.5 规模判断与子任务策略

| 路径数量 | Step 3 策略 | 说明 |
|---------|------------|------|
| ≤ 5 | 当前任务顺序完成 | 规模小，无需并行 |
| 6-15 | 分 2-3 组并行 | 每组 3-5 条路径，用子任务派发 |
| > 15 | 分 3-5 组并行 | 每组 3-5 条路径，重点保证覆盖率 |

### 5.6 子任务拆分示例

以 1401610_期货资金可用查询 为例（11条路径），展示规划阶段的 TodoWrite 输出：

```
[todo]
1. [pending] Step 1: 从调用链文档提取6个决策节点（D1-D6）
2. [pending] Step 2: 枚举执行路径，填写覆盖矩阵（预估11条）
3. [pending] Step 3-A: PATH-01~04 路径详细分析（普通操作员路径）
4. [pending] Step 3-B: PATH-05~07 路径详细分析（特殊场景+异常路径）
5. [pending] Step 3-C: PATH-08~11 路径详细分析（运维操作员路径）
6. [pending] Step 4: 汇总内存表数据需求
7. [pending] Step 5: 生成测试用例清单和覆盖度分析
8. [pending] Step 6: 文档整合，写入文件，更新索引
```

**关键设计**：
- Step 3 是唯一可并行的步骤，按操作员类型/场景分组派发子任务
- Step 1/2 产出是 Step 3 的输入，必须顺序完成
- Step 4/5/6 依赖 Step 3 全部完成，必须串行

## 6 路径分析要点示例

以 1401610 的 PATH-01 为例，展示单条路径的分析要点：

**路径**：普通操作员 → 有权限 → 非直连 → 郑商所 → 期权传值

**决策条件**：D1=B1a, D2=B2b, D3=B3b, D4=B4b, D5=B5a, D6=B6b

**反向推导数据需求的核心思路**：

| 决策条件 | 推导出的数据需求 |
|---------|---------------|
| D1=B1a (operator_type≠'2') | uft_coperator.operator_type ≠ '2' |
| D2=B2b (入参组件>0) | uft_coper*right 表有匹配权限记录 |
| D3=B3b (asset_id>0) | uft_casset.asset_id > 0 |
| D4=B4b (capital_account_id≠0) | uft_cassetday.capital_account_id > 0 |
| D5=B5a (郑商所) | uft_cfuturesinfo.market_no = 4 |
| D6=B6b (期权占用≥0) | AS层已计算 option_occupy_deposit ≥ 0 |

**这样每条路径都能清晰地从决策条件反推到具体的数据构造要求。**
