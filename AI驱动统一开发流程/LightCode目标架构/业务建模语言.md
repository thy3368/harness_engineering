# AI 驱动一体化研发流程业务建模语言目标架构说明

## 1. 文档目标

本文档按经典编译器三分法描述 **业务建模语言体系** 的目标架构，重点解决当前 Frontend 侧 DSL 分散、模型设计器与语言耦合、AI 使用入口不稳定、语义治理不统一等问题。

目标不是继续增加一种新的 DSL，而是形成一套统一的 **业务建模语言**：

- Frontend 只面向一种业务建模语言规格。
- HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等历史格式不再作为并列 DSL 发展，而是通过兼容适配进入统一语言。
- Middle 负责统一 IR、语义模型、类型系统、校验、影响分析和测试语义。
- Backend 负责把统一 IR 生成 Java / C++ / SQL / 配置 / 测试代码等工程产物。
- 开发工具、AI Agent、CLI、模型设计器都调用同一套语言能力，不各自实现解析、校验和生成逻辑。

分层口径如下：

| 层次 | 定位 | 核心问题 |
|------|------|----------|
| Frontend | 统一业务建模语言输入层 | 业务逻辑如何用一种语言进入统一 IR |
| Middle | 统一业务建模语言 IR 与语义治理层 | 业务语义如何被稳定表达、校验、测试和复用 |
| Backend | 目标语言与工程产物生成层 | 统一 IR 如何生成 Java / C++ / SQL 等目标产物 |

## 2. 总体目标架构

```text
业务需求 / 结构化需求 / 可视化模型 / 历史 DSL / 存量元数据
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Frontend：统一业务建模语言输入层                │
│ - 统一业务建模语言规格                         │
│ - 文本语法 / 可视化模型 / AI 生成结构            │
│ - 历史 DSL 兼容适配：HSDDML / HFlow / YML / XML │
│ - 语法检查 / 格式化 / 诊断 / CLI / LSP          │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Middle：统一业务建模语言 IR 与语义治理层         │
│ - 统一 IR / AST / 语义模型                     │
│ - 元数据规范 / 类型系统 / 引用关系              │
│ - 语义校验 / 影响分析 / 测试语义 / 资产复用      │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ Backend：目标语言与工程产物生成层               │
│ - Java Generator / C++ Generator / SQL Generator│
│ - 配置生成 / 测试代码生成 / 工程模板适配         │
│ - JRES / CRES / 构建流水线 / 生成报告           │
└──────────────────────────────────────────────┘
                    │
                    ▼
Java / C++ / SQL / 配置 / 测试代码 / 工程产物
```

核心变化：

| 原有状态 | 目标状态 |
|----------|----------|
| 多种 DSL 并列存在 | 一种业务建模语言作为唯一目标语言规格 |
| 各工具各自解析 DSL | 工具统一调用 Frontend 编译能力 |
| 可视化模型绑定具体工具格式 | 可视化模型只是业务建模语言的一种编辑视图 |
| AI 直接生成多种目标格式 | AI 优先生成统一业务建模语言，再由工具校验和生成 |
| 旧 DSL 与新语言关系不清 | 旧 DSL 通过适配器迁移到统一语言，不再扩散语义 |

## 3. Frontend：统一业务建模语言输入层

### 3.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 定义唯一的业务建模语言输入规格，将文本、可视化模型、AI 生成结构和历史 DSL 统一解析为标准语法结构。 |
| 输入契约 | 接收业务建模语言文本、结构化需求、可视化模型、AI 生成片段，以及 HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等历史格式。 |
| 输出契约 | 输出可进入 Middle 层的 AST、模型结构、元数据引用、初步语义结构和诊断结果。 |
| 交互契约 | 与开发工具、CLI、LSP、AI Agent、模型设计器、文件系统和历史格式适配器交互。 |
| 质量契约 | 语法稳定、格式统一、错误可诊断、版本可识别、适合 AI 局部生成和局部修复。 |

Frontend 的目标不是维护多个入口语言，而是把所有入口收敛到同一个业务建模语言规格：

```text
业务建模语言文本 ───────────────┐
可视化模型编辑结果 ─────────────┤
AI 生成业务结构 ────────────────┤
历史 DSL 兼容适配结果 ──────────┤
                                ▼
                      统一业务建模语言 Frontend
                                │
                                ▼
                          AST / 初步语义结构
```

### 3.2 统一语言表达范围

| 表达类型 | 目标能力 |
|----------|----------|
| 数据模型 | 表达领域对象、字段、枚举、约束、索引、关系和版本。 |
| 接口模型 | 表达服务接口、输入输出、错误码、幂等、权限和兼容规则。 |
| 流程模型 | 表达业务流程、步骤、分支、并行、补偿、异常路径和状态迁移。 |
| 规则模型 | 表达校验规则、计算规则、准入规则、风控规则和派生字段。 |
| 查询模型 | 表达查询条件、聚合、排序、分页、权限过滤和数据访问意图。 |
| 测试模型 | 表达测试场景、输入数据、预期结果、断言和覆盖目标。 |
| 生成配置 | 表达目标语言、工程模板、生成策略、命名规则和运行参数。 |

### 3.3 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 业务建模语言 Spec | 定义统一语法、语义、版本、禁用写法、示例和兼容规则。 |
| 文本解析器 | 解析业务建模语言文本，生成 AST、语法诊断和格式化结果。 |
| 可视化模型适配器 | 将设计器中的图形编辑结果转换为业务建模语言结构。 |
| AI 生成适配器 | 将结构化需求和 AI 输出约束为合法的业务建模语言片段。 |
| 历史 DSL 适配器 | 将 HSDDML、HFlow JSON、大数据 YML、表设计器 XML 转换为统一语言结构。 |
| 语法检查器 | 支持语法错误检查、引用预检查、版本检查和可读诊断。 |
| 格式化器 | 提供统一格式化，减少人工、AI、设计器生成结果的差异。 |
| LSP 服务 | 支持语法高亮、补全、跳转、引用查找、悬浮说明和快速修复。 |
| CLI 工具 | 提供 parse、check、format、convert、diff、explain 等命令，方便 AI 和流水线调用。 |

### 3.4 历史 DSL 统一策略

HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等格式需要保留读取能力，但目标上不再作为新的业务语义扩展点。

| 历史格式 | 目标定位 | 处理方式 |
|----------|----------|----------|
| HSDDML | 历史数据建模来源 | 转换为统一业务建模语言的数据模型。 |
| HFlow JSON | 历史流程编排来源 | 转换为统一业务建模语言的流程模型。 |
| 大数据 YML | 历史数据处理配置来源 | 转换为查询模型、流程模型或生成配置。 |
| 表设计器 XML | 历史表结构设计来源 | 转换为数据模型和元数据引用。 |
| 其他元数据 DSL | 历史工具资产来源 | 通过适配器转换，不能绕过统一语言直接进入 Middle。 |

统一策略如下：

| 策略 | 说明 |
|------|------|
| 只进不扩 | 历史 DSL 可以被导入和迁移，但不继续扩展新语义。 |
| 转换优先 | 历史 DSL 先转换为统一业务建模语言，再进入 Middle。 |
| 诊断透明 | 转换过程输出字段映射、语义缺失、兼容风险和人工确认项。 |
| 双轨过渡 | 过渡期保留旧格式读取，但目标产物以统一业务建模语言为准。 |
| 统一测试 | 迁移后的模型必须进入统一语法检查、语义校验和测试语义。 |

### 3.5 语言与设计器解耦

可视化设计器不应拥有独立业务语义。设计器只是业务建模语言的一种编辑方式。

| 边界 | 说明 |
|------|------|
| 语言规格 | 定义业务对象、流程、规则、接口、测试和生成配置的标准表达。 |
| 设计器 | 负责图形化编辑、拖拽、布局、属性面板和交互体验。 |
| 保存格式 | 以业务建模语言文件或其结构化等价形式为主，设计器布局信息单独保存。 |
| 校验入口 | 设计器保存、导入、生成前都调用统一 Frontend check。 |
| 差异比较 | 业务语义 diff 基于语言结构，布局 diff 不影响业务语义。 |

## 4. Middle：统一业务建模语言 IR 与语义治理层

### 4.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 承接 Frontend 输出，形成统一 IR，负责业务语义治理、元数据引用、类型系统、依赖关系、影响分析、测试语义和资产复用。 |
| 输入契约 | 接收 AST、模型结构、元数据引用、初步语义结构、诊断上下文和版本信息。 |
| 输出契约 | 输出稳定、透明、可测试、可翻译、可复用的统一业务建模语言 IR。 |
| 交互契约 | 与 Frontend、Backend、测试工具、影响分析工具、业务建模语言仓库和开发工具交互。 |
| 质量契约 | IR 语义稳定、向下兼容、可审查、可追踪、可测试、可生成。 |

### 4.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| 统一业务建模语言 IR | 作为业务逻辑的核心中间表达，屏蔽输入形式差异。 |
| AST / 语义模型 | 承载语法结构、语义节点、引用关系、依赖关系和来源位置。 |
| 元数据规范 | 管理数据模型、接口模型、流程模型、规则模型、查询模型和测试模型。 |
| 类型系统 | 管理字段类型、对象类型、表达式类型、接口类型、集合类型和枚举类型。 |
| 语义校验 | 校验引用合法性、类型一致性、流程完整性、规则冲突和兼容性。 |
| 影响分析 | 分析需求、模型、IR、生成代码、测试资产和运行反馈之间的影响关系。 |
| 测试语义模型 | 支撑 IR 测试、测试用例生成、断言生成和测试报告生成。 |
| 资产复用接口 | 支撑组件、模板、规则、测试、生成策略和领域知识复用。 |
| 版本兼容模型 | 管理语言版本、IR 版本、生成器版本和历史模型迁移关系。 |

### 4.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 分散元数据规范 | 各类 DSL 和工具中已有部分元数据表达，但缺少统一治理。 |
| 局部语义模型 | 不同工具内可能已有局部模型、流程或规则表达。 |
| 局部校验能力 | 部分工具具备格式校验、模型校验或生成前校验。 |
| 组件化资产雏形 | 存在可复用业务逻辑或模板，但缺少统一仓库治理和测试绑定。 |
| 历史格式适配经验 | 已有 HSDDML、HFlow、大数据 YML、表设计器 XML 等格式理解基础。 |

### 4.4 差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 缺少统一 IR 定义 | 定义统一业务建模语言 IR、AST、语义模型和版本策略。 |
| 元数据规范分散 | 建立统一元数据规范、引用关系和兼容规则。 |
| 语义校验不统一 | 建设统一语义校验、类型系统和错误诊断协议。 |
| 测试语义不足 | 建立 IR 测试语义模型、测试生成规范和覆盖度反馈。 |
| 资产复用缺少治理 | 建设业务建模语言仓库与组件复用规范。 |
| 历史 DSL 语义不完整 | 为迁移过程建立缺失语义识别、人工确认和风险报告。 |

## 5. Backend：目标语言与工程产物生成层

### 5.1 逻辑架构

| 维度 | 内容 |
|------|------|
| 职责 | 将统一业务建模语言 IR 翻译为 Java / C++ / SQL 等目标语言代码，以及配置、测试代码和工程产物。 |
| 输入契约 | 接收统一 IR、元数据规范、翻译规则、目标语言参数、工程模板和测试语义。 |
| 输出契约 | 输出 Java / C++ / SQL、配置文件、测试代码、工程结构、生成报告和追踪映射。 |
| 交互契约 | 与 Middle、开发工具、代码仓库、构建流水线、JRES / CRES 等目标体系交互。 |
| 质量契约 | 生成结果可追踪、可重复、可构建、可测试，目标代码能追踪到 IR 和模型来源。 |

### 5.2 目标实现架构

| 模块 | 目标能力 |
|------|----------|
| Java Generator | 将 IR 生成 Java 服务代码、接口适配代码、校验代码和测试代码。 |
| C++ Generator | 将 IR 生成 C++ 业务代码、核心交易逻辑或低延迟代码。 |
| SQL Generator | 将 IR 生成 SQL 查询、脚本、视图或数据处理逻辑。 |
| 配置生成器 | 生成接口、规则、部署、运行参数和产品配置。 |
| 测试代码生成器 | 基于测试语义生成单元测试、集成测试、回归测试代码。 |
| 工程模板适配 | 适配不同目标工程结构、目录规范、构建方式和运行框架。 |
| 原生代码解析 | 支持 Java / C++ 存量代码理解、回迁和迁移辅助。 |
| 生成报告 | 输出生成结果、差异、依赖、失败原因和可追踪关系。 |

### 5.3 当前实现架构

| 当前实现 | 说明 |
|----------|------|
| 代码生成器 | 已有或计划中的目标代码生成能力。 |
| JRES | Java 方向运行、生成或工程承载体系。 |
| CRES | C / C++ 方向运行、生成或工程承载体系。 |
| 局部原生代码解析 | Java / C++ 存量代码解析能力需要进一步整合。 |
| 局部工程模板 | 不同目标语言或产品线可能已有独立工程模板。 |

### 5.4 差距与建设重点

| 差距 | 建设重点 |
|------|----------|
| 多语言生成规则不统一 | 建立统一 Backend 翻译规则、生成模板和目标语言参数。 |
| 生成结果可追踪不足 | 建设 IR 到目标代码的映射和生成报告。 |
| Java / C++ 生成体系分散 | 统一 JRES / CRES 与业务建模语言 IR 的对接方式。 |
| 存量代码迁移困难 | 建设原生代码解析、语义回迁和迁移辅助能力。 |
| 测试代码生成不足 | 建设基于 IR 测试语义的测试代码生成器。 |

## 7. AI 更友好、更原生的业务建模语言设计注意点

### 7.1 总体原则

AI 更友好的业务建模语言，不应只是“让 AI 更容易写代码”，而应让 AI 更容易 **理解业务语义、生成稳定结构、接受工具校验、解释变更原因、修复错误并沉淀资产**。

| 原则 | 说明 |
|------|------|
| 单一目标语言 | AI 不应在 HSDDML、HFlow、YML、XML 等格式之间选择，而应统一生成业务建模语言。 |
| 结构优先 | 语言表达应尽量结构化，减少大段自由文本。 |
| 语义显式 | 业务对象、字段、规则、流程、接口、状态、异常路径需要显式表达。 |
| 上下文可定位 | 每段语言结构应能定位到需求、模型、规则、测试或生成产物。 |
| 可校验 | AI 生成结果必须能被语法校验、语义校验、引用校验和测试校验。 |
| 可解释 | 语言结构应支持 AI 解释生成依据、引用对象、变更点和影响范围。 |
| 可修复 | 错误诊断应能反馈给 AI，驱动定向修复，而不是重新生成整段内容。 |
| 可复用 | 语言组件应具备参数化、模板化和测试绑定能力。 |

### 7.2 Frontend 设计注意点

| 设计点 | 说明 |
|--------|------|
| 统一输入规格 | Frontend 只定义一种业务建模语言，历史 DSL 通过适配器转换。 |
| 少歧义语法 | 避免同一业务含义存在多种等价写法，减少 AI 生成不稳定。 |
| 显式字段引用 | 字段、对象、服务、规则应使用可解析引用，而不是纯自然语言描述。 |
| 支持局部生成 | 支持 AI 只生成某个流程、规则、函数、接口或模型片段。 |
| 支持错误定位 | 语法错误、引用错误、缺失字段应能定位到具体节点。 |
| Prompt 友好 | 语言规格应能整理成 AI 可使用的 spec / skill / 示例集。 |
| CLI 友好 | parse、check、format、convert、diff、explain 命令应适合 AI Agent 自动调用。 |

### 7.3 Middle 设计注意点

| 设计点 | 说明 |
|--------|------|
| IR 结构稳定 | 统一业务建模语言 IR 应稳定，避免频繁破坏性变化。 |
| 语义节点明确 | 流程、规则、数据访问、服务调用、异常处理、测试断言应有明确节点类型。 |
| 元数据引用统一 | IR 中的对象、字段、接口、规则引用应统一指向元数据规范。 |
| 类型系统可解释 | 类型、枚举、集合、对象、表达式应能被 AI 和工具共同理解。 |
| 影响分析可计算 | IR 应保留依赖关系，支持变更影响分析。 |
| 测试语义内置 | 语言结构应能直接关联测试场景、输入数据、预期结果和断言。 |
| 版本兼容明确 | AI 生成和修复时需要知道当前语言版本、IR 版本和兼容约束。 |

### 7.4 Backend 设计注意点

| 设计点 | 说明 |
|--------|------|
| 生成规则确定 | 目标代码生成应由规则化 Backend 承担，避免完全依赖 LLM 直接出码。 |
| 目标语言差异显式 | Java / C++ / SQL 的差异应通过生成规则、模板和目标语言参数表达。 |
| 代码可追踪 | 生成代码应能追踪到对应 IR 节点、模型对象和业务规则。 |
| 支持差异生成 | 支持根据 IR 变更生成目标代码差异，而不是全量覆盖。 |
| 生成报告标准化 | 输出生成结果、失败原因、依赖关系和可追踪映射。 |
| AI 修复有边界 | AI 修复建议应优先回到业务建模语言或生成规则层，而不是直接修改目标代码。 |

### 7.5 AI 协作契约

| 契约 | 说明 |
|------|------|
| 上下文契约 | AI 输入应包含需求、模型、IR 片段、元数据、错误诊断、测试报告和资产示例。 |
| 生成契约 | AI 输出应优先生成统一业务建模语言结构，而不是历史 DSL 或目标语言代码。 |
| 校验契约 | AI 输出必须经过语法、语义、引用、兼容和测试校验。 |
| 解释契约 | AI 应能说明生成依据、引用对象、变更点和潜在影响。 |
| 修复契约 | AI 根据诊断结果进行局部修复，保留变更说明。 |
| 资产契约 | AI 生成或修复后的稳定片段可沉淀为组件、模板、规则或测试资产。 |

### 7.6 建设重点

| 建设重点 | 说明 |
|----------|------|
| 业务建模语言 Spec | 将语言语法、语义、示例、禁用写法整理成 AI 可消费规范。 |
| 标准示例库 | 提供数据模型、接口模型、流程模型、规则模型、查询模型、测试模型的高质量示例。 |
| 错误诊断协议 | 将工具诊断结果结构化，便于 AI 定向修复。 |
| 上下文组装规范 | 定义 AI 生成时应携带哪些需求、模型、IR、资产和测试上下文。 |
| 组件化表达 | 支持 AI 生成和复用小粒度、可测试、可组合的语言组件。 |
| 人工审查点 | 明确哪些 AI 生成结果需要业务架构师、开发人员或测试人员确认。 |

## 8. CLI 与工程化能力

业务建模语言要适合开发工具和 AI Agent 使用，必须提供稳定 CLI，而不是只依赖 IDE 插件或设计器。

| 命令 | 目标能力 |
|------|----------|
| parse | 将业务建模语言文件解析为 AST 或结构化 JSON。 |
| check | 执行语法检查、引用检查、版本检查和基础语义检查。 |
| format | 对业务建模语言文件执行统一格式化。 |
| convert | 将 HSDDML、HFlow JSON、大数据 YML、表设计器 XML 转换为统一业务建模语言。 |
| diff | 对比两个模型版本的业务语义差异。 |
| explain | 解释模型节点、引用关系、影响范围和生成来源。 |
| gen | 调用 Backend 生成目标语言代码、配置和测试代码。 |
| test | 执行 IR 测试、生成测试或回归测试。 |

CLI 输出需要稳定、结构化、可机器读取：

| 输出类型 | 说明 |
|----------|------|
| 诊断结果 | 包含文件、位置、错误码、严重级别、说明和修复建议。 |
| 转换报告 | 包含历史 DSL 到统一语言的字段映射、缺失语义和人工确认项。 |
| 影响分析报告 | 包含变更节点、受影响模型、生成产物和测试资产。 |
| 生成报告 | 包含生成文件、来源 IR、差异、失败原因和追踪映射。 |

## 9. 建设顺序建议

| 阶段 | 建设重点 |
|------|----------|
| 第一阶段 | 定义统一业务建模语言 Spec，明确 Frontend 不再发展多套 DSL。 |
| 第二阶段 | 建设 Frontend 文本解析、语法检查、格式化、CLI 和基础 LSP。 |
| 第三阶段 | 定义 Middle 统一 IR、AST、元数据规范、类型系统和语义校验。 |
| 第四阶段 | 建设 HSDDML、HFlow JSON、大数据 YML、表设计器 XML 到统一语言的转换适配器。 |
| 第五阶段 | 建设 Backend Java / C++ / SQL 生成能力，并对接 JRES / CRES。 |
| 第六阶段 | 建设 IR 测试、影响分析、资产仓库和 AI 修复闭环。 |

## 10. 总结

按 Frontend / Middle / Backend 分层后，业务建模语言体系的边界应进一步收敛：

- Frontend 负责“业务逻辑如何用一种语言进入统一 IR”。
- Middle 负责“业务语义如何被稳定表达和治理”。
- Backend 负责“统一 IR 如何生成目标语言和工程产物”。

目标架构的关键是统一掉 Frontend 的 DSL 分裂。HSDDML、HFlow JSON、大数据 YML、表设计器 XML 等历史格式应被纳入兼容适配和迁移路径，而不是继续作为并列语言发展。最终所有开发工具、AI Agent、CLI、模型设计器和生成器都应围绕同一套业务建模语言、同一套 IR 和同一套校验生成链路工作。
