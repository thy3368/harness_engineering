# 伪码编译生成目标架构拆分版

本文档参考《伪码编译生成当前实现架构及演进计划》，按目标架构口径将伪码编译生成拆分为两部分：

- **伪码及编译器**：公司级伪码语言、编译器、工具链和代码生成能力。
- **伪码设计器**：面向用户、可视化建模和 AI 的伪码编辑与设计入口。

两部分必须解耦：设计器不承载编译器语义，编译器不依赖设计器内部状态。双方只通过标准伪码文件、CLI / LSP / MCP、诊断协议、生成报告和追踪映射交互。

## 1. 总体目标架构

```text
业务需求 / 结构化需求 / 可视化模型 / AI 生成建议
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 伪码设计器                                    │
│ - 文本编辑 / 结构化编辑 / 可视化设计            │
│ - AI 伪码生成 / 诊断展示 / 生成触发             │
└──────────────────────────────────────────────┘
                    │
                    │ 标准伪码文件 / CLI / LSP / MCP / 诊断协议
                    ▼
┌──────────────────────────────────────────────┐
│ 伪码及编译器                                  │
│ - 伪码规范 / 解析校验 / 统一 IR                │
│ - Java / C++ / SQL 生成 / 测试 / 生成报告       │
└──────────────────────────────────────────────┘
                    │
                    ▼
Java / C++ / SQL / 配置 / 测试代码 / 生成报告
```

## 2. 当前状态映射

当前实现以 **UF30 伪代码工具** 为起点，吸收 **Ares Studio** 成熟实践，逐步统一为公司级伪码体系。

| 当前能力 | 现状 | 目标归属 |
|----------|------|----------|
| UF30 伪代码工具 | IDEA 插件形态，偏 Java 生成，HEP 功能较完整。 | 设计器 + 编译器起点 |
| Ares Studio 伪代码 | Eclipse 形态，偏 C/C++ 平台，已有成熟业务实践。 | 编译器语法与生成实践输入 |
| IDEA 插件 | UF30 当前主要入口，过渡期继续维护。 | 设计器过渡形态 |
| VSCode 插件 | 目标主力入口，承接编辑、补全、诊断、生成触发。 | 设计器目标形态 |
| CLI 核心 | 目标 Headless 能力，承载编译、校验、生成、报告。 | 编译器目标形态 |
| 元数据能力 | 依赖 HEP 现有规范修订扩展。 | 编译器与设计器共同依赖 |

## 3. 第一部分：伪码及编译器

伪码及编译器是底层语言和工具链能力，目标是把标准伪码稳定、低成本、可追踪地编译为工程产物。

### 3.1 当前问题

| 问题 | 表现 | 影响 |
|------|------|------|
| 语法体系分立 | Ares Studio 与 UF30 语法相似但分别维护。 | 知识无法共享，难以形成公司级统一中间表达。 |
| 编译器分立 | Ares 偏 C/C++，UF30 偏 Java，两套解析器和生成器独立演进。 | Java / C++ / SQL 多目标生成无法统一。 |
| 编译器与 IDE 耦合 | UF30 当前为 IDEA 插件形态，核心能力未充分 Headless 化。 | 难以接入 VSCode、CI/CD 和 AI Agent。 |
| 元数据规范分散 | HEP、HSDDML、HFlow、YML、XML 等格式分散。 | 伪码引用、代码生成、影响分析和追踪映射不稳定。 |
| 生成质量闭环不足 | 编译错误信息、边界 case、回归测试、生成报告仍需加强。 | 生成代码质量不稳定，推广依赖人工兜底。 |

### 3.2 目标能力

| 能力 | 目标 |
|------|------|
| 标准伪码规范 | 统一语法、语义、版本、禁用写法、元数据引用和示例。 |
| 统一编译器 | 抽取 UF30 编译器为独立模块，吸收 Ares Studio 成熟语法实践。 |
| 统一 IR | 让生成器依赖稳定 IR，而不是直接依赖文本伪码或 IDE 状态。 |
| 多目标生成 | 支持 Java / C++ / SQL、配置和测试代码生成。 |
| 元数据治理 | 与元数据规范 v1.0 同步发布，统一字段、接口、错误码、权限和引用关系。 |
| 工具链能力 | 提供 check、fmt、lint、generate、test、diff、doc、report 等 CLI 能力。 |
| 追踪报告 | 建立需求、伪码、IR、源码、测试之间的可追踪链路。 |

### 3.3 价值点

| 价值点 | 说明 |
|--------|------|
| 降低重复维护 | 消除 Ares Studio 与 UF30 两套伪码体系重复演进成本。 |
| 支持多目标生成 | 将 Java / C++ / SQL 生成统一到同一套伪码和 IR 体系下。 |
| 降低 AI token 成本 | 高频稳定场景走编译生成，生成阶段不依赖模型推理。 |
| 支持 CI/CD | CLI Headless 化后，校验、生成、测试可进入流水线。 |
| 提升可追踪性 | 生成产物可回溯到伪码、IR、元数据和需求来源。 |

### 3.4 演进计划

| 阶段 | 编译器演进重点 |
|------|----------------|
| 2026-05 | 收编 UF30，发布 v0.1.0；启动伪代码语法规范和元数据规范草案。 |
| 2026-06~07 | 抽取 CLI 核心；发布伪代码语法规范 v1.0 和元数据规范 v1.0。 |
| 2026-08~10 | 增强编译器错误信息、编译速度和边界 case；启动 C++ / SQL 输出增强。 |
| 2026-11~12 | 完成伪代码 -> Java 代码生成 MVP；完成生成质量和回归测试验收。 |
| 2027 | 完成三范式支持，推进多目标生成优化和元数据规范 v2.0。 |
| 2028 | 形成全面一体化能力，支持需求 -> 伪码 -> 代码 -> 测试闭环。 |

## 4. 第二部分：伪码设计器

伪码设计器是上层入口能力，目标是让用户、可视化建模工具和 AI 都能稳定产出标准伪码，并调用编译器完成校验和生成。

### 4.1 当前问题

| 问题 | 表现 | 影响 |
|------|------|------|
| IDE 入口碎片化 | Eclipse、IDEA、VSCode、Web 等多入口并存。 | 用户体验割裂，插件能力重复建设。 |
| UF30 入口偏 IDEA | UF30 当前主要依赖 IDEA 插件。 | VSCode 化和统一 IDE 推广需要迁移成本。 |
| 可视化与伪码边界不清 | 可视化模型和伪码之间缺少稳定转换契约。 | 容易把画布状态、表单状态误当作编译器输入。 |
| AI 输出缺少统一入口 | AI 可能直接生成代码或非标准伪码。 | 输出不可控，难以审查、校验和编译。 |
| 诊断展示依赖工具实现 | 诊断、差异、生成报告缺少统一展示协议。 | 设计器容易复制编译器语义，形成二次规则。 |

### 4.2 目标能力

| 能力 | 目标 |
|------|------|
| 伪码编辑 | 支持文本编辑、结构化编辑、局部修改和版本管理。 |
| 可视化设计 | 可视化设计结果必须转换为标准伪码后再进入编译器。 |
| AI 辅助 | 调用 AI 生成伪码、解释诊断、修复错误、生成伪码测试用例。 |
| 诊断展示 | 展示编译器返回的诊断、差异、影响范围、生成报告和审查关注点。 |
| 生成触发 | 通过 CLI / MCP 触发校验、格式化、生成、测试和报告输出。 |
| 编辑期能力 | 通过 LSP 获取诊断、补全、跳转和悬浮说明。 |
| 上下文组织 | 为 AI Agent 组装需求、伪码、诊断、元数据、代码片段和测试反馈。 |

### 4.3 价值点

| 价值点 | 说明 |
|--------|------|
| 降低 IDE 碎片化 | VSCode 自封装作为长期主力形态，IDEA 插件作为过渡形态。 |
| 保持编译器解耦 | 设计器不复制语义规则，不依赖 AST / IR / 生成器内部实现。 |
| 提升 AI 可控性 | AI 以标准伪码为目标输出，生成内容可校验、可审查、可编译。 |
| 提升用户体验 | 用户在设计器中完成编辑、诊断查看、生成触发和报告查看。 |
| 支持可视化演进 | 可视化设计通过标准伪码与编译器交互，不把 UI 状态传入编译器。 |

### 4.4 演进计划

| 阶段 | 设计器演进重点 |
|------|----------------|
| 2026-05 | UF30 IDEA 插件作为首个可用版本发布，保障现有用户可用。 |
| 2026-06~07 | 建设 VSCode 伪码插件骨架，支持语法高亮、补全、错误提示和编译触发。 |
| 2026-08 | 完善 VSCode 元数据管理能力，支持元数据与伪码关联跳转。 |
| 2026-09~10 | 发布 VSCode 自封装 IDE Beta，内置 UDP 核心插件包。 |
| 2026-11~12 | 发布 UDP v1.0（VSCode 形态），IDEA 插件进入维护模式。 |
| 2027 | 建设可视化与伪码双向绑定 MVP，完善设计器和标准伪码转换契约。 |
| 2028 | 支持 AI Agent 深度接入，实现需求、伪码、代码、测试的交互式闭环。 |

## 5. 解耦原则

- 编译器的权威输入是标准伪码，不是设计器内部状态。
- 设计器负责编辑、展示、上下文组织和工具触发，不实现编译器语义。
- 编译器负责解析、校验、IR、生成、诊断和报告，不承载设计器 UI 状态。
- 可视化设计结果必须落为标准伪码，才能进入编译器。
- AI 可以辅助生成伪码和解释诊断，但不能绕过标准伪码直接固化业务语义。
- CLI 是编译器能力的权威入口，IDE、设计器、AI Agent、CI/CD 都复用同一套命令能力。

## 6. 整体演进原则

- 以 UF30 为起点，不另起炉灶，优先继承已有用户群和使用习惯。
- 以统一伪代码体系为主轴，吸收 Ares Studio 成熟实践。
- 以 CLI 核心承载编译、校验、生成能力，IDE 只做入口和交互适配。
- 以 VSCode 自封装作为长期主力形态，IDEA 插件作为过渡期维护形态。
- 以元数据规范和伪代码语法规范同步治理，保证生成结果可追踪、可测试、可复用。
