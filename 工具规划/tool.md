# 架构工具目标和规划

### 1.1 目标用户

- 架构师：用于架构守护、方案评审、规则沉淀

### 1.2 解决的问题

- 架构规则分散在文档和经验中，难以被稳定执行
- 需求、设计、代码之间缺少统一的架构约束和映射关系
- 评审依赖人工经验，效率低且结果不稳定
- 优秀架构案例和过程资产难以沉淀复用

### 1.3 不覆盖范围

- 不替代正式架构评审决策
- 不直接替代业务需求评审和测试验证

## 2. 建设目标

- 提升需求、设计、代码与架构规范的一致性
- 快速完成流程产出物的审查、打分和问题定位
- 提升过程产出物质量，降低后期返工成本
- 将架构规范、架构资产和 AI skill 能力串联成可执行工具链
- 形成可持续演进的架构治理能力

## 3. 规则依据

- 项目架构规范
- 技术选型规范
- 研发流程规范
- 架构资产库
- 历史优秀案例和常见问题清单

## 9. 研发团队配合要求

- 提供统一的需求和设计文档模板
- 提供统一的仓库目录规范和模块命名规范
- 统一管理 AI 辅助开发 skill 的访问地址和版本
- 提供架构资产的维护责任人和更新机制
- 为审查工具接入提供必要的仓库权限、文档权限和 CI 接入点

# 流程产出物审查对象

- 需求
- 设计
- AI辅助开发skill
- 架构资产
- 代码

# 流程产出物审查工具分类

- 需求审查工具：用于检查需求完整性、边界清晰度和非功能需求覆盖情况。
- 设计审查工具：用于检查架构分层、模块职责、依赖关系和技术方案合理性。
- AI 辅助开发 skill 审查工具：用于检查 skill 是否注入了正确的架构约束、上下文和使用规范。
- 架构资产审查工具：用于检查模板、规范、案例等架构资产的完整性、适用性和可复用性。
- 代码审查工具：用于检查代码结构、模块边界、依赖方向和架构规范符合度。
- 综合评估工具：用于对各类流程产出物输出统一评分、问题清单和整改建议。

## 11. 实施路线

### 11.1 MVP 阶段

- MVP 先覆盖需求、设计、代码三类核心审查对象，后续扩展到 AI 辅助开发 skill 和架构资产
- 先实现基础检查、评分和报告输出
- 先以 skill 和脚本为主，不急于建设复杂平台

## 12. 成功标准

- 关键架构违规问题能够在开发前期被识别
- 设计评审效率和一致性明显提升
- AI 辅助开发输出更稳定地符合架构规范
- 架构资产复用率逐步提升
- 规则、资产、流程之间形成稳定闭环
